Your inbound webhook processor threw 500 exceptions two hours ago. You've stored the raw payloads. The upstream bug is fixed. Your first instinct is to write a quick Artisan command that loops through the failed rows and reprocesses each one.

Stop. "Replay the same body" is not always safe, and "the upstream bug is fixed" is not sufficient justification on its own.

Before you replay a single payload, answer three questions.

---

## Question 1: Has the upstream schema changed?

When your processor failed, you stored the body that arrived. You did not store the body that will arrive tomorrow. These may not be the same shape.

Schema drift is the most underestimated risk in webhook replay. The upstream service fixed their bug — but the fix might have also renamed a field, changed a type, or started sending additional required properties that your handler now expects. When you replay the old body, you're replaying the pre-fix shape through the post-fix handler.

Check this before anything else:

```php
// Validate the stored payload against your current rules
// before queuing it for replay

$validator = Validator::make(
    json_decode($failedWebhook->payload, true),
    OrderStatusWebhookRequest::rules(),
);

if ($validator->fails()) {
    $failedWebhook->update([
        'replay_status' => 'schema_mismatch',
        'replay_errors' => $validator->errors()->toArray(),
    ]);
    continue;
}
```

Schema mismatches must be surfaced as a distinct failure class — not silently skipped, not lumped in with processing errors. They tell you the stored payload is stale and needs a different resolution path (usually: re-fetch from source if the upstream exposes a resource endpoint).

**Stored-payload replay vs re-fetching from source**

If the upstream provides a REST endpoint for the resource (`GET /orders/{id}`), prefer re-fetching. You get the current canonical state rather than a snapshot from when things were broken. The tradeoff: you lose the exact point-in-time semantics — the status might have changed again since the webhook fired. Whether that matters depends on your domain. For most order status transitions it's fine. For payment notifications where the upstream event ID carries legal meaning, re-fetching changes what you're processing.

Know which situation you're in before you choose.

---

## Question 2: Is your handler idempotent?

Idempotency means processing the same payload twice produces the same outcome as processing it once. Your handler probably isn't idempotent by default.

The typical pattern: a webhook arrives, you create a record, send a confirmation email, fire a job. If you replay the payload, you create a duplicate record, send a second email, and fire the job again. The payload is identical. The consequences are not.

The fix is an idempotency key propagated from the webhook through every side effect.

Upstream webhook systems almost always send a unique event identifier in the payload or headers (`X-Webhook-ID`, `event_id`, `idempotency_key`). Use it:

```php
final class ProcessOrderStatusWebhook implements ShouldQueue
{
    public function __construct(
        private readonly string $webhookId,
        private readonly array $payload,
    ) {}

    public function handle(OrderRepository $orders): void
    {
        $order = $orders->findByNumber($this->payload['order_number']);

        // Guard: skip if this event was already applied
        if ($order->hasAppliedWebhookEvent($this->webhookId)) {
            return;
        }

        DB::transaction(function () use ($order) {
            $order->applyStatusTransition(
                status: OrderStatus::from($this->payload['status']),
                webhookEventId: $this->webhookId,
            );
        });
    }
}
```

The `hasAppliedWebhookEvent` check queries a table that records which event IDs have been processed for this aggregate. The check and the write happen inside the same transaction. Now it doesn't matter if this job runs once or ten times — the outcome is identical after the first run.

If the upstream doesn't send an idempotency key, derive one deterministically from the payload content:

```php
$webhookId = hash('sha256', $failedWebhook->payload);
```

This is fragile if the body includes timestamps or nonces that change per delivery, but for most structured payloads it works.

## Question 3: Do you have downstream side effects that can't be repeated?

Some operations are naturally idempotent. Database upserts, status transitions guarded by a state machine, cache invalidations — replay these freely.

Others are not. Make an explicit inventory before you replay anything:

- **Outbound emails** — does your handler call `Mail::send()`? Does it check whether the email was already sent?
- **Payment captures** — does the webhook trigger a charge or refund? Does your payment provider have idempotency key support and are you using it?
- **Third-party API calls** — does processing create a record in another system? Will that system create a duplicate if you post the same data twice?
- **Webhooks you fire to your own consumers** — do you forward events downstream? Will your consumers handle duplicates?

For each non-idempotent side effect, you need a guard. The pattern is the same: record that the side effect occurred, keyed on the webhook event ID, and check before executing.

```php
// Before sending a transactional email
if (WebhookSideEffect::wasExecuted($this->webhookId, 'order_confirmation_email')) {
    return;
}

Mail::to($order->customer_email)->send(new OrderConfirmedMail($order));

WebhookSideEffect::record($this->webhookId, 'order_confirmation_email');
```

This is more bookkeeping than most teams want to write upfront. That's fine — build it when you need it. But when you're staring at 500 failed payloads and deciding whether to replay, this inventory is what determines your answer.

## Build a dry-run mode first

Before you replay anything at production scale, run a dry-run pass that validates without executing:

```php
<?php

declare(strict_types=1);

namespace App\Console\Commands;

use App\Models\FailedWebhook;
use App\Http\Requests\OrderStatusWebhookRequest;
use Illuminate\Console\Command;
use Illuminate\Support\Facades\Validator;

final class ReplayFailedWebhooks extends Command
{
    protected $signature = 'webhooks:replay
        {--dry-run : Validate payloads without processing}
        {--limit=100 : Maximum number to process}
        {--chunk=25 : Batch size}';

    protected $description = 'Replay stored failed webhook payloads';

    public function handle(): int
    {
        $dryRun = $this->option('dry-run');
        $limit = (int) $this->option('limit');
        $chunk = (int) $this->option('chunk');

        $stats = ['valid' => 0, 'schema_mismatch' => 0, 'already_processed' => 0, 'queued' => 0];

        FailedWebhook::query()
            ->whereNull('replayed_at')
            ->oldest()
            ->limit($limit)
            ->chunk($chunk, function ($webhooks) use ($dryRun, &$stats) {
                foreach ($webhooks as $webhook) {
                    $body = json_decode($webhook->payload, true);

                    $validator = Validator::make($body, OrderStatusWebhookRequest::rules());

                    if ($validator->fails()) {
                        $stats['schema_mismatch']++;
                        $webhook->update(['replay_status' => 'schema_mismatch']);
                        continue;
                    }

                    $webhookId = $body['event_id'] ?? hash('sha256', $webhook->payload);

                    if (ProcessedWebhookEvent::where('webhook_id', $webhookId)->exists()) {
                        $stats['already_processed']++;
                        $webhook->update(['replay_status' => 'already_processed']);
                        continue;
                    }

                    $stats['valid']++;

                    if (! $dryRun) {
                        dispatch(new ProcessOrderStatusWebhook($webhookId, $body));
                        $webhook->update(['replayed_at' => now(), 'replay_status' => 'queued']);
                        $stats['queued']++;
                    }
                }
            });

        $this->table(
            ['Valid', 'Schema Mismatch', 'Already Processed', 'Queued'],
            [array_values($stats)],
        );

        return self::SUCCESS;
    }
}
```

Run with `--dry-run` first. Look at the schema mismatch count. If it's nonzero, you have decisions to make before you queue anything. If it's zero and already-processed is what you expect, proceed with the real run.

## Rollback: when half the replays succeed

Mass replay at scale means partial success is a near-certainty. Your queue worker will process some jobs before hitting an error. Some of those jobs will have committed database writes. Some will have sent emails.

Design for partial success from the start:

- Process in small batches with a delay between them (`--chunk=25` with a brief sleep is enough)
- Mark each webhook record atomically when it's queued, not when it's processed — so a failed job doesn't leave the record in an ambiguous state
- Keep the `replay_status` column as your ground truth; query it to understand where you are at any point

If a run goes sideways halfway through, you need to be able to answer: which webhooks were processed successfully, which were queued but failed, and which were never touched. The `replayed_at` and `replay_status` columns give you this. Don't skip them.

---

## The checklist

Before replaying stored webhook payloads:

1. **Schema validation** — run stored bodies through current validation rules; handle mismatches separately
2. **Idempotency** — confirm your handler is guarded by an event ID check; derive one if upstream doesn't provide it
3. **Side effects inventory** — list every external call your handler makes and confirm each has a guard
4. **Dry run** — validate the full batch before queuing a single job
5. **Chunk and monitor** — replay in small batches; watch your queue depth and error rate between chunks

Replay is a recovery mechanism, not a shortcut. The answers to these three questions determine whether you're recovering cleanly or creating a second incident on top of the first.
