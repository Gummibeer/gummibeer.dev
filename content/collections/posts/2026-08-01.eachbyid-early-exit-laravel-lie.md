The Laravel docs say you can stop chunk processing early by returning `false` from your callback. That's true — for `chunk()`. For `chunkById()` and `eachById()`, it depends on the version you're running, and on older versions it's simply ignored.

Here's the setup: you have 50,000 user records to process. You're chunking through them in batches of 500. Halfway through, you detect a condition that means you should stop — maybe you've hit a rate limit, or you've found the record you were looking for. You return `false`. And then… the loop keeps going.

## What `chunk` actually does

`Builder::chunk` is the straightforward one. It runs a `LIMIT`/`OFFSET` query for each page, calls your callback with the collection, and checks the return value:

```php
// Illuminate/Database/Query/Builder.php
public function chunk($count, callable $callback): bool
{
    $this->enforceOrderBy();

    $page = 1;

    do {
        $results = $this->forPage($page, $count)->get();
        $countResults = $results->count();

        if ($countResults == 0) {
            break;
        }

        if ($callback($results) === false) {
            return false;
        }

        unset($results);
        $page++;
    } while ($countResults == $count);

    return true;
}
```

`=== false` check, explicit early return. Returning `false` from your callback stops the loop and propagates a `false` return value up to the caller. Clean.

## What `chunkById` does

`chunkById` uses a cursor-style query — instead of `OFFSET`, it tracks the last seen ID and adds a `WHERE id > ?` clause on each iteration. This avoids the classic `OFFSET` performance cliff on large tables.

```php
// Illuminate/Database/Query/Builder.php
public function chunkById($count, callable $callback, $column = null, $alias = null): bool
{
    $column ??= $this->defaultKeyName();
    $alias ??= $column;
    $lastId = null;
    $page = 1;

    do {
        $clone = clone $this;
        $results = $clone->forPageAfterId($count, $lastId, $column)->get();
        $countResults = $results->count();

        if ($countResults == 0) {
            break;
        }

        if ($callback($results) === false) {
            return false;
        }

        $lastId = data_get($results->last(), $alias);

        if ($lastId === null) {
            throw new RuntimeException(
                "The chunkById operation was aborted because the [{$alias}] column is not present in the query result."
            );
        }

        unset($results);
        $page++;
    } while ($countResults == $count);

    return true;
}
```

In current Laravel (10+), this also checks `=== false`. So returning `false` works.

But here's where it gets interesting: `eachById` delegates to `chunkById`.

```php
public function eachById(callable $callback, $count = 1000, $column = null, $alias = null): bool
{
    return $this->chunkById($count, function ($results) use ($callback) {
        foreach ($results as $key => $value) {
            if ($callback($value, $key) === false) {
                return false;
            }
        }
    }, $column, $alias);
}
```

The inner closure returns `false` when your callback does — and that `false` propagates to `chunkById`, which then returns `false` itself. Correct.

So what's the lie?

## The lie is in older versions

In Laravel versions before the `chunkById` fix landed (around 8.x patches and into 9.x), the `chunkById` implementation did not check the return value of the callback at all. It just called it and moved on:

```php
// Pre-fix chunkById — the broken version
do {
    // ...
    $callback($results); // return value ignored
    // ...
} while ($countResults == $count);
```

If you were running a Laravel 8 application with a batch command that relied on `return false` inside `eachById`, your early-exit logic was silently doing nothing. The loop ran to completion every single time.

The `chunk` method has checked the return value correctly for much longer. `chunkById` caught up later. The documentation never made this distinction obvious.

## A test that catches both paths

Write this test before you ship any command that uses early exit:

```php
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;
use App\Models\User;

class ChunkEarlyExitTest extends TestCase
{
    use RefreshDatabase;

    public function test_chunk_stops_on_false(): void
    {
        User::factory()->count(30)->create();

        $processed = 0;

        User::query()->chunk(10, function ($users) use (&$processed) {
            $processed += $users->count();
            return false; // stop after first chunk
        });

        $this->assertSame(10, $processed);
    }

    public function test_each_by_id_stops_on_false(): void
    {
        User::factory()->count(30)->create();

        $processed = 0;

        User::query()->eachById(function (User $user) use (&$processed) {
            $processed++;
            return false; // stop after first record
        }, chunkSize: 10);

        $this->assertSame(1, $processed);
    }

    public function test_chunk_by_id_stops_on_false(): void
    {
        User::factory()->count(30)->create();

        $processed = 0;

        User::query()->chunkById(10, function ($users) use (&$processed) {
            $processed += $users->count();
            return false; // stop after first chunk
        });

        $this->assertSame(10, $processed);
    }
}
```

If any of these fail, you've found the version mismatch before it bites you in production.

## When not to rely on `return false`

Early exit via return value is fine for simple stop conditions — rate limit hit, record found, quota exhausted. But it has a design smell: the callback now has two responsibilities (processing records and controlling the loop), and the control signal is an implicit `false` rather than an explicit intent.

A few alternatives worth considering:

**Throw a dedicated exception.** This works across all versions and is impossible to ignore silently:

```php
class ProcessingQuotaExceeded extends RuntimeException {}

try {
    User::query()->eachById(function (User $user) use (&$quota) {
        if ($quota <= 0) {
            throw new ProcessingQuotaExceeded();
        }

        $this->processUser($user);
        $quota--;
    });
} catch (ProcessingQuotaExceeded) {
    // stopped cleanly
}
```

**Collect IDs first, then process a slice.** If you know in advance how many records you want, just query for them:

```php
$ids = User::query()
    ->where('status', 'pending')
    ->limit(500)
    ->pluck('id');

User::whereIn('id', $ids)->each(fn (User $user) => $this->processUser($user));
```

No early exit needed because you never loaded the records you didn't want.

**Use a generator.** `cursor()` returns a lazy collection, and you can `take()` from it:

```php
User::query()
    ->cursor()
    ->take(500)
    ->each(fn (User $user) => $this->processUser($user));
```

This keeps memory low and is naturally bounded without any return-value magic.

## The takeaway

`return false` in chunk callbacks is not a reliable cross-version contract in Laravel — it was broken in `chunkById` and by extension `eachById` for a meaningful window of time. If your Artisan commands or background jobs depend on early exit to avoid overprocessing, write the test first. And if you want a stop condition you can actually trust, throw an exception — it's explicit, it's unmissable, and it works on every version.
