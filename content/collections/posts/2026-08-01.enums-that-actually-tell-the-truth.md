You have a `PaymentMethod` enum. You also have five separate `match ($method)` blocks sprinkled across a payment service, a fee calculator, a receipt formatter, a webhook dispatcher, and an authorization policy. Every time you add a new payment method, someone forgets two of the five. The tests catch it — if you're lucky — a week later, in staging.

The fix isn't better documentation or a checklist. It's recognizing that the logic living in those `match` expressions belongs on the enum itself.

## The Smell: Parallel Static Maps

Here's the enum:

```php
enum PaymentMethod: string
{
    case Card = 'card';
    case BankTransfer = 'bank_transfer';
    case Wallet = 'wallet';
    case BuyNowPayLater = 'bnpl';
}
```

And here's what accumulates across your codebase:

```php
// In PaymentService.php
$handler = match ($method) {
    PaymentMethod::Card => new CardPaymentHandler(),
    PaymentMethod::BankTransfer => new BankTransferHandler(),
    PaymentMethod::Wallet => new WalletHandler(),
    PaymentMethod::BuyNowPayLater => new BnplHandler(),
};

// In FeeCalculator.php
$feeRate = match ($method) {
    PaymentMethod::Card => 0.029,
    PaymentMethod::BankTransfer => 0.005,
    PaymentMethod::Wallet => 0.015,
    PaymentMethod::BuyNowPayLater => 0.0,
};

// In AuthorizationPolicy.php
$requiresVerification = match ($method) {
    PaymentMethod::BankTransfer, PaymentMethod::BuyNowPayLater => true,
    default => false,
};
```

Each of these is a translation of the same enum to something else. When you add `PaymentMethod::Crypto`, you need to find and update all three — and the three others you forgot to grep for.

This is the parallel static map smell. Multiple places encode the same branching logic, and nothing enforces that they stay in sync.

## Step One: Move the Handler Onto the Enum

Define a contract first:

```php
interface PaymentHandlerContract
{
    public function capture(Payment $payment): PaymentResult;
    public function refund(Payment $payment, int $amountInCents): RefundResult;
}
```

Then add a `handler()` method to the enum:

```php
enum PaymentMethod: string
{
    case Card = 'card';
    case BankTransfer = 'bank_transfer';
    case Wallet = 'wallet';
    case BuyNowPayLater = 'bnpl';

    public function handler(): PaymentHandlerContract
    {
        return match ($this) {
            self::Card => new CardPaymentHandler(),
            self::BankTransfer => new BankTransferHandler(),
            self::Wallet => new WalletHandler(),
            self::BuyNowPayLater => new BnplHandler(),
        };
    }
}
```

Now the call site becomes:

```php
$result = $method->handler()->capture($payment);
```

One `match`, one place. Add `PaymentMethod::Crypto` and the enum itself tells you — via an unhandled match arm — that you need to provide a handler. No grep required.

## Interface Methods vs. Abstract Enum Methods

PHP 8.1 enums can implement interfaces. That opens a second design: instead of returning a handler object, make the enum itself implement the contract.

```php
enum PaymentMethod: string implements PaymentHandlerContract
{
    case Card = 'card';
    case BankTransfer = 'bank_transfer';

    public function capture(Payment $payment): PaymentResult
    {
        return match ($this) {
            self::Card => $this->captureCard($payment),
            self::BankTransfer => $this->captureBankTransfer($payment),
        };
    }

    // ...
}
```

This works but has a real downside: handler logic lives inside the enum, and enums cannot be instantiated with constructor arguments. You can't inject a `GatewayClient` or an `EventDispatcher` into an enum case. The moment your handler needs a dependency, you're stuck passing it as a method argument or pulling it from a container, neither of which is clean.

The `handler(): HandlerContract` approach sidesteps this entirely. The enum stays a pure value object. The handler classes get proper constructors and can be resolved through the service container:

```php
public function handler(): PaymentHandlerContract
{
    return match ($this) {
        self::Card => app(CardPaymentHandler::class),
        self::BankTransfer => app(BankTransferHandler::class),
        self::Wallet => app(WalletHandler::class),
        self::BuyNowPayLater => app(BnplHandler::class),
    };
}
```

If you're outside Laravel or want to avoid the facade, pass a container or factory — but the shape is the same. The enum tells you what handler to use. The container provides the handler with its dependencies.

## Predicate Methods: Collapse the Conditionals

The handler dispatch is the obvious case. But scattered `match` expressions also show up as multi-case boolean checks:

```php
// In OrderPolicy.php
if (in_array($method, [PaymentMethod::BankTransfer, PaymentMethod::BuyNowPayLater])) {
    // require identity verification
}

// In CheckoutController.php
if ($method === PaymentMethod::BankTransfer || $method === PaymentMethod::BuyNowPayLater) {
    // show verification step
}

// In NotificationService.php
$delayed = match ($method) {
    PaymentMethod::BankTransfer, PaymentMethod::BuyNowPayLater => true,
    default => false,
};
```

These are all expressing the same concept — "this method requires identity verification before we can proceed." But none of them say that. They list cases and leave the reader to infer the intent.

Add a predicate method:

```php
public function requiresIdentityVerification(): bool
{
    return match ($this) {
        self::BankTransfer, self::BuyNowPayLater => true,
        default => false,
    };
}
```

Now the call sites read like intent:

```php
if ($method->requiresIdentityVerification()) {
    // ...
}
```

When `PaymentMethod::Crypto` needs verification too, you update one place. More importantly, when a new developer reads the policy, they don't have to reverse-engineer what the case list means.

Other predicates that commonly emerge from this refactor:

```php
public function supportsInstantRefund(): bool
{
    return $this === self::Card || $this === self::Wallet;
}

public function chargesFee(): bool
{
    return $this !== self::BuyNowPayLater;
}

public function isDelayed(): bool
{
    return $this === self::BankTransfer;
}
```

Each one encodes a fact about the domain, expressed once, named for what it means rather than what it checks.

## The Migration Path

Don't rewrite everything at once. The enum is already there — you're just giving it knowledge it was always supposed to have.

**Step 1:** Add the method to the enum. Don't touch callers yet.

**Step 2:** Pick one call site — start with the most frequently modified one — and redirect it through the enum method.

**Step 3:** Run the tests. Commit.

**Step 4:** Repeat for remaining call sites, one at a time.

**Step 5:** Once all callers go through the enum, delete the old maps and standalone `match` expressions.

This works because the enum method and the scattered `match` blocks are behaviorally equivalent during the migration. You're not changing behavior, you're moving where it lives.

If you're using static analysis (Psalm, PHPStan), the exhaustiveness checking on `match` in the enum method is a bonus: adding a new case without updating the method is a type error, not a silent runtime bug.

## What You End Up With

Before:

```
PaymentService       → match ($method) → CardPaymentHandler
FeeCalculator        → match ($method) → 0.029
AuthorizationPolicy  → match ($method) → true/false
CheckoutController   → match ($method) → show step
NotificationService  → match ($method) → delayed flag
```

After:

```
PaymentMethod::Card
  → handler()                     → CardPaymentHandler
  → requiresIdentityVerification() → false
  → supportsInstantRefund()        → true
  → chargesFee()                   → true
  → isDelayed()                    → false
```

The enum is now the single source of truth for everything that varies by payment method. Adding a new case means filling in one enum definition. Forgetting to handle it is a compile-time error, not a production incident.

That's the whole point. An enum that knows nothing about its own domain is just a list of strings dressed up in type safety. An enum that carries its knowledge pays for itself every time someone adds a case.
