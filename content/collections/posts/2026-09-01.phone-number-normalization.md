A clean phone input is boring.

The user picks a country, enters a number, [`giggsey/libphonenumber-for-php`](https://github.com/giggsey/libphonenumber-for-php) parses it and I store the E.164 version.

The interesting part starts when the phone number didn't come from my nice phone input.

Legacy data. A CSV import. Another system. A vendor that validated numbers differently. Or a system that decided punctuation isn't important and stripped all of it.

That's the situation where phone number normalization gets fun.

## The easy numbers

My phone number is:

```text
+491621525105
```

That's easy. It already tells the parser everything it needs.

This one is also pretty straightforward when I already have German dialing context:

```text
00491621525105
```

And common formatting noise isn't the interesting problem either:

```text
+49 162 1525105
+49 (162) 1525105
+49-162-1525105
```

Libphonenumber is built for this.

But then an external system sends this:

```text
491621525105
```

Same number, but somebody stripped every special character. Including the `+`.

I've seen exactly that kind of data.

And this is where I don't want validation to immediately say "nope". There is a very obvious candidate: maybe this is already the full international number and only the marker is missing.

So before I start guessing a country from somewhere else, I try the number itself.

## First: can the number explain itself?

The helper I currently use tries the original input and a `+` prefixed version before falling back to external country information:

```php
public static function resolveRegionCode(string $phoneNumber): ?string
{
    return collect([
        $phoneNumber,
        Str::start($phoneNumber, '+'),
    ])
        ->unique(strict: true)
        ->values()
        ->map(fn (string $phone) => (new self())->resolve(
            phoneNumber: $phone,
            countryCode: null,
            callback: fn (
                PhoneNumberUtil $phoneNumberUtil,
                PhoneNumber $parsedPhoneNumber,
            ) => $phoneNumberUtil->getRegionCodeForNumber($parsedPhoneNumber),
        ))
        ->first(fn (?string $regionCode) => filled($regionCode));
}
```

For `+491621525105`, the first candidate already works.

For `491621525105`, the first one doesn't have enough context, but `+491621525105` does.

That's already enough to recover a surprisingly useful class of broken imports without inventing anything.

The `unique(strict: true)` is intentional, by the way. These are numeric-looking strings. I don't want PHP's loose comparison rules deciding that two different phone candidates are the same thing before I've even parsed them.

The actual parsing is still strict. I don't keep something just because libphonenumber managed to construct an object from it:

```php
private function tryParse(
    PhoneNumberUtil $phoneNumberUtil,
    string $phoneNumber,
    ?string $countryCode,
): ?PhoneNumber {
    try {
        $parsed = $phoneNumberUtil->parse(trim($phoneNumber), $countryCode);

        if ($phoneNumberUtil->isValidNumber($parsed)) {
            return $parsed;
        }
    } catch (Throwable $e) {
        // Do nothing
    }

    return null;
}
```

That's the important split for me: be generous with **candidates**, but strict with what counts as the final number.

## And then there is the number people actually type

The harder version of my number is this:

```text
01621525105
```

That's the version in my muscle memory.

It's also what browser autocomplete tends to fill for me.

And I would bet it's what a lot of people enter when a form doesn't force them through a country-aware phone input.

Now there is no country calling code hidden in the string that I can recover. `+0162...` obviously doesn't solve anything.

At this point I need context.

The current helper accepts a country for exactly that reason. If it can't resolve a region from the phone itself, it uses the supplied country as parsing context:

```php
private function getCountryCode(string $phoneNumber, ?string $country): string
{
    if ($phoneNumber) {
        if ($regionCode = self::resolveRegionCode($phoneNumber)) {
            return $regionCode;
        }
    }

    if ($country) {
        if ($countryCode = Country::getCountryCode(trim($country))) {
            return $countryCode;
        }
    }

    return 'US';
}
```

That final `US` fallback is project-specific legacy behavior. The interesting part is the order before it:

1. Let the phone identify itself if possible.
2. Otherwise use known country context.
3. Only then fall back to whatever product-specific default exists.

For clean application data, that country is often easy. The user has an address, a booking, a billing profile or another record that already gives me a sensible region.

For truly random external data, it gets more interesting.

## Country is evidence, not truth

For a private project I had to deal with phone numbers from basically anywhere and with much weaker guarantees.

There wasn't one `country` field I could trust.

Instead I could have several hints:

- address country;
- billing country;
- current IP country;
- browser language/locale;
- previous session countries;
- some external profile metadata.

None of these are truth.

An IP can be a VPN. A browser language can be English while the user lives in France. Someone can be traveling. Billing and residence aren't guaranteed to be the same thing either.

But together they are useful.

So the next layer is to collect as many signals as I have, rank the likely countries and try the local number against them:

```php
$signals = collect([
    ['country' => $addressCountry, 'priority' => 40],
    ['country' => $billingCountry, 'priority' => 30],
    ['country' => $ipCountry, 'priority' => 20],
    ['country' => $browserCountry, 'priority' => 10],
])
    ->concat(
        collect($historicalSessionCountries)
            ->map(fn (string $country) => [
                'country' => $country,
                'priority' => 0,
            ]),
    )
    ->filter(fn (array $signal) => filled($signal['country']));

$countries = $signals
    ->groupBy('country')
    ->map(fn ($signals, string $country) => [
        'country' => $country,
        'score' => ($signals->count() * 100)
            + $signals->max('priority'),
    ])
    ->sortByDesc('score')
    ->pluck('country');

foreach ($countries as $country) {
    $normalized = PhoneNumberHelper::tryFromString(
        phoneNumber: $number,
        country: $country,
    );

    if ($normalized !== null) {
        return $normalized;
    }
}

return null;
```

The exact scoring is business logic, not phone-number logic.

The point is that repeated signals beat single weak signals. If the address, billing country and browser all say Germany, Germany should probably be tried before the current IP says Spain.

Same with history. If 90% of previous sessions were from France and today's request comes from Spain, I wouldn't suddenly make Spain my first assumption for a local phone number.

Could the user have moved? Sure.

Could they be traveling? Also sure.

That's why I'm still only generating candidates and validating them afterwards.

And if address, billing, IP and language all point to different countries ... well, that's an interesting signal on its own, but that's another topic.

## A local number can be valid in more than one country

There is one annoying edge case left.

A local-looking number can theoretically parse as a valid number in multiple countries.

So this:

```php
foreach ($countries as $country) {
    if ($normalized = PhoneNumberHelper::tryFromString($number, $country)) {
        return $normalized;
    }
}
```

only makes sense if the countries are sorted by actual confidence.

That's why I care about the signal ordering.

For a low-risk import or migration, taking the first high-confidence valid candidate can be perfectly practical.

For authentication, account recovery, money movement or anything else where guessing wrong matters, I would keep all valid candidates and treat multiple different E.164 results as ambiguous instead of silently picking one.

Same parser. Different tolerance for guessing.

## Strict validation and graceful normalization are different jobs

The helper exposes both behaviors because I need both:

```php
public static function fromString(
    string $phoneNumber,
    ?string $country = null,
    int $format = PhoneNumberFormat::E164,
): string {
    return (new self())->format($phoneNumber, $country, $format);
}

public static function tryFromString(
    string $phoneNumber,
    ?string $country = null,
    int $format = PhoneNumberFormat::E164,
): ?string {
    return (new self())->tryFormat($phoneNumber, $country, $format);
}
```

`tryFromString()` gives me the strict version: either I can turn the input into a valid phone number or I get `null`.

That's what I want for validation, migrations and candidate testing.

The tolerant version exists for places where returning the best normalized representation is still better than exploding because some legacy record is ugly.

Those two behaviors shouldn't be mixed accidentally.

## This isn't an excuse for a bad phone input

None of this means I want users to type arbitrary crap into new forms.

For new data I still want a proper country-aware phone input, validation at the boundary and a normalized E.164 value stored afterwards.

This pipeline is for the messy parts around that happy path:

- migrating old data;
- consuming external systems;
- repairing values from integrations;
- accepting harmless formatting differences;
- being graceful when the number is clearly recoverable;
- trying sensible country context before finally giving up.

I don't want validation to fail only because a vendor removed one `+`.

But I also don't want "being helpful" to turn into inventing a phone number that wasn't there.

So I keep the guesses explicit, order them by confidence and let libphonenumber be the boring strict part at the end.

That's enough.
