A phone number was valid. It had the country calling code and the national number. The only missing character was the leading `+`.

Our application still rejected it.

The parser did exactly what we told it to do: treat every number without a `+` as a national number from our default region. The input was not valid in that region, so validation failed. The application then treated a formatting problem as if the phone number itself was wrong.

This sounds like a one-character bug. It is not.

It is a modeling bug caused by mixing four separate questions:

1. Is this input a possible phone number?
2. Which numbering plan should parse it?
3. What canonical value should we store or compare?
4. What should happen when the digits and the attached country metadata disagree?

This post is a rough guide to separating those questions with PHP, Laravel, and [`giggsey/libphonenumber-for-php`](https://github.com/giggsey/libphonenumber-for-php).

No hard-coded number in this post represents a person. Phone values use placeholders such as `+[CC][NSN]`, where `[CC]` is a country calling code and `[NSN]` is a national significant number.

---

## Three strings that look similar but mean different things

Before discussing code, we need precise terms.

### E.164

An E.164 number has this conceptual shape:

```text
+[CC][NSN]
```

The first `+` means "the following digits start with an international country calling code." It is not decoration. It changes how the parser interprets the digits.

E.164 is the right canonical storage and comparison format for most applications:

- it includes the country calling code;
- it has no spaces or local punctuation;
- it does not depend on the viewer's region;
- it is bounded to 15 digits after the `+`.

An extension is not part of E.164. Store it separately.

### National format

A national number has this conceptual shape:

```text
[NATIONAL_PREFIX][NATIONAL_NUMBER]
```

It makes sense only inside a numbering plan. The same leading digits can mean different things in different regions. A trunk prefix may be present for domestic dialing and removed in E.164.

This means a national number cannot be parsed neutrally. The parser needs a region:

```php
$phoneNumberUtil->parse($nationalNumber, $region);
```

Passing a region here is an assertion:

> Interpret these digits as a national number under this region's numbering plan.

It is not a harmless fallback.

### International digits without `+`

The problematic middle state looks like this:

```text
[CC][NSN]
```

The value contains the complete international digits, but not the marker that tells the parser they are international.

Humans often recognize it. A strict parser cannot safely assume it. Without the `+`, the same string could also be a national number from some region.

This is the central ambiguity:

- hypothesis A: the producer removed the `+` from an international number;
- hypothesis B: the producer sent a national number and expects region metadata to provide context.

Both can be plausible. In rare cases, both can produce valid but different phone numbers.

## A default region is an assertion, not a neutral fallback

Most phone libraries accept a default region because national numbers need one. That parameter is easy to misunderstand.

This code does not mean "use this region only if nothing else works":

```php
$parsed = $phoneNumberUtil->parse($input, config('phone.default_region'));
```

It means:

> If the input does not explicitly declare an international calling code, parse it as a national number from this region.

For input that already starts with `+`, libphonenumber can use the calling code and largely ignore the default region. For input without `+`, the region controls interpretation.

A hard-coded default can therefore create false confidence:

- a valid foreign number is rejected because it is invalid under the default numbering plan;
- a foreign number is accepted as a different domestic number;
- a national number is normalized into the wrong E.164 value;
- two representations of the same stored number no longer match during login;
- a backfill writes confident-looking but incorrect canonical data.

The dangerous part is not that parsing fails. Failure is visible. The dangerous part is that parsing can succeed under the wrong assumption.

I now think of every region source as evidence with a confidence level:

1. An explicit `+` calling code is strongest.
2. A complete international number with only the `+` missing can be strong, depending on data provenance.
3. A country attached to the same phone field or contact record is useful metadata.
4. A country inferred from a broader location string is weaker.
5. The application's home market is not evidence about this phone number.

A default region may be a useful product policy for a region-specific form. It is not a universal phone-normalization policy.

## What libphonenumber actually gives you

`giggsey/libphonenumber-for-php` is a PHP port of Google's libphonenumber. It provides the metadata and parsing rules that a home-grown regex cannot.

The core object is `PhoneNumberUtil`:

```php
use libphonenumber\PhoneNumberFormat;
use libphonenumber\PhoneNumberUtil;

$phoneNumberUtil = PhoneNumberUtil::getInstance();

$parsed = $phoneNumberUtil->parse($input, $defaultRegion);

$isPossible = $phoneNumberUtil->isPossibleNumber($parsed);
$isValid = $phoneNumberUtil->isValidNumber($parsed);
$e164 = $phoneNumberUtil->format($parsed, PhoneNumberFormat::E164);
$region = $phoneNumberUtil->getRegionCodeForNumber($parsed);
$callingCode = $parsed->getCountryCode();
```

These methods answer different questions:

- `isPossibleNumber()` checks broad length and structure constraints.
- `isValidNumber()` checks the number against current metadata for its numbering plan.
- `format(..., E164)` produces the canonical international representation.
- `getRegionCodeForNumber()` returns an ISO region where one can be resolved.
- `getCountryCode()` on the parsed object returns the numeric calling code, not an ISO region.

That last distinction is worth repeating. "Country code" is overloaded:

- calling code: the numeric prefix after `+`;
- region code: an ISO alpha-2 code used by libphonenumber as parsing context.

Name your methods accordingly. `resolveRegionCode()` is clearer than `getCountryCode()` when the method returns an ISO region.

### Parsing with no region

When an input starts with `+`, this is the clean path:

```php
$parsed = $phoneNumberUtil->parse($e164Input, null);
```

The number declares its own international context.

For a national number, `null` is not enough:

```php
$parsed = $phoneNumberUtil->parse($nationalInput, null);
```

This normally throws `NumberParseException` because the parser has no region with which to interpret the number.

For international digits without `+`, we can test a specific recovery hypothesis:

```php
$candidate = '+' . $internationalDigits;
$parsed = $phoneNumberUtil->parse($candidate, null);
```

If that candidate is valid, we have shown that the digits can represent a valid international number when the missing marker is restored. We have not proved that this was the producer's intent.

### Region resolution is not universal

Do not assume every valid calling code maps neatly to one country.

- Some calling codes are shared by multiple regions.
- Some prefixes are non-geographic.
- The library may return a special non-geographic region marker.
- Metadata evolves as numbering plans change.

The canonical E.164 value is usually a better identity for matching than a region label.

## Decide the precedence before writing the helper

The helper cannot remove ambiguity. It can only encode a policy.

Our data source commonly supplied complete international digits and sometimes removed punctuation, including the leading `+`. Attached country metadata could be missing, broad, or stale. For that source, the practical precedence became:

1. Parse an explicit international number as international.
2. For a value without `+`, try it as complete international digits by adding `+`.
3. If that is not valid, parse the original value as a national number using normalized metadata.
4. If neither interpretation is valid, return no canonical number.
5. Keep any legacy default-region behavior outside the strict normalization path.

In plain language:

> Trust a valid phone-inferred region first. Use metadata to recover national input when the phone cannot identify itself.

That is not the right policy for every form.

If your product has a domestic-only signup form with a required country selector, metadata-first can be more appropriate. If your import feed promises E.164 but sometimes strips punctuation, phone-first is more appropriate.

The important part is that the order is explicit, centralized, and tested.

### The ambiguous case

Suppose both of these are valid:

- `+[DIGITS]` as an international number;
- `[DIGITS]` as a national number under the metadata region.

If they normalize to different E.164 values, the input is ambiguous.

You have three reasonable policies:

1. **Source-contract policy:** pick the interpretation promised by this data source.
2. **Reject policy:** return an ambiguous result and ask for explicit country context.
3. **Record-both policy:** preserve both candidates for review or a staged backfill.

For authentication and irreversible data cleanup, rejecting or recording ambiguity is safer than silently selecting a default. For a tolerant display-only formatter, a source-contract policy may be acceptable.

Do not pretend the library "detected the country" from nowhere. It validated a hypothesis that your code supplied.

## A centralized PHP helper

The following code is deliberately generic. It separates the result from the parsing mechanism so callers can see how a value was resolved.

```php
<?php

namespace App\Support\PhoneNumbers;

enum PhoneResolutionSource: string
{
    case ExplicitInternational = 'explicit_international';
    case RecoveredInternational = 'recovered_international';
    case MetadataNational = 'metadata_national';
}
```

```php
<?php

namespace App\Support\PhoneNumbers;

final readonly class NormalizedPhoneNumber
{
    public function __construct(
        public string $e164,
        public ?string $region,
        public PhoneResolutionSource $source,
    ) {}
}
```

The resolver applies the precedence in one place:

```php
<?php

namespace App\Support\PhoneNumbers;

use libphonenumber\NumberParseException;
use libphonenumber\PhoneNumberFormat;
use libphonenumber\PhoneNumberUtil;

final class PhoneNumberNormalizer
{
    public function __construct(
        private readonly PhoneNumberUtil $phoneNumberUtil,
    ) {}

    public function normalize(
        string $input,
        ?string $metadataRegion = null,
    ): ?NormalizedPhoneNumber {
        $input = trim($input);

        if ($input === '') {
            return null;
        }

        if (str_starts_with($input, '+')) {
            return $this->tryCandidate(
                input: $input,
                region: null,
                source: PhoneResolutionSource::ExplicitInternational,
            );
        }

        $recoveredInternational = $this->tryCandidate(
            input: '+' . $input,
            region: null,
            source: PhoneResolutionSource::RecoveredInternational,
        );

        if ($recoveredInternational !== null) {
            return $recoveredInternational;
        }

        if ($metadataRegion === null || trim($metadataRegion) === '') {
            return null;
        }

        return $this->tryCandidate(
            input: $input,
            region: strtoupper(trim($metadataRegion)),
            source: PhoneResolutionSource::MetadataNational,
        );
    }

    private function tryCandidate(
        string $input,
        ?string $region,
        PhoneResolutionSource $source,
    ): ?NormalizedPhoneNumber {
        try {
            $parsed = $this->phoneNumberUtil->parse($input, $region);

            if (! $this->phoneNumberUtil->isValidNumber($parsed)) {
                return null;
            }

            return new NormalizedPhoneNumber(
                e164: $this->phoneNumberUtil->format(
                    $parsed,
                    PhoneNumberFormat::E164,
                ),
                region: $this->phoneNumberUtil->getRegionCodeForNumber($parsed),
                source: $source,
            );
        } catch (NumberParseException) {
            return null;
        }
    }
}
```

Bind the library singleton once:

```php
use App\Support\PhoneNumbers\PhoneNumberNormalizer;
use libphonenumber\PhoneNumberUtil;

$this->app->singleton(
    PhoneNumberNormalizer::class,
    fn (): PhoneNumberNormalizer => new PhoneNumberNormalizer(
        PhoneNumberUtil::getInstance(),
    ),
);
```

Now controllers, form requests, jobs, models, and importers ask one service the same question. None of them invents its own region precedence.

### Do not make the tolerant fallback invisible

Many mature applications already have a method that "always returns something." It catches parsing errors and returns the original string or prepends a guessed prefix.

Keep that behavior if callers depend on it, but name it honestly:

```php
public function formatOrOriginal(
    string $input,
    ?string $metadataRegion = null,
): string {
    return $this->normalize($input, $metadataRegion)?->e164 ?? $input;
}
```

Do not use `formatOrOriginal()` for validation or authentication. Its return type cannot tell you whether normalization succeeded.

A nullable strict method and a tolerant display method serve different jobs.

## If you need ambiguity detection, return candidates

The previous helper implements phone-first precedence. A stricter system can evaluate both hypotheses before selecting one.

```php
final readonly class PhoneNormalizationCandidates
{
    public function __construct(
        public ?NormalizedPhoneNumber $international,
        public ?NormalizedPhoneNumber $national,
    ) {}

    public function isAmbiguous(): bool
    {
        return $this->international !== null
            && $this->national !== null
            && $this->international->e164 !== $this->national->e164;
    }
}
```

The calling code can then choose a policy:

```php
$candidates = $normalizer->candidates(
    input: $input,
    metadataRegion: $metadataRegion,
);

if ($candidates->isAmbiguous()) {
    return PhoneNormalizationResult::ambiguous($candidates);
}

return PhoneNormalizationResult::resolved(
    $candidates->international ?? $candidates->national,
);
```

This is more code, but it makes an important fact visible: valid does not always mean unambiguous.

For bulk repair, I would use the candidate-returning version. For a well-understood import source with a stable contract, the simpler precedence resolver can be enough.

## Phone-inferred region versus contact metadata

A contact record may contain several location-like values:

- an explicit phone region selected by the user;
- a country field from an external profile;
- a free-text location;
- a property or reservation location;
- an application default.

These values do not have equal meaning.

An explicit phone-region selector belongs to the phone input. A profile country may describe residence. A reservation country may describe the destination. A free-text location may be a city, state, country, or all three. The application default describes your business, not the contact.

The common mistake is to collapse all of them into one method named `normalizedCountry()` and then pass that result into every phone parser.

Instead, keep provenance:

```php
final readonly class PhoneRegionHint
{
    public function __construct(
        public string $region,
        public PhoneRegionHintSource $source,
    ) {}
}
```

Then a phone parser can accept or reject weak sources based on the operation.

For example:

- signup form: accept the user's explicit selector;
- imported contact: prefer valid international digits, then source metadata;
- login matching: normalize the stored phone first, then use its region to interpret a national credential;
- backfill: reject free-text-location-only ambiguity;
- display: use the stored canonical number and the viewer's locale only for formatting.

### Free-text location is a last resort

Taking the last comma-separated segment of a location can be useful:

```php
$candidate = trim(Arr::last(explode(',', $location)));
```

It can also be wrong. A final segment may be a state, province, territory, or informal label that shares a name with a country. A country lookup returning a match does not prove that the segment meant the country.

If free-text location is your only hint:

- keep it lower priority than a valid phone-inferred region;
- return `null` when the value is not confidently recognized;
- do not overwrite an explicit phone region;
- test known ambiguous geographic names from your own supported data;
- log the source used during backfills.

The safest fallback is often no fallback.

## The Laravel `unique()` bug hiding in the retry list

The most surprising bug in this work had nothing to do with telephony.

Consider a resolver that tries two strings:

```php
$candidates = collect([
    $digits,
    Str::start($digits, '+'),
])->unique();
```

It looks correct. If the input lacks `+`, the collection should contain both variants.

But Laravel's `Collection::unique()` uses loose comparison by default. PHP treats numeric-looking strings as numbers during loose comparison. This small, non-phone example demonstrates the problem:

```php
collect(['123', '+123'])->unique()->all();

// ['123']
```

The second candidate disappears before parsing. The code claims to try the missing-`+` recovery path but never does.

Use strict uniqueness:

```php
$candidates = collect([
    $digits,
    Str::start($digits, '+'),
])
    ->unique(strict: true)
    ->values();
```

Now both strings remain:

```php
['123', '+123']
```

This is a general PHP lesson: identifiers that contain only digits are still identifiers. Phone numbers, postal codes, account references, and external IDs should remain strings. When deduplicating them, use strict comparison.

There was a second easy failure in the same pattern: creating `$phone` inside `map()` but accidentally passing the outer `$phoneNumber` variable into the parser. Every iteration then tested the original input. A dataset covering "international digits without plus" catches both mistakes.

## Validation, formatting, and matching are three APIs

One helper often grows methods named `fromString()`, `tryFromString()`, `isValid()`, `format()`, and `matches()`. Unless their contracts are precise, callers use the wrong one.

### Validation

Validation decides whether an input is acceptable for a specific operation.

Questions include:

- Is a national number allowed without an explicit region?
- Is an inferred missing `+` acceptable?
- Is a possible number enough, or must it be valid?
- Are short codes allowed?
- Are non-geographic numbers allowed?
- Is ambiguity allowed?

A form rule should express that policy:

```php
final class ValidPhoneNumber implements ValidationRule
{
    public function __construct(
        private readonly PhoneNumberNormalizer $normalizer,
        private readonly ?string $region = null,
    ) {}

    public function validate(
        string $attribute,
        mixed $value,
        Closure $fail,
    ): void {
        if (! is_string($value)) {
            $fail('The phone number must be text.');

            return;
        }

        if ($this->normalizer->normalize($value, $this->region) === null) {
            $fail('Enter a complete phone number with its country calling code.');
        }
    }
}
```

Validation must not mutate persistent data as a side effect.

### Formatting

Formatting converts a parsed number to a representation:

- E.164 for storage and exact comparison;
- international display for a human audience;
- national display only when the viewing region is known;
- RFC3966 for a `tel:` URI when appropriate.

Formatting starts after successful parsing. It is not evidence that the raw input was unambiguous.

### Matching

Matching decides whether two inputs identify the same number under your policy.

For authentication, I prefer to normalize both sides and compare canonical E.164 strings:

```php
public function matches(
    string $credential,
    string $storedPhone,
    ?string $storedRegion = null,
): bool {
    $stored = $this->normalizer->normalize(
        input: $storedPhone,
        metadataRegion: $storedRegion,
    );

    if ($stored === null) {
        return false;
    }

    $credentialNumber = $this->normalizer->normalize($credential)
        ?? $this->normalizer->normalize(
            input: $credential,
            metadataRegion: $stored->region,
        );

    return $credentialNumber?->e164 === $stored->e164;
}
```

This order matters:

1. Normalize the stored number.
2. Try to interpret the credential without a region assertion.
3. If needed, use the region resolved from the stored phone as a fallback for a national credential.
4. Compare canonical E.164 values.

The stored phone's resolved region is better phone context than a broad profile-country field.

Libphonenumber also has number-matching APIs that can report exact, national-significant-number, short-number, or no match. They are useful, but decide which match levels your security boundary accepts. An authentication check should not silently accept a weak suffix or short-number match.

## Credential type detection needs the same order

A combined login field may accept a name, email address, or phone number. Classification can fail before matching ever runs.

A common flow is:

1. email validation;
2. phone validation with profile country;
3. otherwise treat as name.

If the profile country is wrong, a complete international phone without `+` becomes a name. The later phone-matching code never gets a chance.

Use the same precedence:

```php
public function getCredentialType(
    string $credential,
    ?Contact $contact,
): CredentialType {
    if (filter_var($credential, FILTER_VALIDATE_EMAIL)) {
        return CredentialType::Email;
    }

    if ($this->normalizer->normalize($credential) !== null) {
        return CredentialType::Phone;
    }

    $storedPhone = $contact?->phone;

    if ($storedPhone !== null) {
        $normalizedStoredPhone = $this->normalizer->normalize(
            input: $storedPhone,
            metadataRegion: $contact->phoneRegion,
        );

        if (
            $normalizedStoredPhone !== null
            && $this->normalizer->normalize(
                input: $credential,
                metadataRegion: $normalizedStoredPhone->region,
            ) !== null
        ) {
            return CredentialType::Phone;
        }
    }

    return CredentialType::Name;
}
```

Phone auto-detection is the first phone step. Contact-specific region context is the second-step fallback for national credentials.

Also guard every nullable relationship. A record may have a phone stored directly while the related contact row is absent. The normalization fix should not replace a validation failure with a null-property exception.

## Multiple stored phone sources make precedence visible again

Real systems often have more than one phone field:

- contact phone;
- reservation or order phone;
- a completed identity form;
- an imported communication profile;
- an older denormalized column.

Do not hide this in a long null-coalescing expression. Build a candidate list and apply one matcher:

```php
$storedPhones = collect([
    $contact === null
        ? null
        : $phoneFormatter->fromContact($contact),
    $reservation->phone,
    $completedDetails?->phone,
])
    ->filter(fn (mixed $phone): bool => is_string($phone) && filled($phone))
    ->unique(strict: true)
    ->values();

$matches = $storedPhones->contains(
    fn (string $storedPhone): bool => $phoneMatcher->matches(
        credential: $credential,
        storedPhone: $storedPhone,
    ),
);
```

This gives each source a clear place, avoids null errors, and makes it easy to add source-specific observability.

Do not put a unique database constraint on phone numbers without a domain reason. Phone numbers can be shared, recycled, proxied, or reused across records. Canonicalization makes equality possible; it does not make phone ownership unique.

## Storage posture: canonicalize at the boundary, preserve evidence

The ideal write path is simple:

1. receive raw input;
2. receive explicit region context when the UI has it;
3. normalize;
4. store E.164;
5. store extension separately;
6. optionally preserve the raw value and resolution source for audit.

A useful schema during migration can look like:

```php
Schema::table('contacts', function (Blueprint $table): void {
    $table->string('phone_raw')->nullable();
    $table->string('phone_e164', 16)->nullable()->index();
    $table->char('phone_region', 2)->nullable();
    $table->string('phone_resolution_source')->nullable();
    $table->timestamp('phone_normalized_at')->nullable();
});
```

The E.164 column needs space for `+` plus up to 15 digits. The raw column is evidence, not an alternate comparison field.

For new writes, reject or quarantine ambiguity instead of adding another malformed value.

### Do not start with a destructive backfill

A safer rollout:

1. Add nullable canonical and provenance columns.
2. Normalize new writes.
3. Read canonical first, with legacy normalization as fallback.
4. Run a dry backfill that records counts by resolution source.
5. Separate resolved, invalid, and ambiguous rows.
6. Review samples without exposing raw phone values in logs.
7. Backfill only high-confidence rows.
8. Keep ambiguous rows for a later policy decision.
9. Remove read fallback only after coverage is measured.

An idempotent Laravel operation might use:

```php
Contact::query()
    ->whereNull('phone_normalized_at')
    ->whereNotNull('phone_raw')
    ->eachById(function (Contact $contact) use ($normalizer): void {
        $result = $normalizer->normalize(
            input: $contact->phone_raw,
            metadataRegion: $contact->phone_region,
        );

        if ($result === null) {
            NormalizationMetrics::unresolved();

            return;
        }

        $contact->forceFill([
            'phone_e164' => $result->e164,
            'phone_region' => $result->region,
            'phone_resolution_source' => $result->source->value,
            'phone_normalized_at' => now(),
        ])->save();
    });
```

For a production backfill, add dry-run mode, checkpoints, rate control, collision reporting, and a dedicated operation record. Do not log raw phone numbers. Log counts and opaque record references only where access controls permit.

### Library metadata is a dependency

Phone validity changes as numbering plans change. Pin the package version, update it intentionally, and expect some results to move after metadata updates.

If a canonical value was already confirmed and stored, do not automatically re-interpret it on every package update. Revalidation and reformatting are separate maintenance operations.

## UI copy should match the parser contract

If the UI says "Phone number" but the backend requires E.164, the contract is incomplete.

Better helper copy:

> Include the country calling code. A leading `+` is recommended.

For a combined identity field:

> Enter the name, email address, or phone number used for this record. For a phone number, include the country calling code.

The placeholder can remain generic:

```text
+[CC][NSN]
```

Do not use a real customer's number as an example. If the design requires a realistic example, use only a number explicitly reserved by an official numbering authority for documentation and label it as a documentation example.

An authentication error must also describe the state without leaking whether an account exists:

> We could not match that entry to this record. No login session was created. Check the name, email address, or complete phone number, including its country calling code.

That says what failed, confirms the current state, and gives a concrete next step. It does not reveal which stored identity field matched or failed.

## Build a test matrix, not three happy paths

Phone normalization is ideal for dataset tests. The behavior is a matrix of representation, region evidence, and intended operation.

At minimum, cover these input classes:

| Input shape                 | Metadata region | Expected result                             |
| --------------------------- | --------------- | ------------------------------------------- |
| `+[CC][NSN]`                | none            | valid E.164                                 |
| `+[CC][NSN]`                | matching        | explicit phone wins                         |
| `+[CC][NSN]`                | conflicting     | explicit phone wins                         |
| `[CC][NSN]`                 | none            | recover only if valid as international      |
| `[CC][NSN]`                 | matching        | phone-first result                          |
| `[CC][NSN]`                 | conflicting     | phone-first result under this policy        |
| `[NATIONAL_NUMBER]`         | matching        | metadata national fallback                  |
| `[NATIONAL_NUMBER]`         | none            | unresolved                                  |
| malformed text              | any             | unresolved                                  |
| blank input                 | any             | unresolved                                  |
| ambiguous digits            | conflicting     | reject or record ambiguity                  |
| valid non-geographic number | any             | canonical value with explicit region policy |

Then test each operation:

- strict normalization;
- display formatting;
- stored-phone matching;
- credential classification;
- model helper behavior;
- controller login behavior;
- backfill classification.

### Generate library-owned example numbers

Do not copy production phone values into tests. Libphonenumber can provide example numbers for supported regions:

```php
use libphonenumber\PhoneNumberFormat;
use libphonenumber\PhoneNumberType;
use libphonenumber\PhoneNumberUtil;

function exampleE164(string $region): string
{
    $phoneNumberUtil = PhoneNumberUtil::getInstance();
    $example = $phoneNumberUtil->getExampleNumberForType(
        $region,
        PhoneNumberType::MOBILE,
    );

    if ($example === null) {
        throw new RuntimeException("No library example for region {$region}.");
    }

    return $phoneNumberUtil->format($example, PhoneNumberFormat::E164);
}
```

Build the missing-`+` case from that example:

```php
$e164 = exampleE164($region);
$internationalDigits = ltrim($e164, '+');

Assert::assertSame(
    $e164,
    $normalizer->normalize($internationalDigits)?->e164,
);
```

This uses library-provided example data, not user data.

Be aware that example numbers can change when metadata changes. Pinning the package makes the tests deterministic. If the exact number is not the point, assert relationships instead of hard-coded digits:

```php
$result = $normalizer->normalize($internationalDigits);

Assert::assertNotNull($result);
Assert::assertSame($e164, $result->e164);
Assert::assertSame(
    PhoneResolutionSource::RecoveredInternational,
    $result->source,
);
```

### Test the strict uniqueness regression directly

The telephony test proves behavior, but a tiny unit test documents the PHP trap:

```php
public function test_candidate_variants_use_strict_uniqueness(): void
{
    $candidates = collect(['123', '+123'])
        ->unique(strict: true)
        ->values();

    Assert::assertSame(['123', '+123'], $candidates->all());
}
```

Both values are intentionally too short to represent valid phone examples. The test is about string identity.

### Prove the tests fail

After the tests pass, temporarily break one behavior at a time:

- change `unique(strict: true)` back to `unique()`;
- pass the original input in every retry iteration;
- move metadata before phone inference;
- remove the national-format fallback;
- call the contact formatter without a null guard.

The focused tests should fail for the expected reason. Restore the implementation and run them again.

This is especially valuable for precedence tests. A green test that passes under both policy orders does not protect the policy.

## Observability without leaking phone numbers

Normalization failures are operationally useful. Raw phone numbers are sensitive.

Record safe dimensions:

- resolution source;
- valid, invalid, or ambiguous;
- input had leading `+`;
- metadata region was present;
- inferred and metadata regions agreed;
- data source or integration type;
- helper version or library metadata version.

Avoid:

- raw input;
- canonical E.164 output;
- free-text profile fields;
- request payloads containing phone numbers;
- full exception context when it serializes method arguments.

A structured event can look like:

```php
logger()->info('phone_normalization_completed', [
    'outcome' => $outcome->value,
    'source' => $result?->source->value,
    'had_plus' => str_starts_with(trim($input), '+'),
    'metadata_region_present' => filled($metadataRegion),
    'regions_agree' => $regionsAgree,
]);
```

If you need to correlate repeated failures, use an access-controlled opaque record identifier. Do not hash raw phone numbers and assume that makes them anonymous; phone spaces are enumerable, and unsalted hashes can be reversed by lookup.

## Operational lessons from a one-character symptom

### 1. Parsing defaults are business rules

A default region changes meaning. Put it in a named policy, not a utility method's hidden fallback.

### 2. Canonical strings are outputs, not inputs

E.164 is an excellent storage format. Raw input is not E.164 just because it contains the right digits.

### 3. Validity does not prove intent

Adding `+` and getting a valid result validates one hypothesis. It does not prove the producer intended that interpretation.

### 4. Metadata has provenance

A phone's explicit region, a profile country, a location string, and an application default are not interchangeable.

### 5. Centralization prevents policy drift

Credential classification, controller matching, model accessors, jobs, and integrations must not each invent their own precedence.

### 6. Strict comparison matters for numeric-looking identifiers

PHP's loose comparison can erase the exact candidate that a recovery algorithm needs.

### 7. Read paths must handle partial relationships

A phone may exist even when a related model does not. A normalization improvement is incomplete if it introduces null errors.

### 8. Backfills need confidence classes

"Resolved" is not one bucket. Explicit international, recovered international, metadata national, ambiguous, and invalid should be measurable separately.

### 9. UI copy is part of validation

If users must include a country calling code, say so before validation fails.

### 10. A phone number is not a user identifier

Numbers can be shared, reassigned, or proxied. Normalization helps compare phone numbers; it does not establish ownership.

---

## The final rule

The bug started because every number without `+` was treated as if it belonged to one default region.

The fix was not "always prepend `+`." That would replace one guess with another.

The fix was to define and centralize an evidence order:

1. trust explicit international context;
2. test the missing-`+` international hypothesis when the source makes it plausible;
3. use phone-specific metadata to recover national input;
4. surface ambiguity;
5. return no canonical value when evidence is insufficient;
6. keep legacy defaults out of strict validation and matching.

The leading `+` is only one character. The assumption behind it is the whole system.
