Most Laravel package CI pipelines start simple and decay. Someone adds a PHP version, then a Laravel version, then a coverage step, then a cache that breaks every Tuesday when Packagist shifts. After a year the pipeline runs for 14 minutes and nobody knows which jobs can be safely deleted.

Here's a baseline that's correct from the start — matrix testing, PHPStan as a separate job, real caching, and coverage that's actually useful.

---

## The `composer.json` Scripts First

Before the CI file, make sure your `composer.json` has scripts that can be called without arguments. CI should invoke scripts, not inline commands. That way you can run the same thing locally.

```json
{
    "scripts": {
        "test": "vendor/bin/pest --colors=always",
        "test:coverage": "vendor/bin/pest --colors=always --coverage --min=80",
        "analyse": "vendor/bin/phpstan analyse --no-progress",
        "lint": "vendor/bin/pint --test"
    }
}
```

`test` runs without coverage. `test:coverage` adds the threshold. PHPStan is `analyse`, not `phpstan`, because you might swap tools or add arguments later without touching CI.

## The Full Pipeline

Here's the complete `.gitlab-ci.yml`. Walk through it section by section below.

```yaml
image: php:8.3-cli

stages:
    - lint
    - analyse
    - test

variables:
    COMPOSER_CACHE_DIR: '$CI_PROJECT_DIR/.composer-cache'

cache:
    key:
        files:
            - composer.lock
        prefix: '$CI_JOB_NAME'
    paths:
        - .composer-cache/
        - vendor/

.php-base: &php-base
    before_script:
        - apt-get update -qq && apt-get install -y -qq git unzip
        - curl -sS https://getcomposer.org/installer | php -- --install-dir=/usr/local/bin --filename=composer
        - composer install --prefer-dist --no-progress --no-interaction

lint:pint:
    stage: lint
    <<: *php-base
    script:
        - composer lint
    rules:
        - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
        - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

analyse:phpstan:
    stage: analyse
    <<: *php-base
    script:
        - composer analyse
    rules:
        - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
        - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

.test-base: &test-base
    stage: test
    script:
        - apt-get update -qq && apt-get install -y -qq git unzip
        - curl -sS https://getcomposer.org/installer | php -- --install-dir=/usr/local/bin --filename=composer
        - composer require "laravel/framework:$LARAVEL_VERSION" --no-update --no-interaction
        - composer update --prefer-dist --no-progress --no-interaction
        - composer test

test:matrix:
    <<: *test-base
    image: php:$PHP_VERSION-cli
    parallel:
        matrix:
            - PHP_VERSION: ['8.2', '8.3', '8.4']
              LARAVEL_VERSION: ['^11.0', '^12.0']
    cache:
        key:
            files:
                - composer.lock
            prefix: 'test-php$PHP_VERSION-laravel$LARAVEL_VERSION'
        paths:
            - .composer-cache/
    rules:
        - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
        - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

test:coverage:
    stage: test
    image: php:8.3-cli
    before_script:
        - apt-get update -qq && apt-get install -y -qq git unzip
        - curl -sS https://getcomposer.org/installer | php -- --install-dir=/usr/local/bin --filename=composer
        - pecl install pcov && docker-php-ext-enable pcov
        - composer install --prefer-dist --no-progress --no-interaction
    script:
        - composer test:coverage
    coverage: '/^\s*Lines:\s+(\d+(?:\.\d+)?%)/'
    artifacts:
        reports:
            coverage_report:
                coverage_format: cobertura
                path: build/coverage/cobertura.xml
    rules:
        - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

## Stage Order and Why It Matters

Three stages: `lint`, `analyse`, `test`. This order is deliberate.

Lint runs first because a style violation is the fastest failure. If Pint flags a file, you don't want to wait for six matrix jobs to tell you the same thing. Fail cheap before you fail expensive.

PHPStan runs before tests for the same reason. A type error caught at the static analysis stage doesn't need a test run to confirm it. Static analysis is also faster than any real test suite because it doesn't boot the framework.

Tests run last and in parallel. By the time they start, lint and static analysis have already confirmed the code is structurally correct.

## The Matrix

```yaml
parallel:
    matrix:
        - PHP_VERSION: ['8.2', '8.3', '8.4']
          LARAVEL_VERSION: ['^11.0', '^12.0']
```

This produces six jobs. GitLab's `parallel: matrix` creates one job per combination and names them automatically: `test:matrix [8.2, ^11.0]`, `test:matrix [8.3, ^11.0]`, and so on.

Each job pins its own Laravel version at install time:

```yaml
- composer require "laravel/framework:$LARAVEL_VERSION" --no-update --no-interaction
- composer update --prefer-dist --no-progress --no-interaction
```

The `--no-update` flag adds the constraint to `composer.json` without resolving it. The subsequent `update` resolves the full dependency tree under that constraint. This is the correct pattern — you're not hacking `composer.json`, you're using Composer as it was designed.

Drop older PHP and Laravel versions when they go EOL. Don't add new versions until they're stable enough that your package actually works on them.

## Cache Keys That Don't Betray You

The default GitLab cache is keyed on branch name. That means every branch gets its own cold cache. Useful for branch isolation, useless for packages where the dependencies barely change between branches.

Key on `composer.lock` instead:

```yaml
cache:
    key:
        files:
            - composer.lock
        prefix: '$CI_JOB_NAME'
    paths:
        - .composer-cache/
```

The `files` key generates a hash of `composer.lock`. When your lockfile changes — because you bumped a dependency — the cache invalidates. When the lockfile stays the same, every job that runs against the same lockfile reuses the cache, regardless of branch.

The `prefix` keeps the lint job's cache separate from the test job's cache. Same lockfile, different environments, different cache entries.

For the matrix jobs, prefix on the specific PHP and Laravel version combination:

```yaml
cache:
    key:
        files:
            - composer.lock
        prefix: 'test-php$PHP_VERSION-laravel$LARAVEL_VERSION'
```

A PHP 8.2 + Laravel 11 install is a different set of binaries than PHP 8.4 + Laravel 12. They should not share a cache.

## PHPStan as a Separate Job

PHPStan does not belong in the test matrix. It has its own concerns: does the code typecheck? That question doesn't depend on the PHP runtime version the way test execution does — at least not for the range of PHP versions a modern Laravel package targets.

Run it once, on your primary PHP version, against your `phpstan.neon`:

```yaml
analyse:phpstan:
    stage: analyse
    <<: *php-base
    script:
        - composer analyse
```

Your `phpstan.neon` should have no baseline file. If it currently does, that's a separate cleanup task. The baseline is a deferral, not a solution. The CI job should pass without one.

The config:

```neon
includes:
    - vendor/larastan/larastan/extension.neon

parameters:
    level: 6
    paths:
        - src
        - tests
    treatPhpDocTypesAsCertain: false
```

Level 6 is the minimum that catches real bugs. Higher is better. No baseline. If you can't reach your target level without a baseline, lower the level until you can, then raise it incrementally as you fix the underlying issues.

## Coverage: One Job, Not Six

Running coverage across the full matrix is expensive and the numbers won't differ meaningfully between PHP versions. Run it once, on your primary PHP version, on the default branch only.

```yaml
test:coverage:
    rules:
        - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

Use PCOV instead of Xdebug for coverage. PCOV is a single-purpose extension that's faster and doesn't interfere with debugging tooling. Install it in the `before_script` for the coverage job only — you don't want the overhead in the matrix jobs.

```yaml
before_script:
    - pecl install pcov && docker-php-ext-enable pcov
```

The `coverage:` key extracts the coverage percentage for GitLab's pipeline badge:

```yaml
coverage: '/^\s*Lines:\s+(\d+(?:\.\d+)?%)/'
```

The regex format depends on your test runner's output. The one above works with Pest's default output. Check your actual output if it doesn't match.

The artifact ships a Cobertura report for GitLab's built-in diff coverage annotation in MR views:

```yaml
artifacts:
    reports:
        coverage_report:
            coverage_format: cobertura
            path: build/coverage/cobertura.xml
```

Add the Pest configuration to produce it:

```php
// pest.config.php / Pest.php
uses()->coverage()->in('src');
```

And the CLI flag:

```json
{
    "scripts": {
        "test:coverage": "vendor/bin/pest --colors=always --coverage --coverage-cobertura=build/coverage/cobertura.xml --min=80"
    }
}
```

Do not commit coverage reports. Add `build/` to `.gitignore`. The reports live in GitLab artifacts, not in the repository.

## Fail-Fast vs Run-All

By default, GitLab's `parallel: matrix` runs all jobs and reports all failures. For a package matrix, this is the right behaviour. You want to know that your code fails on PHP 8.2 + Laravel 11 _and_ PHP 8.3 + Laravel 12, not just the first one that fails.

If you're running a large matrix — four PHP versions, three Laravel versions, twelve jobs — and PRs are taking too long, you can add a fail-fast job that runs on your primary version first:

```yaml
test:smoke:
    stage: test
    image: php:8.3-cli
    <<: *test-base
    variables:
        PHP_VERSION: '8.3'
        LARAVEL_VERSION: '^12.0'
    rules:
        - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

Run the smoke job before `test:matrix` in a separate sub-stage. If it fails, you get the failure in under two minutes instead of waiting for the full matrix. If it passes, the full matrix runs in parallel and you have the complete picture.

For most packages, the smoke job is overkill. Six matrix jobs in parallel finish in the same time as one.

## Rules: What Runs Where

Every job has explicit `rules`. The defaults:

- Lint and PHPStan: run on MR events and the default branch.
- Matrix tests: run on MR events and the default branch.
- Coverage: run on the default branch only.

```yaml
rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

This prevents duplicate pipelines on MR branches. Without these rules, GitLab runs both a branch pipeline and an MR pipeline for every push to an open MR. You'd pay for every job twice.

If you're on GitLab Free and paying per minute, this matters more than it sounds.

## Compared to GitHub Actions

The GitHub Actions equivalent for this pipeline is longer to write but equivalent in capability. The matrix syntax is similar:

```yaml
strategy:
    matrix:
        php: ['8.2', '8.3', '8.4']
        laravel: ['^11.0', '^12.0']
```

The main differences in practice:

- GitHub Actions caches with `actions/cache`, keyed on a hash you construct manually. GitLab's `key: files:` syntax does the hash for you.
- GitLab's `parallel: matrix` names jobs automatically. GitHub Actions names them by the matrix values, which is equivalent.
- GitLab MR pipelines dedup automatically when you use `rules`. GitHub Actions requires `concurrency` groups to get the same behaviour.
- Coverage diff annotations in GitLab are built-in via the Cobertura artifact. On GitHub you need a third-party Action.

Neither is clearly superior. GitLab's cache and rules are slightly more ergonomic for this use case. GitHub Actions has broader ecosystem support for things like `shivammathur/setup-php`, which lets you skip the `pecl install` dance entirely.

If your package is open source and on both platforms, maintain the GitHub Actions workflow for public contributors and GitLab CI for your internal pipeline. The `composer` scripts are the same — the CI files call the same commands.

## The Minimum Viable Version

If you want to copy something small and grow it:

```yaml
image: php:8.3-cli

stages:
    - test

variables:
    COMPOSER_CACHE_DIR: '$CI_PROJECT_DIR/.composer-cache'

cache:
    key:
        files:
            - composer.lock
    paths:
        - .composer-cache/
        - vendor/

test:
    stage: test
    before_script:
        - apt-get update -qq && apt-get install -y -qq git unzip
        - curl -sS https://getcomposer.org/installer | php -- --install-dir=/usr/local/bin --filename=composer
        - composer install --prefer-dist --no-progress --no-interaction
    script:
        - composer test
        - composer analyse
```

One job. Tests and PHPStan together. No matrix, no coverage. Start here on a new package. Add the matrix when you're ready to declare PHP and Laravel version support. Add coverage when you have enough tests for the number to be meaningful.

The full pipeline above doesn't become correct by adding things — it becomes correct when the tests, the PHPStan config, and the declared support matrix are all honest. Get those right first. The CI file is just the runner.
