> This is a rough draft. The Address API, namespaces, payloads, error text, and URLs in this post are fictional. All example domains use `example.invalid`, which is reserved for documentation.

Most PHP SDKs start with one exception:

```php
throw new ApiException($response->body());
```

This feels sufficient while the integration is small. The request failed, an exception was thrown, and the response body is available in the logs. What else could a caller need?

Quite a lot, as it turns out.

Imagine a fictional Address API. It validates postal addresses before an order can continue. The API can reject a request because:

- the API token is invalid;
- the client sent malformed JSON;
- the postal code does not belong to the region;
- the street number is outside the known range;
- the fictional geocoder cannot resolve the address;
- the client exceeded its rate limit;
- or the provider introduced an error the SDK has never seen.

If all of these failures become `ApiException`, every application using the SDK must inspect the response again. One application searches the message for "postal." Another checks a nested JSON property. A third looks through the stack trace to guess which operation failed. Each application slowly rebuilds part of the SDK's missing error model.

The result is fragile code in the worst possible place: recovery logic.

A PHP SDK should translate a remote API contract into a local PHP contract. That includes failures. The caller should be able to catch an exception at the level it understands:

```text
BadResponseException
├── AuthenticationException
├── RateLimitException
└── AddressRequestException
    └── AddressValidationException
        ├── PostalRegionMismatchException
        ├── StreetNumberOutOfRangeException
        └── GeocodeResolutionException
```

That tree gives us three useful catch levels:

- broad: any bad response from the Address API;
- middle: any address validation problem;
- leaf: one known problem with a specific recovery path.

The difficult part is not creating the classes. The difficult part is dispatching reliably when the remote payload is inconsistent, preserving useful debugging context without leaking it, and evolving the hierarchy without surprising existing callers.

This post builds that design from the bottom up.

## The Generic Exception Tax

Assume the fictional Address API returns this response:

```json
{
    "error": {
        "code": "ADDRESS_REJECTED",
        "message": "The submitted address could not be accepted.",
        "details": [
            {
                "code": "POSTAL_REGION_MISMATCH",
                "message": "The postal code does not match the region."
            }
        ]
    }
}
```

Every value in this payload is synthetic.

The SDK currently throws one generic exception:

```php
namespace Example\AddressSdk\Exception;

use RuntimeException;

final class ApiException extends RuntimeException
{
}
```

The application then has to recover like this:

```php
try {
    $client->validate($address);
} catch (ApiException $exception) {
    $payload = json_decode($exception->getMessage(), true);
    $message = strtolower($payload['error']['message'] ?? '');

    if (str_contains($message, 'postal')
        && str_contains($message, 'region')) {
        // Ask an operator to correct the address.
    }

    throw $exception;
}
```

This code has several problems.

First, it assumes the exception message is JSON. Exception messages are for humans and logs, not transport storage.

Second, it checks prose. A copy edit from "does not match" to "is not valid for" breaks the recovery path.

Third, it uses the broadest exception type, so the catch block runs for authentication failures, throttling, malformed requests, and new provider errors.

Fourth, every consumer writes a slightly different version. Bug fixes do not propagate through the ecosystem.

The SDK already understands the response format. It should perform the classification once.

## Exceptions Are Part of the SDK's Public API

An exception hierarchy is not an internal implementation detail. It is a public set of catch points.

If version 1 of an SDK throws `AddressRequestException`, consumers may already have:

```php
try {
    $client->validate($address);
} catch (AddressRequestException $exception) {
    $this->markAddressForReview();
}
```

Version 2 can add a child exception:

```php
final class PostalRegionMismatchException extends AddressValidationException
{
}
```

As long as the inheritance chain remains intact, the old catch block still works:

```text
PostalRegionMismatchException
    is an AddressValidationException
    is an AddressRequestException
    is a BadResponseException
```

This is the central compatibility benefit. The SDK can become more precise without forcing every caller to update on the same day.

The hierarchy should describe useful behavior, not reproduce every remote error code as a class. A provider might publish 200 codes. Your callers probably need five or ten behavioral groups.

For the fictional Address API, this hierarchy is enough:

```php
namespace Example\AddressSdk\Exception;

class BadResponseException extends \RuntimeException
{
}

class AuthenticationException extends BadResponseException
{
}

class RateLimitException extends BadResponseException
{
}

class AddressRequestException extends BadResponseException
{
}

class AddressValidationException extends AddressRequestException
{
}

final class PostalRegionMismatchException extends AddressValidationException
{
}

final class StreetNumberOutOfRangeException extends AddressValidationException
{
}

final class GeocodeResolutionException extends AddressValidationException
{
}
```

The middle class matters as much as the leaves. `AddressValidationException` gives applications a stable way to handle every correctable address problem, including future ones the SDK may add later.

Without that middle layer, callers must either catch each leaf or fall back to the very broad `AddressRequestException`.

## Keep Response Handling Out of Application Code

We need a small response contract for the examples. This is also fictional:

```php
namespace Example\AddressSdk\Http;

interface Response
{
    public function status(): int;

    public function body(): string;

    public function json(?string $path = null): mixed;
}
```

The exception should retain access to the response, but its message should not be the raw body:

```php
namespace Example\AddressSdk\Exception;

use Example\AddressSdk\Http\Response;
use RuntimeException;
use Throwable;

class BadResponseException extends RuntimeException
{
    public function __construct(
        private readonly Response $response,
        string $message = 'The fictional Address API rejected the request.',
        ?Throwable $previous = null,
    ) {
        parent::__construct(
            message: $message,
            code: $response->status(),
            previous: $previous,
        );
    }

    public function response(): Response
    {
        return $this->response;
    }
}
```

This distinction is important:

- the exception message is short and safe by default;
- the response remains available when code explicitly needs it;
- the original transport exception can remain in the previous-exception chain.

The response may contain the submitted address or other sensitive values. Retaining it does not make it safe to log. We will return to that problem later.

## Two-Layer `fromResponse()` Dispatch

One giant factory can map every possible failure:

```php
match ($code) {
    'AUTH_FAILED' => new AuthenticationException(...),
    'RATE_LIMITED' => new RateLimitException(...),
    'POSTAL_REGION_MISMATCH' => new PostalRegionMismatchException(...),
    // 40 more cases
};
```

This works until it does not. The root exception becomes coupled to every endpoint and every detail format.

A better design uses two dispatch layers.

Layer one selects the broad error family:

- authentication;
- rate limiting;
- address request;
- unknown bad response.

Layer two belongs to that family and selects a more precise subtype.

### Layer one: broad family dispatch

```php
namespace Example\AddressSdk\Exception;

use Example\AddressSdk\Http\Response;
use Throwable;

class BadResponseException extends \RuntimeException
{
    public function __construct(
        private readonly Response $response,
        string $message = 'The fictional Address API rejected the request.',
        ?Throwable $previous = null,
    ) {
        parent::__construct($message, $response->status(), $previous);
    }

    public static function fromResponse(
        Response $response,
        ?Throwable $previous = null,
    ): self {
        $code = $response->json('error.code');

        return match ($code) {
            'AUTH_FAILED' => new AuthenticationException(
                response: $response,
                previous: $previous,
            ),
            'RATE_LIMITED' => new RateLimitException(
                response: $response,
                previous: $previous,
            ),
            'ADDRESS_REJECTED' => AddressRequestException::fromResponse(
                response: $response,
                previous: $previous,
            ),
            default => new self(
                response: $response,
                previous: $previous,
            ),
        };
    }

    public function response(): Response
    {
        return $this->response;
    }
}
```

The root factory knows only the top-level protocol. It does not need to know what makes a postal code invalid.

### Layer two: address-specific dispatch

```php
namespace Example\AddressSdk\Exception;

use Example\AddressSdk\Http\Response;
use Throwable;

class AddressRequestException extends BadResponseException
{
    /**
     * @var array<string, class-string<AddressValidationException>>
     */
    private const array DETAIL_CODE_MAP = [
        'POSTAL_REGION_MISMATCH' => PostalRegionMismatchException::class,
        'STREET_NUMBER_OUT_OF_RANGE' => StreetNumberOutOfRangeException::class,
        'GEOCODE_RESOLUTION_FAILED' => GeocodeResolutionException::class,
    ];

    public static function fromResponse(
        Response $response,
        ?Throwable $previous = null,
    ): self {
        $exceptionClass = self::resolveExceptionClass($response);

        return new $exceptionClass(
            response: $response,
            previous: $previous,
        );
    }

    /**
     * @return class-string<AddressRequestException>
     */
    private static function resolveExceptionClass(Response $response): string
    {
        foreach (self::details($response) as $detail) {
            $code = $detail['code'] ?? null;

            if (is_string($code) && isset(self::DETAIL_CODE_MAP[$code])) {
                return self::DETAIL_CODE_MAP[$code];
            }
        }

        return self::resolveFromMessage($response)
            ?? AddressRequestException::class;
    }

    /**
     * @return list<array<string, mixed>>
     */
    private static function details(Response $response): array
    {
        $details = $response->json('error.details');

        if (! is_array($details)) {
            return [];
        }

        return array_values(array_filter(
            $details,
            static fn (mixed $detail): bool => is_array($detail),
        ));
    }
}
```

The address family owns address classification. If the provider adds an address-specific field next year, that change stays here.

You can repeat this pattern for other families without turning `BadResponseException` into a catalogue of the whole remote system.

## Machine Discriminator First, Message Fallback Second

The most important rule in the resolver is precedence:

1. use a documented machine-readable discriminator;
2. use message matching only as a compatibility fallback;
3. return a safe unknown parent when neither matches.

The fictional API gives us `error.details[*].code`. That field should win because it was designed for software.

Messages are written for people. They change because of punctuation, spelling, localization, support guidance, or product copy. Even when they appear stable for years, they are still prose.

That does not mean message matching is always forbidden. Real APIs are imperfect. Some old endpoints omit the detail code. Some only return it for one deployment region. Some documented codes arrive under a different property.

A message fallback can be a practical compatibility layer if it is narrow, tested, and lower priority than machine data.

```php
/**
 * @return class-string<AddressValidationException>|null
 */
private static function resolveFromMessage(
    Response $response,
): ?string {
    foreach (self::messages($response) as $message) {
        $normalized = strtolower(trim($message));

        if (str_contains($normalized, 'postal code')
            && str_contains($normalized, 'region')) {
            return PostalRegionMismatchException::class;
        }

        if (str_contains($normalized, 'street number')
            && str_contains($normalized, 'outside')
            && str_contains($normalized, 'range')) {
            return StreetNumberOutOfRangeException::class;
        }

        if (str_contains($normalized, 'geocoder')
            && str_contains($normalized, 'no location match')) {
            return GeocodeResolutionException::class;
        }
    }

    return null;
}

/**
 * @return list<string>
 */
private static function messages(Response $response): array
{
    $messages = [];
    $topLevel = $response->json('error.message');

    if (is_string($topLevel) && $topLevel !== '') {
        $messages[] = $topLevel;
    }

    foreach (self::details($response) as $detail) {
        foreach (['message', 'description'] as $key) {
            $value = $detail[$key] ?? null;

            if (is_string($value) && $value !== '') {
                $messages[] = $value;
            }
        }
    }

    return $messages;
}
```

The discriminator-first rule prevents a dangerous edge case. Consider this synthetic response:

```json
{
    "error": {
        "code": "ADDRESS_REJECTED",
        "message": "The fictional geocoder returned no location match.",
        "details": [
            {
                "code": "POSTAL_REGION_MISMATCH",
                "message": "The postal code does not match the region."
            }
        ]
    }
}
```

The top-level message and the detail code disagree. The detail code is more specific and machine-readable, so the SDK should return `PostalRegionMismatchException`.

That precedence must have a test. Otherwise a future cleanup may reorder the checks and silently change behavior.

### Avoid fuzzy message matching

Do not turn the fallback into a general text classifier:

```php
// Too broad.
if (str_contains($message, 'address')) {
    return AddressValidationException::class;
}
```

An authentication error might say, "The account address could not be loaded." A broad keyword would misclassify it.

Fallback checks should use enough independent terms to identify one known sentence family. If you cannot make the match narrow, return the unknown parent.

An unclassified exception is better than a confidently wrong exception.

## Multiple Details Need an Explicit Rule

Some APIs return more than one detail:

```json
{
    "error": {
        "code": "ADDRESS_REJECTED",
        "message": "The fictional Address API found multiple problems.",
        "details": [
            {
                "code": "POSTAL_REGION_MISMATCH",
                "message": "The postal code does not match the region."
            },
            {
                "code": "GEOCODE_RESOLUTION_FAILED",
                "message": "The fictional geocoder returned no location match."
            }
        ]
    }
}
```

There is no universally correct class for two simultaneous failures. The SDK needs a deterministic policy.

Possible policies are:

1. first recognized detail wins;
2. the most specific or actionable detail wins;
3. throw a composite exception containing all recognized details;
4. return only the middle `AddressValidationException`.

For a small SDK, "first recognized detail wins" is often the simplest choice because many APIs order details by importance. It must still be documented and tested.

If the remote API does not guarantee order, use an explicit priority map:

```php
private const array DETAIL_PRIORITY = [
    'POSTAL_REGION_MISMATCH' => 10,
    'STREET_NUMBER_OUT_OF_RANGE' => 20,
    'GEOCODE_RESOLUTION_FAILED' => 30,
];
```

Then sort recognized codes by your recovery needs. Do not let PHP array order become an accidental business rule.

## An RFC 7807 Variant

Many APIs use the Problem Details format defined by RFC 7807. A synthetic response could look like this:

```json
{
    "type": "https://errors.example.invalid/address/postal-region-mismatch",
    "title": "Address validation failed",
    "status": 422,
    "detail": "The postal code does not match the region.",
    "code": "POSTAL_REGION_MISMATCH"
}
```

The URL is fictional and uses `example.invalid`.

In this format, `type` is the primary machine discriminator. The extension member `code` can be a secondary discriminator. `title` and `detail` remain human-readable text.

```php
private const array PROBLEM_TYPE_MAP = [
    'https://errors.example.invalid/address/postal-region-mismatch'
        => PostalRegionMismatchException::class,
    'https://errors.example.invalid/address/street-number-out-of-range'
        => StreetNumberOutOfRangeException::class,
    'https://errors.example.invalid/address/geocode-resolution-failed'
        => GeocodeResolutionException::class,
];

/**
 * @return class-string<AddressRequestException>
 */
private static function resolveProblemDetails(Response $response): string
{
    $type = $response->json('type');

    if (is_string($type) && isset(self::PROBLEM_TYPE_MAP[$type])) {
        return self::PROBLEM_TYPE_MAP[$type];
    }

    $code = $response->json('code');

    if (is_string($code) && isset(self::DETAIL_CODE_MAP[$code])) {
        return self::DETAIL_CODE_MAP[$code];
    }

    return self::resolveFromProblemDetail($response)
        ?? AddressRequestException::class;
}
```

The same precedence still applies:

1. `type`;
2. extension `code`;
3. narrow match against `detail`;
4. unknown family parent.

Do not dispatch on `title`. Titles are especially likely to be localized or rewritten.

Also do not infer behavior from the path segments of an unknown `type` URI. Treat the complete URI as an opaque identifier. If the provider changes its URI structure, your SDK should not guess.

## Preserve the Response and Previous Exception Safely

Classification should not destroy the original failure.

If the HTTP transport throws a timeout or request exception, callers may need that exception for retry decisions and diagnostics. The typed API exception should keep it as `$previous`:

```php
try {
    $response = $this->transport->send($request);
} catch (TransportException $transportException) {
    throw new NetworkException(
        message: 'The fictional Address API request did not complete.',
        previous: $transportException,
    );
}

if ($response->status() >= 400) {
    throw BadResponseException::fromResponse(
        response: $response,
    );
}
```

When a transport library represents an HTTP error as an exception that contains a response, pass that exception through:

```php
try {
    $response = $this->transport->send($request);
} catch (HttpResponseException $httpException) {
    throw BadResponseException::fromResponse(
        response: $httpException->response(),
        previous: $httpException,
    );
}
```

This gives diagnostics both layers:

```text
PostalRegionMismatchException
└── previous: HttpResponseException
```

There are four safety rules.

### 1. Do not put the raw body in the exception message

This is tempting:

```php
parent::__construct($response->body());
```

It also means every default exception logger receives the full payload. An address API can echo a full address. Other APIs may echo payment data, names, tokens, or documents.

Use a stable message:

```php
parent::__construct(
    message: 'The fictional Address API rejected the address.',
    code: $response->status(),
    previous: $previous,
);
```

### 2. Offer an allowlisted diagnostic context

The exception can expose safe, structured fields:

```php
/**
 * @return array{
 *     status: int,
 *     error_code: string|null,
 *     detail_code: string|null
 * }
 */
public function diagnosticContext(): array
{
    return [
        'status' => $this->response()->status(),
        'error_code' => $this->stringValue('error.code'),
        'detail_code' => $this->firstDetailCode(),
    ];
}
```

The allowlist is the point. Do not return the whole decoded response under a key named `context`.

### 3. Redact headers

If the response abstraction exposes headers, do not include authorization, cookies, signatures, or provider-specific secret headers in logs. Prefer a small allowlist such as content type and retry timing.

### 4. Think about serialization

Queued jobs and cached failure records may serialize exceptions. A retained response can contain a large body, stream handles, request headers, or sensitive fields.

Options include:

- make API exceptions explicitly non-serializable;
- store only a redacted response snapshot;
- exclude the response during serialization;
- or document that these exceptions must not cross process boundaries.

For many SDKs, a small immutable snapshot is safer than a full transport response:

```php
final readonly class ResponseSnapshot
{
    public function __construct(
        public int $status,
        public ?string $errorCode,
        public ?string $detailCode,
    ) {
    }
}
```

The best choice depends on the SDK contract. The minimum rule is simple: preserving a response is useful, but logging or serializing it by default is not safe.

## Catch at the Granularity You Need

The hierarchy exists so application code can choose the correct level.

### Broad catch: the integration failed

Use the root when the application has one fallback for every provider failure:

```php
try {
    $result = $addressClient->validate($address);
} catch (BadResponseException $exception) {
    $this->pauseTheWorkflow();
    $this->recordIntegrationFailure($exception->diagnosticContext());
}
```

This catch includes authentication, throttling, address validation, and unknown bad responses.

It is useful at process boundaries, but it is usually too broad for a targeted correction message or alert.

### Middle catch: the address needs correction

Use the category parent when all known address problems have the same application action:

```php
try {
    $result = $addressClient->validate($address);
} catch (AddressValidationException $exception) {
    $this->requestAddressCorrection();
}
```

This is often the best default. The application does not need to know every provider code. It only needs to know that the address can be corrected.

### Leaf catch: one precise recovery path

Use a leaf when one error has unique handling:

```php
try {
    $result = $addressClient->validate($address);
} catch (PostalRegionMismatchException $exception) {
    $this->highlightPostalCodeAndRegionFields();
} catch (AddressValidationException $exception) {
    $this->requestGeneralAddressCorrection();
}
```

Order matters. Catch the leaf before its parent.

This structure reads like the recovery policy:

1. for a postal-region mismatch, highlight two fields;
2. for another known validation failure, ask for a general correction;
3. let unrelated failures continue to the outer error boundary.

## Alert Routing Without Message Parsing

Typed exceptions are operational types too.

Before the SDK has a hierarchy, an application might route alerts like this:

```php
$message = strtolower($exception->getMessage());

if (str_contains($message, 'postal')
    && str_contains($message, 'region')) {
    $this->sendAddressCorrectionAlert();
}
```

That repeats the SDK's classification problem.

With typed exceptions, alert routing becomes explicit:

```php
match (true) {
    $exception instanceof PostalRegionMismatchException
        => $this->alerts->send(
            destination: AlertDestination::AddressOperations,
            severity: AlertSeverity::Critical,
            context: $exception->diagnosticContext(),
        ),
    $exception instanceof AddressValidationException
        => $this->alerts->send(
            destination: AlertDestination::AddressOperations,
            severity: AlertSeverity::Warning,
            context: $exception->diagnosticContext(),
        ),
    $exception instanceof AuthenticationException
        => $this->alerts->send(
            destination: AlertDestination::IntegrationOwners,
            severity: AlertSeverity::Critical,
            context: $exception->diagnosticContext(),
        ),
    default => $this->alerts->send(
        destination: AlertDestination::Engineering,
        severity: AlertSeverity::Error,
        context: $exception->diagnosticContext(),
    ),
};
```

The application routes on semantic type. It does not care how the provider spelled the message.

### Do not sniff the stack trace

Another common workaround is to search the exception trace for a class or method:

```php
$cameFromCheckout = collect($exception->getTrace())
    ->contains(
        fn (array $frame): bool =>
            ($frame['class'] ?? null) === CheckoutAction::class,
    );
```

This is fragile for a different reason. Refactoring a method, introducing a queue, adding a decorator, or changing an HTTP client can alter the trace without changing business behavior.

If alert severity depends on business context, pass that context explicitly:

```php
try {
    $addressClient->validate($address);
} catch (PostalRegionMismatchException $exception) {
    $this->alerts->sendAddressFailure(
        exception: $exception,
        workflow: AddressWorkflow::OrderSubmission,
        impact: WorkflowImpact::Blocking,
    );

    throw $exception;
}
```

The SDK should classify the remote failure. The application should supply local business context. Neither layer should infer the other's meaning from a stack trace.

## Unknown Errors Must Stay Visible

No map is complete forever.

Tomorrow, the fictional Address API may return:

```json
{
    "error": {
        "code": "ADDRESS_REJECTED",
        "message": "The submitted address could not be accepted.",
        "details": [
            {
                "code": "BUILDING_ACCESS_UNCONFIRMED",
                "message": "The building access data could not be confirmed."
            }
        ]
    }
}
```

The SDK has never seen `BUILDING_ACCESS_UNCONFIRMED`.

It should not:

- throw a PHP error because the map has no key;
- guess a leaf class from one word in the message;
- return `null`;
- or silently treat the response as successful.

It should return the closest safe parent:

```php
return new AddressRequestException(
    response: $response,
    previous: $previous,
);
```

The parent preserves compatibility and keeps the failure visible. Applications with a broad catch continue to work. Diagnostics still include the unknown detail code, so maintainers can decide whether it deserves a new class.

You can make the fallback more expressive:

```php
final class UnknownAddressException extends AddressRequestException
{
}
```

That class is useful if callers want a separate alert for unmapped provider behavior. It is less useful if it adds a type that nobody catches. Choose based on actual recovery needs.

The important property is that unknown errors degrade safely.

## A Complete Factory Shape

Putting the pieces together, the fictional SDK can keep parsing and construction separate:

```php
namespace Example\AddressSdk\Exception;

use Example\AddressSdk\Http\Response;
use Throwable;

class AddressRequestException extends BadResponseException
{
    /**
     * @var array<string, class-string<AddressValidationException>>
     */
    private const array DETAIL_CODE_MAP = [
        'POSTAL_REGION_MISMATCH' => PostalRegionMismatchException::class,
        'STREET_NUMBER_OUT_OF_RANGE' => StreetNumberOutOfRangeException::class,
        'GEOCODE_RESOLUTION_FAILED' => GeocodeResolutionException::class,
    ];

    public static function fromResponse(
        Response $response,
        ?Throwable $previous = null,
    ): self {
        $class = self::resolveFromDetailCode($response)
            ?? self::resolveFromMessage($response)
            ?? self::class;

        return new $class(
            response: $response,
            message: self::safeMessageFor($class),
            previous: $previous,
        );
    }

    /**
     * @return class-string<AddressValidationException>|null
     */
    private static function resolveFromDetailCode(
        Response $response,
    ): ?string {
        foreach (self::details($response) as $detail) {
            $code = $detail['code'] ?? null;

            if (is_string($code) && isset(self::DETAIL_CODE_MAP[$code])) {
                return self::DETAIL_CODE_MAP[$code];
            }
        }

        return null;
    }

    /**
     * @param class-string<AddressRequestException> $class
     */
    private static function safeMessageFor(string $class): string
    {
        return match ($class) {
            PostalRegionMismatchException::class
                => 'The postal code does not match the region.',
            StreetNumberOutOfRangeException::class
                => 'The street number is outside the supported range.',
            GeocodeResolutionException::class
                => 'The fictional geocoder returned no location match.',
            default
                => 'The fictional Address API rejected the address.',
        };
    }

    // details(), messages(), and resolveFromMessage() as shown above.
}
```

This code has a deliberate order:

```text
detail code
    ↓ no match
message fallback
    ↓ no match
AddressRequestException
```

Keeping those stages separate makes the precedence easy to test and review.

## Testing the Hierarchy

The test suite must prove classification, compatibility, and preservation. A few happy-path tests are not enough.

### Test matrix

At minimum, cover these cases:

| Input                                       | Expected exception                  | Why                         |
| ------------------------------------------- | ----------------------------------- | --------------------------- |
| Known top-level authentication code         | `AuthenticationException`           | Layer-one dispatch          |
| Known top-level rate-limit code             | `RateLimitException`                | Layer-one dispatch          |
| Known address detail code                   | Matching leaf                       | Layer-two dispatch          |
| Known detail code in the second detail item | Matching leaf                       | Full detail scan            |
| Missing detail code with known message      | Matching leaf                       | Compatibility fallback      |
| Known code with conflicting message         | Code-selected leaf                  | Precedence                  |
| Unknown address detail code                 | `AddressRequestException`           | Safe family fallback        |
| Unknown top-level code                      | `BadResponseException`              | Safe root fallback          |
| Empty details array                         | Parent fallback                     | Shape tolerance             |
| `details` is not an array                   | Parent fallback                     | Malformed payload tolerance |
| Invalid JSON                                | Parent fallback                     | Parsing tolerance           |
| Response supplied to factory                | Same response is accessible         | Context preservation        |
| Previous exception supplied                 | Same exception is `getPrevious()`   | Chain preservation          |
| Leaf thrown                                 | Catchable by leaf, middle, and root | Compatibility               |

## Common Pitfalls

The pattern is small, but several implementation details can make it brittle.

### Pitfall 1: parsing only the first detail

This misses responses where the useful code appears later:

```php
$code = $response->json('error.details.0.code');
```

Scan all detail objects unless the API contract guarantees the first one is authoritative.

### Pitfall 2: treating every new remote code as a new class

Classes should correspond to useful catch behavior. If five provider codes all mean "the address needs manual correction," they may belong under one `AddressValidationException`.

Add a leaf only when callers can do something meaningfully different.

### Pitfall 3: using message matching as the primary contract

If a discriminator exists, use it. Message matching is a fallback for known gaps, not the foundation.

### Pitfall 4: using one giant regular expression

A complex expression hides intent and makes near-miss tests difficult. Small checks with explicit terms are easier to review.

### Pitfall 5: putting raw payloads into exception messages

Default logging systems capture exception messages. Keep raw bodies behind explicit access and expose allowlisted diagnostic context.

### Pitfall 6: dropping the previous exception

Without `$previous`, transport details disappear. Always thread it through every factory and constructor.

### Pitfall 7: inconsistent constructor signatures

Dynamic construction requires compatible constructors:

```php
return new $exceptionClass(
    response: $response,
    previous: $previous,
);
```

If one leaf adds a required constructor argument, the factory breaks. Put shared data on the base class. Use named constructors for exceptional leaf-specific data.

### Pitfall 8: returning `static` from a factory that changes class

This signature looks attractive:

```php
public static function fromResponse(Response $response): static
```

It is misleading when calling the parent factory can return a sibling or a different child. Static analysis may assume the result matches the called class.

Use `self` on the family factory or document a precise `class-string` return flow. A separate resolver object is also valid if the type system becomes awkward.

### Pitfall 9: reparenting an existing exception casually

Moving a class from one parent to another changes which catch blocks receive it. That can be a breaking change even if the class name stays the same.

### Pitfall 10: exact-class checks in consumer code

This is brittle:

```php
if ($exception::class === AddressRequestException::class) {
    // ...
}
```

When the SDK adds a leaf, the condition stops matching. Consumers should use `instanceof` unless they truly need exact identity.

### Pitfall 11: hiding unknown errors

Do not classify every unknown address error as a known leaf just to keep dashboards tidy. Unknown provider behavior should remain visible.

### Pitfall 12: alert routing inside the SDK

The SDK knows the remote error type. It does not know whether the current application flow blocks an order, runs a background cleanup, or powers an optional preview.

Keep business severity and alert destination in the application.

## When a Resolver Object Is Better

Static factories are easy to discover:

```php
throw BadResponseException::fromResponse($response);
```

They are a good fit while the mapping is small and deterministic.

If classification grows, move it into a dedicated resolver:

```php
final class ExceptionResolver
{
    public function resolve(
        Response $response,
        ?Throwable $previous = null,
    ): BadResponseException {
        // Broad and family dispatch.
    }
}
```

This helps when:

- different API versions use different mappings;
- the resolver needs injected configuration;
- endpoint context affects interpretation;
- several payload formats coexist;
- or extension packages register additional mappings.

Do not begin with a plugin system for three codes. Start with the static map. Extract the resolver when real requirements appear.

## Evolution and Versioning

Exception hierarchies evolve with the remote API. Treat each change as a public-contract change.

### Adding a new leaf

Suppose version 1 returns `AddressValidationException` for `GEOCODE_RESOLUTION_FAILED`. Version 1.1 introduces `GeocodeResolutionException` as a child.

Parent catches remain compatible:

```php
catch (AddressValidationException $exception) {
    // Still runs.
}
```

However, operational behavior can still change:

- exact-class assertions may fail;
- alert routers may now select a leaf-specific destination;
- consumers that serialize class names may observe a new value.

This is usually suitable for a minor release, but it deserves release notes.

### Adding an alias for a provider code

The provider may emit both:

```text
POSTAL_REGION_MISMATCH
ZIP_REGION_MISMATCH
```

Both can map to the same exception:

```php
private const array DETAIL_CODE_MAP = [
    'POSTAL_REGION_MISMATCH' => PostalRegionMismatchException::class,
    'ZIP_REGION_MISMATCH' => PostalRegionMismatchException::class,
];
```

Keep old aliases until the provider contract guarantees they are gone. Removing one too early turns a known failure back into an unknown parent.

### Renaming a public exception

Renaming is a breaking change. The safest option is often to keep the old public name and improve its documentation. A perfect name is not always worth an ecosystem-wide migration.

If the class was not declared `final`, a deprecated compatibility subclass can help. If it was declared `final`, introducing a second name is more awkward and may confuse static analysis. Treat that as another reason to avoid casual renames.

### Reparenting a class

This can silently change catch behavior:

```text
Before:
GeocodeResolutionException → AddressValidationException

After:
GeocodeResolutionException → GeocodingServiceException
```

Applications catching `AddressValidationException` stop receiving it. That is a major-version change unless you can preserve both contracts through another design.

### Changing fallback precedence

Switching from "message first" to "code first" is a correctness fix, but it may alter the selected class for conflicting payloads. Record the change and add a regression fixture.

### Supporting a new API version

Do not mix incompatible code maps without context:

```php
ExceptionResolver::forVersion(ApiVersion::V2)
    ->resolve($response);
```

Version-specific resolvers make removal and testing easier. They also avoid a map full of comments such as "only for old accounts" or "sometimes used by v2."

### Track unknown discriminators

The safe parent fallback should expose the unknown machine code through diagnostic context. Applications can count unknown values without logging the body.

That observation loop is how the hierarchy improves:

1. unknown code falls back safely;
2. diagnostics show a repeated discriminator;
3. maintainers confirm its semantics;
4. the SDK adds a mapping and tests;
5. consumers can adopt a more precise catch when useful.

The map grows from evidence, not speculation.

## A Practical Migration Plan

If your SDK already throws one generic exception, migrate without breaking callers.

### Step 1: keep the existing root

Do not replace the old exception immediately. Make it the stable root or keep it as a compatibility parent.

### Step 2: add one useful middle category

Find a set of failures with the same recovery action. For the fictional API, that is `AddressValidationException`.

### Step 3: add only proven leaves

Use payload fixtures from documentation or controlled synthetic tests. Do not create classes for codes you have never observed and do not understand.

### Step 4: route construction through `fromResponse()`

There must be one path that converts bad responses into exceptions. If some request classes still use `new ApiException($body)`, callers get inconsistent behavior.

### Step 5: update application catches by behavior

Move message parsing to type checks:

```php
catch (PostalRegionMismatchException $exception) {
    // Specific recovery.
}
```

Move groups of leaf catches to the middle parent when they share behavior:

```php
catch (AddressValidationException $exception) {
    // Shared correction flow.
}
```

### Step 6: keep the unknown path noisy enough

Do not suppress every parent exception after adding the first leaves. Unknown failures should still reach normal diagnostics.

### Step 7: release and document the catch contract

Documentation should show the tree and examples for broad, middle, and leaf catches. A flat list of class names does not explain intended use.

## The Real Boundary of Responsibility

A good SDK does not decide the whole recovery policy.

The fictional Address API SDK should know:

- the response is an address failure;
- the machine code means postal-region mismatch;
- the response status;
- which safe diagnostic fields are available;
- and which transport exception came before it.

The application should know:

- whether this request blocks an order;
- whether a person can correct the address;
- whether to retry;
- where an alert belongs;
- the alert severity;
- and which local entity or workflow is affected.

Typed exceptions create a clean handoff between those layers.

The SDK says:

```text
PostalRegionMismatchException
```

The application says:

```text
This happened during a blocking order submission, so request correction
and send a critical operations alert.
```

No message parsing. No stack-trace archaeology. No duplicate JSON traversal in every consumer.

## Final Checklist

Before shipping typed vendor exceptions, verify:

- [ ] Existing broad catch blocks still catch every new child.
- [ ] A useful middle category exists for shared recovery.
- [ ] Machine-readable discriminators have priority over messages.
- [ ] Message fallback is narrow and tested.
- [ ] Unknown codes return a safe parent.
- [ ] Multiple detail objects have a deterministic policy.
- [ ] The response remains accessible where the SDK contract requires it.
- [ ] The raw response body is not the exception message.
- [ ] The previous transport exception is preserved.
- [ ] Diagnostic context uses an allowlist.
- [ ] Alert routing uses exception types, not prose.
- [ ] Business impact is passed explicitly, not inferred from the trace.
- [ ] Tests cover broad, middle, and leaf compatibility.
- [ ] Tests prove code precedence over conflicting text.
- [ ] Tests cover malformed and unknown payloads.
- [ ] At least one focused test was observed failing with the mapping removed.
- [ ] Release notes explain new public exception classes and catch points.

## Closing Thought

An HTTP status tells you that a request failed. A typed exception tells your application what kind of failure crossed the boundary.

That difference matters most after the request has already gone wrong.

The simplest useful design is not complicated:

1. keep a stable root exception;
2. add a middle class for shared behavior;
3. add leaves only for errors with distinct recovery;
4. dispatch on machine codes first;
5. use messages only as a narrow fallback;
6. preserve the original context without logging it by default;
7. return a safe parent for everything unknown.

Once the SDK owns that translation, every consumer becomes smaller. Recovery code reads in domain terms. Alerts route by type. Refactors stop depending on stack traces. Provider copy changes stop breaking production logic.

The exception tree becomes what the SDK should have provided from the start: a stable local model of a remote failure contract.
