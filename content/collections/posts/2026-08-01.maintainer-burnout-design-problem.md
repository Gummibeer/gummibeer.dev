I wrote about [lessons from open source software](https://gummibeer.dev/blog/lessons-from-open-source-software) a while back. That post was reactive — a response to what I'd observed after years of maintaining packages. This one is more prescriptive. Less philosophy, more recipes.

The thesis: most of the time that burns maintainers out isn't spent on hard technical problems. It's spent on things that look like communication but are really structural failures. You're answering the same question for the forty-third time not because the answer is hard, but because nothing in your repo's defaults routes people to it first.

Here are the five issue types that drain maintainer time the most, and what you can actually do about them.

---

## 1. "Why doesn't this work with [Laravel version]?"

These show up whenever a major version of a dependency drops. They're not bugs. They're usually either a version constraint you haven't relaxed yet, a breaking change in the dependency's API, or the user's own composer.json being wrong.

**What happens without mitigations:** You answer individually. You write the same message about checking `composer why` and your `require` block. You do this eight times across a release cycle.

**Mitigation: a version compatibility issue template.**

```yaml
# .github/ISSUE_TEMPLATE/compatibility.yml
name: Compatibility Question
description: Issues running the package with a specific version of a dependency
labels: [question]
body:
    - type: input
      id: package-version
      attributes:
          label: Package version
      validations:
          required: true
    - type: input
      id: dependency-version
      attributes:
          label: Framework/dependency version (Laravel, Symfony, PHP, etc.)
      validations:
          required: true
    - type: textarea
      id: composer-output
      attributes:
          label: Output of `composer why [package-name]`
          description: Run this in your project root and paste the output
      validations:
          required: true
    - type: textarea
      id: error
      attributes:
          label: Error message or unexpected behaviour
      validations:
          required: true
```

The `composer why` field alone filters out a significant chunk of these. People either find the answer themselves running the command, or they paste output that immediately tells you the problem.

## 2. "My PR has been open for six months"

These are painful because they're often valid. The PR is fine. You just haven't had time. And now the contributor is frustrated, the branch is stale, and you feel guilty every time you see the notification.

**Mitigation: set honest expectations upfront.**

Your `CONTRIBUTING.md` should state your review bandwidth plainly. Not "we aim to review within X days" — that's aspirational and you'll break it. Something like: "This package is maintained in spare time. PRs are reviewed when capacity allows, which may take weeks to months. If you need faster turnaround, consider opening an issue to discuss the approach first."

Then use the stale bot — but carefully.

```yaml
# .github/stale.yml
daysUntilStale: 90
daysUntilClose: 14
staleLabel: stale
exemptLabels:
    - pinned
    - security
    - good first issue
staleIssueMessage: >
    This issue has been open for 90 days without activity. If it's still
    relevant, please leave a comment to keep it open. Otherwise it will be
    closed in 14 days.
stalePrMessage: >
    This PR has been open for 90 days without activity. If you'd like to
    continue, please rebase and leave a comment. Otherwise it will be closed
    in 14 days. Closing doesn't mean the work isn't appreciated — it keeps
    the queue manageable.
closeStaleIssuesComment: >
    Closing due to inactivity. Feel free to reopen if this is still relevant.
```

The phrasing matters. "Closing doesn't mean the work isn't appreciated" isn't feel-good padding — it's a genuine attempt to preserve the relationship. Contributors who get a cold automated close without context don't come back.

One rule: **never auto-close issues labelled `bug` or `security`**. The stale bot is for managing queue length, not triaging severity.

## 3. "I need this feature for my project"

This is the one that causes the most long-term damage. The request is often reasonable. You can see how it fits. But it's also not quite right for the package — too specific, too opinionated for the general case, or it requires a scope expansion you're not ready to commit to.

**Mitigation: close early, explain concisely, point outward.**

The correct response is not "maybe someday" — that's what creates the six-month backlog. It's: "This is outside the scope of what this package does. Here's why. Here's where else you could go."

What "outside scope" means needs to be documented. Your `README.md` should have a brief section on what the package explicitly does and does not do. Not every package has this, and the ones that don't end up fielding requests forever.

When you close, use GitHub's "Close as not planned" and leave a note. A template for your clipboard:

> This is outside the scope of this package — [package name] handles [specific thing], not [requested thing]. You might get better results with [alternative] or by writing a custom [wrapper/extension]. I'm closing this to keep the issue tracker focused, but I appreciate you taking the time to open it.

If you find yourself writing this same message three times, add it to your issue template's "before you submit" checklist.

## 4. "Tests are failing on CI" (on PRs that look fine locally)

These usually fall into three categories: environment differences, flaky tests, or the contributor's branch being behind `main`. All three are fixable with automation or better PR defaults.

**Mitigation: a PR checklist that catches 80% of review comments before review.**

```markdown
<!-- .github/pull_request_template.md -->

## Summary

<!-- What does this PR do? One or two sentences. -->

## Checklist

- [ ] Tests pass locally (`composer test`)
- [ ] Branch is rebased on current `main`
- [ ] New behaviour is covered by a test
- [ ] `CHANGELOG.md` updated (or this is a chore/docs-only change)
- [ ] No unrelated changes included
```

Short and honest. Don't add items you're not actually going to enforce — checklist items that reviewers routinely ignore teach contributors to ignore them too.

For environment differences, specify your supported PHP and framework versions in the CI matrix and make it visible. If your `composer.json` requires PHP `^8.1` but your CI only tests 8.1 and 8.2, document it. Contributors running 8.3 deserve to know before they submit.

## 5. "Is this package still maintained?"

This one stings because it implies you've failed at communication. But it's not always your fault — GitHub's signals around maintenance status are weak. A repo with no commits in eight months and a green "passing" CI badge reads ambiguously.

**Mitigation: explicit maintenance status, cheap releases.**

First: use the `Maintained: yes` / `Maintained: no (as-of YYYY-MM-DD)` pattern in your README, even if it feels silly. It's a one-line change that saves everyone time.

Second: make releasing feel cheap. The main reason maintainers don't ship patch releases often enough is that the release process is manual and tedious. Fix that with automation.

For PHP packages on GitHub, a combination of a conventional commits standard and a simple release workflow gets you a long way:

```yaml
# .github/workflows/release.yml
name: Release
on:
    workflow_dispatch:
        inputs:
            version:
                description: 'Version (e.g. 1.2.3)'
                required: true

jobs:
    release:
        runs-on: ubuntu-latest
        steps:
            - uses: actions/checkout@v4
              with:
                  fetch-depth: 0

            - name: Generate changelog
              run: |
                  echo "## v${{ github.event.inputs.version }}" > release-notes.md
                  git log $(git describe --tags --abbrev=0)..HEAD \
                    --pretty=format:"- %s" \
                    --no-merges >> release-notes.md

            - name: Create tag and release
              uses: softprops/action-gh-release@v2
              with:
                  tag_name: v${{ github.event.inputs.version }}
                  name: v${{ github.event.inputs.version }}
                  body_path: release-notes.md
```

This isn't fully automated — you trigger it manually and pass a version number. That's intentional. For most packages, a human decision about version bumping is correct. The automation handles the tedious parts: collecting commits since the last tag, creating the release, tagging.

If you want to go further, [release-please](https://github.com/googleapis/release-please) or [semantic-release](https://github.com/semantic-release/semantic-release) handle the version decision too, but they require conventional commit discipline from all contributors. Evaluate whether that's a tax worth imposing.

## What Automation Cannot Fix

Let's be honest about the ceiling.

Automation handles routing, triage, and the mechanical parts of a release. It doesn't handle the moment when a motivated contributor submits a large PR that's architecturally wrong — not bad code, just the wrong approach. Handling that well requires a conversation, and conversations take time no bot can substitute for.

It also doesn't fix the fundamental tension in open source: users have infinite requests, and you have finite time. Issue templates reduce noise; they don't reduce the gap between what users want and what you can deliver. If your package has achieved significant adoption, the volume will eventually exceed what any amount of automation can absorb. At that point, the real decisions are about governance — co-maintainers, organization ownership, transfer — not automation.

What automation does is buy you back the hours you were spending on avoidable noise, so that the hard conversations don't feel like the last straw. That's worth a lot. It's just not everything.

Set up the templates. Configure the stale bot kindly. Automate your releases. Then protect the time you've recovered.
