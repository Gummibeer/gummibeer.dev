You're integrating a new shipping rate calculator. The existing one works. The new one is supposed to be better — cheaper API, more accurate rates, better coverage. But "supposed to be" isn't good enough when a miscalculation means you're either overcharging customers or eating the difference yourself.

The answer isn't to write tests and hope. It's shadow mode.

---

## What shadow mode is

Shadow mode runs two implementations in parallel. The **incumbent** produces the result that actually gets used. The **challenger** runs alongside it, produces its own result, and that result is thrown away — but not before you compare the two and log any discrepancy.

No customer sees the challenger's output. No database row is written based on it. But you accumulate real production signal about whether the challenger agrees with the incumbent, and where it doesn't.

When discrepancies drop to an acceptable level, you cut over. Then you delete the shadow path.

This is the same concept Martin Fowler describes in [Branch by Abstraction](https://martinfowler.com/bliki/BranchByAbstraction.html) — except instead of branching at the library level, you're branching at the business logic level and using production traffic to validate the branch before making it permanent.

---

## The three phases

**Phase 1 — Shadow.** Challenger runs in parallel. Its output is compared and logged. Nothing is persisted from it. This is where you discover the bugs you didn't know existed.

**Phase 2 — Compare.** You've fixed the obvious issues. Discrepancies are now rare edge cases. You add more structured observability. You start building confidence. You might also run the challenger result through your downstream systems in a dry-run mode to catch integration bugs.

**Phase 3 — Cut over.** The challenger becomes the incumbent. The old implementation is removed. The shadow infrastructure is deleted.

Most teams rush phase 1 and skip phase 2 entirely. Don't. Phase 2 is where the interesting bugs live.

## Where to put the shadow code

The cleanest placement is a **decorator** that wraps the incumbent behind an interface. Both implementations share the same interface. The decorator delegates to the real implementation, then fires the shadow asynchronously.

```php
interface ShippingRateCalculator
{
    public function calculate(Shipment $shipment): Money;
}
```

```php
final class ShadowShippingRateCalculator implements ShippingRateCalculator
{
    public function __construct(
        private readonly ShippingRateCalculator $incumbent,
        private readonly ShippingRateCalculator $challenger,
        private readonly ShadowComparator $comparator,
    ) {}

    public function calculate(Shipment $shipment): Money
    {
        $incumbentRate = $this->incumbent->calculate($shipment);

        rescue(function () use ($shipment, $incumbentRate): void {
            $challengerRate = $this->challenger->calculate($shipment);
            $this->comparator->compare($shipment, $incumbentRate, $challengerRate);
        });

        return $incumbentRate;
    }
}
```

The `rescue()` call is Laravel's helper that swallows exceptions and optionally reports them. This is important: the challenger must never be able to take down the incumbent's response path. If the new service's API is down, returns garbage, or throws — the customer still gets a rate, and you get a logged exception.

Bind this in a service provider:

```php
$this->app->bind(ShippingRateCalculator::class, function (Application $app): ShippingRateCalculator {
    return new ShadowShippingRateCalculator(
        incumbent: $app->make(FedExRateCalculator::class),
        challenger: $app->make(UpsRateCalculator::class),
        comparator: $app->make(ShadowComparator::class),
    );
});
```

When you cut over, you change one binding. No business logic changes.

An alternative placement is an **event listener**. If the calculation already fires a domain event (`ShipmentRated`), you can attach a listener that re-calculates with the challenger and compares. This works well in event-sourced systems where the calculation is a consequence of a recorded event rather than an inline call.

## What to compare

For discrete values — a list of available service levels, a boolean eligibility result — an exact match is the right check.

For monetary values and floating-point rates, exact match will produce noise. Two implementations that are both correct might differ by a rounding strategy. Decide on a tolerance band upfront.

```php
final class ShadowComparator
{
    private const TOLERANCE_CENTS = 1;

    public function compare(
        Shipment $shipment,
        Money $incumbentRate,
        Money $challengerRate,
    ): void {
        $delta = abs($incumbentRate->getAmount() - $challengerRate->getAmount());

        if ($delta <= self::TOLERANCE_CENTS) {
            $this->recordMatch($shipment);
            return;
        }

        $this->recordMismatch($shipment, $incumbentRate, $challengerRate, $delta);
    }

    private function recordMatch(Shipment $shipment): void
    {
        logger()->info('shadow.shipping_rate.match', [
            'shipment_id' => $shipment->id,
        ]);
    }

    private function recordMismatch(
        Shipment $shipment,
        Money $incumbentRate,
        Money $challengerRate,
        int $delta,
    ): void {
        logger()->warning('shadow.shipping_rate.mismatch', [
            'shipment_id'      => $shipment->id,
            'incumbent_cents'  => $incumbentRate->getAmount(),
            'challenger_cents' => $challengerRate->getAmount(),
            'delta_cents'      => $delta,
            'currency'         => $incumbentRate->getCurrency()->getCode(),
        ]);
    }
}
```

Log the inputs too — not just the outputs. When you're debugging a mismatch two weeks later, you need to reconstruct exactly what the challenger received. Log the shipment weight, dimensions, origin, destination, and service level alongside the result delta.

## Observability

Structured logs are the baseline. But watching logs manually doesn't scale. Add counters and alerting.

```php
private function recordMismatch(...): void
{
    logger()->warning('shadow.shipping_rate.mismatch', [...]);

    app(Metrics::class)->increment('shadow.shipping_rate.mismatch', [
        'origin_country'      => $shipment->origin->countryCode,
        'destination_country' => $shipment->destination->countryCode,
    ]);
}
```

If your mismatch rate spikes after a challenger deployment, you want to know immediately — not when someone happens to check a dashboard.

For Slack alerting, fire a notification when a mismatch exceeds a threshold or when the delta is large enough to be a business problem. A one-cent rounding difference is noise; a five-dollar difference on a twenty-dollar shipment is not.

```php
if ($delta > 500) { // > $5.00
    Notification::route('slack', config('shadow.slack_webhook'))
        ->notify(new LargeShadowMismatch($shipment, $incumbentRate, $challengerRate));
}
```

The goal of observability here is twofold: catch bugs in the challenger, and build the confidence metrics that tell you when you're ready to cut over.

A useful dashboard has three numbers: total comparisons, match rate (last 7 days), and p99 delta. When match rate is above your threshold (95%? 99%? depends on the domain) and the p99 delta is within tolerance, you're ready.

## The critical pitfall: side effects

Shadow code must not have side effects.

This sounds obvious but it's easy to get wrong. If the challenger calls a third-party API that charges per request, you're paying for every shadow call. If the challenger sends a webhook or writes an audit log, external systems will see duplicate events. If the challenger calls an email provider — even in a "dry run" mode — you may still trigger billing or rate limits.

Before you wire up a challenger, audit every external call it makes and ask: what happens if this runs twice for every real request?

For API calls, consider wrapping the challenger in a fake HTTP client during shadow mode, recording the requests it would make rather than making them. For writes, use a null adapter or a fake repository. The challenger's calculation logic gets exercised on real data; its I/O gets stubbed.

```php
final class UpsRateCalculator implements ShippingRateCalculator
{
    public function __construct(
        private readonly UpsApiClient $client,
    ) {}

    public function calculate(Shipment $shipment): Money
    {
        $response = $this->client->getRates($shipment->toUpsRequest());
        return Money::ofMinor($response->lowestRateCents, 'USD');
    }
}
```

If `UpsApiClient` is bound to a recording fake during shadow phase, you get real coverage of the calculation without real external calls. Switch to the live client for phase 2 once you've validated the response parsing logic.

## Cleaning up

Shadow mode is temporary by design. It has a cost: the challenger runs on every request, you're paying for double the computation and possibly double the API calls, and the comparator adds latency.

Set a deadline when you start. "We'll be in shadow mode for four weeks, then cut over or abandon the challenger." Write it in the ticket. Put it in the PR description.

When you cut over:

1. Remove the `ShadowShippingRateCalculator` decorator
2. Update the service provider binding to point directly to the challenger (now the new incumbent)
3. Delete the old incumbent implementation
4. Delete the `ShadowComparator`
5. Remove the shadow-specific log channels and metrics

Leaving shadow code in place indefinitely is the failure mode. It becomes invisible — nobody knows it's still running, the comparison results stop being reviewed, and you have dead code burning API quota. Delete it.

---

## When shadow mode is the right tool

Shadow mode fits best when:

- You're replacing an incumbent service, not adding a net-new capability
- The calculation is deterministic enough to compare (same inputs should produce equivalent outputs)
- You have structured logging and can act on discrepancies
- The timeline allows for an observation period before cut-over

It's less useful when the two services are intentionally non-equivalent — when the challenger is supposed to return different results by design. In that case you don't have a baseline to compare against, and you need a different validation strategy.

For service integrations where correctness matters and you can't afford to find out about bugs in production after you've already cut over — shadow mode is the safest path between here and there.

Calculate. Compare. Notify. Never persist until you're sure.
