`astrotomic/laravel-translatable` has been around since before return type declarations were a thing. It predates PHP 8. It predates named arguments. It uses traits extensively, has magic getter methods, and its `Translation` model relationships are left intentionally generic so package consumers can wire in their own models. Three million downloads. Hundreds of projects depending on it not changing in unexpected ways.

I wanted PHPStan level 6. I wanted a green CI run with no baseline file. Here's what it actually took.

## Why Not Just Use `--generate-baseline`

The baseline is a trap — especially for package authors.

When you generate a baseline, you're telling PHPStan "I know about these errors; ignore them forever." That sounds pragmatic until you realise what you've done: you've frozen the current state of every real bug and every false positive into a file that nobody reviews, that grows silently, and that makes your CI green regardless of whether you've fixed anything or made things worse.

For an application codebase with a tight deadline, the baseline buys you time. For an open source package, it signals to every contributor that "errors are fine here." That's not the culture I want.

The goal was: zero errors, no suppressions, no baseline. Either PHPStan is wrong (and we teach it the right thing) or we are wrong (and we fix it).

## Starting Point: Find the Highest Clean Level

The first thing I did was not run at level 6. I ran at level 0, then 1, then worked up.

```bash
composer require --dev phpstan/phpstan larastan/larastan
```

```neon
# phpstan.neon
includes:
    - vendor/larastan/larastan/extension.neon

parameters:
    level: 0
    paths:
        - src
```

Level 0 was clean. Level 1 had a handful of issues — mostly missing `@return` types on internal helpers. Fixed. Level 2 introduced the first real decision point: the `Translation` model stubs. More on that shortly.

I kept raising the level until I hit something I needed to think about rather than something I could just fix. That turned out to be level 6, specifically around trait method analysis and generic relation types.

Eight hundred errors at level 6, cold. Most of them were in three categories.

## The Trait Problem: Why PHPStan Thinks Your Methods Are Unused

`HasTranslations` is the central trait in the package. It adds methods like `getTranslation()`, `setTranslation()`, `hasTranslation()`, and `forgetAllTranslations()` to any Eloquent model that uses it. The trait itself is about 400 lines.

PHPStan reported dozens of "Method is never used" errors on trait methods. Not because the methods aren't used — they're used constantly, by consumer models in a thousand different applications — but because PHPStan only sees the package source tree. It doesn't see consumers. If nothing inside the package calls `forgetAllTranslations()`, PHPStan reports it as dead code.

The naive fix is `@internal` or an `@phpstan-ignore-next-line`. Both are wrong.

The real fix is understanding why PHPStan reports this at all. Trait methods flagged as unused typically fall into one of two categories:

1. Methods that are part of the public API, intended for consumers — PHPStan can't see those consumers
2. Methods that genuinely are dead code and should be removed

For the first category, the answer is an interface. If the trait's public methods are declared on a contract that the model implements, PHPStan has a reference point — the interface is the "used" declaration, and the trait fulfils it.

I extracted a `HasTranslationsInterface` from the trait's public methods:

```php
interface HasTranslationsInterface
{
    public function getTranslation(string $key, ?string $locale = null, bool $useFallback = true): mixed;
    public function setTranslation(string $key, string $locale, mixed $value): static;
    public function hasTranslation(string $key, ?string $locale = null): bool;
    public function forgetTranslation(string $key, string $locale): static;
    public function forgetAllTranslations(string $locale): static;
    public function translatedAttributes(): array;
}
```

Then I made the trait declare that it implements the interface — without the model needing to do so explicitly — by using the interface as a contract annotation:

```php
/**
 * @implements HasTranslationsInterface
 */
trait HasTranslations
{
    // ...
}
```

PHPStan now understands that the trait's public methods are fulfilling a contract. "Unused" errors: gone.

For the second category — genuinely dead internal helper methods — I removed them. The trait had accumulated several `protected` methods that nothing called anymore. Those were real bugs that PHPStan found correctly.

## Model Property Stubs

The `Translation` model is a base class that package consumers extend. They add their own fillable columns — `name`, `description`, `content`, whatever their domain needs. From PHPStan's perspective, accessing `$translation->name` is accessing an undefined property. It has no idea what columns your consumers added.

There are two approaches here.

The first approach is `@property` docblocks. You annotate the base model with the properties you know will exist:

```php
/**
 * @property string $locale
 * @property int $translatable_id
 * @property string $translatable_type
 */
class Translation extends Model
{
    // ...
}
```

This covers the package's own columns. It doesn't help with consumer-defined columns, but that's correct — PHPStan should complain if you try to access `$translation->name` inside the package itself, because the package doesn't define that column.

The second approach is PHPStan stubs — PHP files that declare the class shape without runtime behaviour. Stubs are useful when you want to describe something that doesn't exist in the codebase at all (like a dynamically generated class) or when you're fighting a particularly stubborn false positive.

For `laravel-translatable`, `@property` docblocks on the base model were the right call. They're visible in IDE autocompletion, they're accurate, and they don't require a separate stubs directory that contributors need to know about.

```neon
# phpstan.neon
parameters:
    level: 6
    paths:
        - src
    ignoreErrors: []
```

No stubs file needed. The docblocks were enough.

## Relation Generics: Making `HasMany` Tell the Truth

This was the most interesting part.

The `Translation` relationship on the `Translatable` model looked like this:

```php
public function translations(): HasMany
{
    return $this->hasMany(
        config('translatable.translation_model'),
        'translatable_id'
    );
}
```

PHPStan (via Larastan) knows that `HasMany` is generic: `HasMany<TRelatedModel, TDeclaringModel>`. Without the type parameters, any code that calls `->translations()->get()` gets back `Collection<int, Model>` — not `Collection<int, Translation>`. That means callers lose type information downstream, and PHPStan reports the omission.

The fix requires specifying the generic parameter in the return type:

```php
/** @return HasMany<Translation, static> */
public function translations(): HasMany
{
    return $this->hasMany(
        config('translatable.translation_model'),
        'translatable_id'
    );
}
```

There's a subtlety here specific to packages: `config('translatable.translation_model')` resolves at runtime to whatever class the consumer has configured. At static analysis time, PHPStan doesn't evaluate config values. So we're lying slightly — we're telling PHPStan the relation is always `Translation`, even though at runtime it might be `App\Models\BookTranslation`.

This is the right lie. The base `Translation` class is the contract. Consumer subclasses should extend it, so `Collection<int, Translation>` is a valid base type for anything the consumer returns. If they extend properly, the type is accurate. If they don't extend and just configure a random model, that's their problem — the package can't protect against that with static analysis anyway.

The bigger win is for package-internal code. Anywhere inside the package that iterates `->translations()`, PHPStan now knows it's getting `Translation` instances, not generic `Model` instances. That eliminated a second wave of errors around accessing translation properties.

## Magic Methods: `getTranslation()` and PHPStan

The package has a `__get()` override that intercepts property access on translated attributes and routes them through `getTranslation()`. PHPStan doesn't follow `__get()` — it has no idea what properties this makes available.

This is where `@property` annotations on the trait itself become important. Not for the trait's own properties (the trait has none), but as documentation to PHPStan that these magic accessors exist.

The problem is you can't annotate a trait with `@property foo` because you don't know what `foo` is — that's the whole point of a translatable package. The consumer decides the columns.

The solution is to document the access pattern without listing specific properties. Larastan provides a `modelDirectories` configuration that helps with Eloquent magic, but for custom `__get()` behaviour in a trait, you need a different approach.

I added `@phpstan-type` declarations for the method signatures that PHPStan was flagging as unreachable return types:

```php
/**
 * @phpstan-return ($locale is null ? string|null : string|null)
 */
public function getTranslation(string $key, ?string $locale = null, bool $useFallback = true): mixed
{
    // ...
}
```

The return type is `mixed` — honest, because the package doesn't know what type the column holds — but PHPStan stops complaining about downstream code that treats the return value as nullable string, because `mixed` is assignable to anything.

This was one of the few places where the answer was "be more honest with the type, not more specific."

## Getting From 800 to 0

The actual progression looked like this:

| Fix                                                         | Errors Eliminated |
| ----------------------------------------------------------- | ----------------- |
| Added `HasTranslationsInterface`                            | ~280              |
| Added `@property` to `Translation`                          | ~190              |
| Added relation generics                                     | ~160              |
| Fixed genuine type errors (wrong return types, null safety) | ~120              |
| Removed dead internal methods                               | ~40               |
| Fixed `@phpstan-return` on magic methods                    | ~10               |

The 120 genuine type errors were the most valuable part. These were real bugs: methods that claimed to return `string` but could return `null`, array shapes that were wrong, a helper that was passing the wrong argument type to an Eloquent scope. PHPStan found actual problems, not noise.

That's the argument against baseline files, stated concretely: those 120 errors would have been suppressed. The baseline would have frozen them in place and they'd still be there, silently wrong, waiting to cause a production issue in someone's application.

## CI Setup

The final `phpstan.neon`:

```neon
includes:
    - vendor/larastan/larastan/extension.neon

parameters:
    level: 6
    paths:
        - src
    checkMissingIterableValueType: false
    reportUnmatchedIgnoredErrors: true
```

`checkMissingIterableValueType: false` is a deliberate relaxation. The package uses `array` as a return type in a lot of places where specifying the full shape would require rewriting the docblocks extensively and wouldn't add value proportional to the effort. This is a trade-off I made consciously — it's not a baseline, it's a config switch that applies uniformly.

`reportUnmatchedIgnoredErrors: true` is a safety net. If I later fix a genuine error that I had suppressed with a `@phpstan-ignore-next-line`, this setting ensures the now-redundant ignore comment becomes an error itself. Nothing stays suppressed silently.

In `composer.json`:

```json
{
    "scripts": {
        "phpstan": "phpstan analyse --memory-limit=256M"
    }
}
```

And the CI job, alongside the existing test matrix:

```yaml
phpstan:
    runs-on: ubuntu-latest
    steps:
        - uses: actions/checkout@v4
        - uses: shivammathur/setup-php@v2
          with:
              php-version: '8.2'
              coverage: none
        - run: composer install --no-interaction --prefer-dist
        - run: composer phpstan
```

No matrix — PHPStan runs once, on the newest PHP version. Running it per PHP version adds CI time without adding signal, because PHPStan's analysis is driven by the types in the code, not the runtime behaviour of a specific PHP version.

## What I'd Do Differently

Run PHPStan from the very beginning on new packages. The cost of retrofitting static analysis to 5 years of accumulated assumptions is significant. Not because the errors are hard to fix — most of them took 30 seconds — but because you have to understand whether each error is real or a tool limitation, and that requires context about design decisions that aren't documented anywhere.

The other thing I'd do differently: add the `HasTranslationsInterface` earlier. The interface forced me to think explicitly about what the trait's contract actually is. That clarity would have been useful years ago, not just as an input to PHPStan but as documentation for contributors.

## The Result

A 5-year-old package, 3 million downloads, PHPStan level 6, zero errors, no baseline file.

Every future PR runs through the same analysis. A contributor who introduces a return type inconsistency or a nullable property access gets a failing CI check, not a code review comment that might get missed. The type information in the relation generics propagates to anyone using the package — their IDE and their own PHPStan runs get accurate types where they previously got `Model`.

Static analysis on mature packages isn't about rewriting the package. It's about making explicit what the package always implicitly promised.
