I tried every todo app. Todoist. Linear personal. Notion databases. Apple Reminders with smart lists. I kept coming back to a plain markdown file. Not because markdown is better, but because the file is mine — I can script it, version it, load it with context from other tools, and open it without leaving my editor.

This is a description of what I actually use. It has rough edges. It's not a product. But it works better than anything I've bought.

## The file

Every morning, a file gets created at a fixed path:

```
~/.cursor/projects/empty-window/TODAY-2026-04-23.md
```

The name is predictable. Any script, any agent, any alias I write knows where today's file lives. That predictability is load-bearing — it means I can build on top of it without configuration.

The structure looks like this:

```markdown
# Today — Thursday, 23 April 2026

_Last synced: ~09:15 CEST_

---

## 🔴 High Priority

- [ ] **PROJ-1042** — Payout not adjusted after alteration — still open, no movement since Mon — [Linear](https://linear.app/...)
- [ ] **PROJ-991** — Shadow tax MR !1201 ready for review — push toward merge — [Linear](https://linear.app/...) / [MR](https://gitlab.com/...)

### From yesterday carry-forward

- [ ] **Cancellation bug** — duplicate refunds — check if Alex resolved — [Linear](https://linear.app/...) / [Order](https://...)
- [ ] **17 orders at risk** — first due May 8 — [Redash query](https://...)

---

## 🟡 Reviews Needed

**Alex**

- [ ] [service!3104](https://gitlab.com/...) — Increase daily cap to 50 (today)

**Jordan**

- [ ] [service!3042](https://gitlab.com/...) — Refund improvements ← "ready to deploy", been waiting

---

## 🟠 Medium / Follow-up

- [ ] **PROJ-1108** — Guest portal fails after payment capture — still triage — [Linear](https://linear.app/...)
- [ ] **Saved: Alteration tax preview spike** — occupancy taxes jump on LOS-unchanged alteration — [Thread](https://...)

---

## 🟢 Open MRs — Need Reviewers

- [ ] [service!1274](https://gitlab.com/...) — sync_orders one-time op (no reviewers yet)

---

## 🗑️ Housekeeping

- [ ] Saved items cleanup — Alex's review list (Apr 9), payment terms thread (Apr 15)

---

## ✅ Done Today

- [x] Reviewed 60 FS reservations (Apr 13–23) — signed off on scaling to 50 ✓
- [x] [service!1307](https://gitlab.com/...) — add `getRefundablePaymentSplits()` — opened ✓
- [x] **Geekbot standup** — posted ✓ [link](https://...)

---

## ✅ Done Today — Not in Original Plan

- [x] **PROJ-600** — done by Alex while I was investigating ✓
- [x] **PROJ-537** — handed off to Alex, no longer my concern ✓
```

A few things to notice:

**The sections are stable.** High priority, reviews needed, medium, open MRs, housekeeping, done today. Every day. I don't reorganise them. That stability means I can find things without reading the whole file.

**Every item has its links inline.** Linear, Slack thread, GitLab MR, Redash query — whatever gives context — right there on the line. I never open the file and then have to go hunting for the ticket number.

**The carry-forward section is explicit.** Anything that didn't get done yesterday and still matters gets seeded into today's file under "From yesterday carry-forward." That section is the antidote to todo-app amnesia, where old items slowly drift to page 3 until you forget they exist.

**"Done Today — Not in Original Plan" is a first-class section.** More on this below.

## How it gets generated

I don't write the file by hand. Every morning I say "daily briefing" in Cursor and an agent does the following, roughly:

```bash
# Pseudocode — not actual shell, but close to what happens

# 1. Check if today's file exists
today_file="TODAY-$(date +%Y-%m-%d).md"
if [ -f "$today_file" ]; then
  base=$(cat "$today_file")   # update in place
else
  yesterday_file="TODAY-$(date -d yesterday +%Y-%m-%d).md"
  [ -f "$yesterday_file" ] && seed=$(grep '^\- \[ \]' "$yesterday_file")
fi

# 2. Pull context in parallel
slack_saved=$(slack search "is:saved")
slack_mentions=$(slack search "to:@me after:yesterday")
linear_issues=$(linear list --assignee=me --limit=50 --order=updatedAt)
gitlab_mrs=$(glab api /merge_requests?state=opened&scope=all)

# 3. Triage and write sections
# High priority = Linear priority ≤ 2, pipeline red, DMs needing reply
# Reviews = MRs assigned to me that I haven't approved
# Medium = everything else open
# Open MRs = my own MRs with no reviewers

# 4. Upsert the file — preserve [x] items, add new [ ] items
write_daily_file "$today_file" "$triage_output"
```

The real implementation is a Cursor agent skill. It fires all the data-gathering steps in parallel, runs triage logic, and upserts the file — preserving any checkboxes I've already ticked. If I've marked something done at 11am, the 3pm refresh doesn't uncheck it.

The upsert logic is the part that took the longest to get right. The naive version regenerates the whole file and wipes your state. The correct version diffs by item identifier — Linear ticket number, MR number, whatever's bold at the start of the line — and only adds items that aren't already present.

## What I actually do with it

I open the file once in the morning after the briefing runs. I read it top to bottom, which takes about two minutes. I delete items that are irrelevant — things that resolved themselves overnight, things I'm consciously deprioritising. I reorder within sections if the order matters. Sometimes I add a note inline.

Then I mostly leave it alone and just tick boxes as the day goes on. At the end of the day, if I want a summary, I run another agent pass that produces standup bullets from the done sections.

The human curation step matters. The automation can't know that the "17 orders at risk" item from last week is actually now handled by someone else but hasn't been closed in Linear yet. It can't know that an MR listed under "reviews needed" is one I'm intentionally skipping because the author is rewriting the approach. You have to read it and make those calls. The file is a draft. You're the editor.

## Standup as a by-product

My team uses Geekbot. Every morning it asks three questions: what did you do yesterday, what will you do today, is anything blocking you.

The agent that generates the daily file also generates prefilled answers to those questions, directly from the file content:

- **Yesterday:** the items in "Done Today" from yesterday's file
- **Today:** the top three from High Priority
- **Blocking:** anything flagged as blocked in Linear or with a "blocked" label on GitLab

I paste, edit lightly, and post. The standup takes 90 seconds instead of 10 minutes of archaeology through my memory and Slack history.

## Why "Done But Not in Original Plan" is a real section

Software engineering days almost never go according to plan. You open Slack and there's a production incident. A colleague asks you to look at something urgently. You notice a bug while reviewing something else and fix it on the spot.

Those things should be recorded. Not because they count double — because they happened, and if I'm asked "what did you do today?" I shouldn't have to reconstruct them from memory or Slack search. They're also useful for understanding where your time actually went versus where you planned it to go.

Keeping them in a separate section from planned work also means I can see at a glance whether a day was mostly execution or mostly firefighting. That's useful signal over time, even if I'm not doing anything formal with it.

## Version control for your work log

The files live in a directory that's a git repo. Every few days I commit. The history is a searchable, durable work log.

```bash
git log --oneline --after="2026-03-01" --before="2026-04-01"
# a3f8c2d TODAY-2026-03-31.md
# b7d1e4a TODAY-2026-03-28.md
# ...
```

If someone asks "what were you working on in March?" I can answer without guessing. If I need to reconstruct a timeline for a postmortem, the files have timestamps, links, and context. It's not a formal work journal — the format is too terse for that — but it's a recoverable record of what I touched and what state things were in on any given day.

This is also where the predictable file naming pays off: `git log -- 'TODAY-*.md'` gives you the full history of every daily file.

## What doesn't work well

The automation is only as good as the data sources. If a Linear issue hasn't been updated in a week and is still listed as "To Do," it keeps appearing in my file. I have to manually verify whether it's actually stale or just poorly maintained. That friction is real.

Slack search results are also inconsistent. Sometimes the "saved items" query misses things. Sometimes keyword searches surface threads that are tangentially related but not actually relevant. The agent is doing its best, but it's triaging noise, not eliminating it.

The upsert matching can also go wrong when item identifiers change — if an MR gets renumbered (rare but it happens) or a Linear issue gets merged, the old item sticks around as a ghost. You notice it when you read the file, which is why reading it every morning matters.

None of this makes me want to go back to a todo app. Apps have these problems too — they just hide them under a nicer UI.

## The actual point

The file isn't better than a todo app because it's markdown. It's better because it's a file — a dumb, scriptable, version-controllable artifact that any tool can read and write. My editor can open it. My shell scripts can grep it. My AI agent can update it. I can commit it. I can search it with `rg`. None of that requires a vendor, an API key, or a subscription.

The structure is arbitrary and you should invent your own. What matters is that it's stable, that you read it every day, and that the automation serves you rather than the other way around. If you're spending more than a few seconds per day maintaining the file's structure, something is wrong.

Mine took about two weeks to stabilise into something I stopped thinking about. Now it just runs.
