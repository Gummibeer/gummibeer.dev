> "Do not remove a fence until you know why it was put up."
> — G.K. Chesterton

You're building a new component that sits next to an existing one. You read the sibling's template and notice it guards against `null` before rendering a label. Your data is loaded from the same source. You know it can't be null here. The guard looks like noise. You leave it out.

Three weeks later, a refactor introduces a second code path that loads the same data with different defaults. That path doesn't guarantee the field. The label crashes in production. You grep for similar guards and find your component is the only one without one.

Chesterton was right.

## What the Fence Principle Says

Chesterton's Fence is a rule about the burden of proof. You cannot responsibly remove something until you can explain its original purpose. If you can't explain why it was put there, you don't yet have enough information to know whether removing it is safe.

Applied to code: before you delete a null check, an empty-array guard, or a conditional branch that "can't possibly trigger," your job is to establish why it was written.

There are exactly three answers:

1. **Defensive coding.** The author didn't trust the upstream type contract and added the guard as a precaution. It may never have triggered, but it was always protecting against a class of mistake, not a specific known case.
2. **Historical regression fix.** Something broke. A null did arrive. The guard was the fix. The commit message probably doesn't say why.
3. **Genuine dead code.** The contract changed, the guard predates that change, and it truly cannot fire anymore.

Only the third case is safe to remove. The first two are doing real work, invisibly.

## The "Redundant" Guard in a Template

Here's the situation concretely. You have a component that displays a booking summary:

```html
<!-- BookingSummary.vue -->
<template>
    <div v-if="booking">
        <p>{{ booking.guestName }}</p>
        <p v-if="booking.property">{{ booking.property.name }}</p>
    </div>
</template>
```

The inner `v-if="booking.property"` looks suspicious. `booking` comes from a Pinia store that always loads property data eagerly. You can trace the fetch — it's always populated. So you build the adjacent `BookingHints` component without the guard:

```html
<!-- BookingHints.vue — your new component -->
<template>
    <div v-if="booking">
        <span class="hint">{{ booking.property.timezone }}</span>
    </div>
</template>
```

Six weeks later someone adds a "quick booking" flow that creates a skeleton record and pushes it to the same store before the property is resolved. `BookingHints` throws. `BookingSummary` handles it silently.

## How to Establish Which Case You Have

Before touching a guard, do three things:

**Read the git history for that line.** `git log -S 'v-if="booking.property"' -- BookingSummary.vue` tells you when it was added. The surrounding commit context often reveals whether it was a proactive decision or a regression fix. A message like "fix null property crash on shared links" is not ambiguous.

**Check whether the type guarantees the field.** If the store's type says `property: Property | null`, the guard is encoding the type system. If it says `property: Property`, ask why the guard is stricter than the type — one of them is wrong, and it's often the type.

**Search for all callers, not just the happy path.** If the data flows in from one place today, grep for everywhere that thing is populated. You're looking for paths that don't pass through the primary loader. `Ctrl+Shift+F` on the store mutation or the API call, not the component.

If you can't get a confident answer from all three, the fence stays.

## Safe Removal: Write the Test First

If you've done the above and you're convinced the guard is genuinely dead, remove it — but write the test before you delete the line. The test should produce the null case explicitly and assert that the component renders without error. If you can't write that test because "there's no way to produce null," that's your proof it's safe. If writing the test turns out to be awkward because null can arrive from a direction you hadn't considered, you just saved yourself a production incident.

Then delete the guard, run the test, commit both changes together. The test is the artifact that documents why this removal was deliberate.

## The Consistency Argument

Even when removal is technically safe, there's a second question worth asking: should your new component match the defensive style of its siblings?

Consistency in template guards isn't just aesthetic. It creates a predictable pattern that future readers can trust. If every component in a section guards against a nullable property, a developer reading `BookingHints` months later will expect that guard to be there. Its absence signals intent — either that it was considered and dismissed, or that it was overlooked.

If the existing guards are clearly defensive in a well-understood domain where null genuinely can't arrive, you might reasonably omit the guard in your new component and treat it as cleanup-to-be-done. But if you're uncertain, match the siblings. Consistency buys you safety for free.

## The Actual Cost of Leaving It In

A null check that never fires costs you nothing at runtime and one line in the template. A null check that you removed because you were confident it couldn't fire costs you a production bug, a debug session, a regression, and the trust of whoever was on call.

The fence is cheap. The gap in the fence is not.
