A policy method calls `$order->payments`. The order has 8,000 payments accumulated over five years. Laravel hydrates every single one of them into memory, builds the collection, hands it back to your policy — which then calls `->isNotEmpty()` and discards the rest. Your server sweated to produce a boolean.

This is not the N+1 problem. It's the opposite: one query that returns a dataset you never needed.

## The N+1 Problem vs the "1 Enormous Query" Problem

Most Eloquent performance advice focuses on N+1: you loop through 100 orders and each one fires a separate query to load its latest payment. Fix it with `with('payments')` and you're done.

But eager loading doesn't solve the problem when the relationship itself is huge. If you `with('payments')` on an order that has 8,000 rows, you've just traded 1 small query for 1 enormous one. You loaded 8,000 Payment models into memory to answer a question that SQL could answer in microseconds.

The two failure modes require different fixes.

## The Policy That Loads Everything

Here's a real pattern that causes problems:

```php
// OrderPolicy.php
public function viewInvoice(User $user, Order $order): bool
{
    return $user->id === $order->user_id
        && $order->payments->isNotEmpty();
}
```

The `$order->payments` call hits the database and hydrates every payment record on that order. If the policy is called from a middleware, a gate check, or a Blade `@can` directive, this happens on every request for that route — even if the relationship was already loaded for other reasons, Eloquent may re-query if the constraint differs.

The fix is to never load what you only need to check existence for:

```php
public function viewInvoice(User $user, Order $order): bool
{
    return $user->id === $order->user_id
        && $order->payments()->exists();
}
```

`exists()` emits `SELECT EXISTS(SELECT 1 FROM payments WHERE order_id = ? LIMIT 1)`. One row, no hydration, no collection. The parentheses matter — `$order->payments()` returns a query builder, `$order->payments` returns the loaded collection.

## `whereHas` vs Loading and Filtering in PHP

The same principle applies when you're filtering a list of parent models. Say you want all orders that have a failed payment:

```php
// Loads all payments for every order, then filters in PHP
$orders = Order::with('payments')
    ->get()
    ->filter(fn (Order $order) => $order->payments->contains(
        fn (Payment $payment) => $payment->status === 'failed'
    ));
```

This is a memory and time disaster at any real scale. Use `whereHas` to push the filter to the database:

```php
$orders = Order::whereHas('payments', function (Builder $query): void {
    $query->where('status', 'failed');
})->get();
```

If you also need the payments themselves, combine it with a scoped eager load:

```php
$orders = Order::whereHas('payments', function (Builder $query): void {
    $query->where('status', 'failed');
})->with(['payments' => function (Builder $query): void {
    $query->where('status', 'failed');
}])->get();
```

Now the existence check and the data load use the same constraint. You're not loading 8,000 records to display the 3 that match.

## `withCount` and `withAggregate` for Summary Data

A lot of UI logic only needs numbers, not records. "This order has 12 payments." "The total paid is 1,450.00." "There are 3 failed attempts."

For counts:

```php
$orders = Order::withCount('payments')->get();

// $order->payments_count is now an int, no collection loaded
```

For aggregates — totals, averages, max/min:

```php
$orders = Order::withAggregate('payments', 'amount', 'sum')->get();

// $order->payments_sum_amount holds the SUM
```

You can stack multiple aggregates and filter them:

```php
$orders = Order::query()
    ->withCount(['payments', 'payments as failed_payments_count' => function (Builder $query): void {
        $query->where('status', 'failed');
    }])
    ->withAggregate('payments as payments_sum_amount', 'amount', 'sum')
    ->get();
```

This is one query. No collections. The Blade template can render `{{ $order->payments_count }}` and `{{ $order->failed_payments_count }}` without ever loading a Payment model.

## Scoped Relations: Stop Exposing the Full Graph

The relationship `$order->payments` is an unbounded access point. Any code that touches it gets everything. Instead, define scoped relationships for the cases you actually need:

```php
// Order.php
public function payments(): HasMany
{
    return $this->hasMany(Payment::class);
}

public function recentPayments(): HasMany
{
    return $this->hasMany(Payment::class)
        ->where('created_at', '>=', now()->subDays(90))
        ->orderByDesc('created_at');
}

public function failedPayments(): HasMany
{
    return $this->hasMany(Payment::class)
        ->where('status', 'failed');
}

public function latestPayment(): HasOne
{
    return $this->hasOne(Payment::class)->latestOfMany();
}
```

Now `$order->recentPayments` only pulls 90 days of data. `$order->latestPayment` pulls one row. The full `$order->payments` is still there for when you genuinely need it — like generating a complete payment history report — but that's an explicit choice, not a default.

The same pattern applies everywhere:

```php
// User.php
public function activityLogs(): HasMany
{
    return $this->hasMany(ActivityLog::class);
}

public function recentActivityLogs(): HasMany
{
    return $this->hasMany(ActivityLog::class)
        ->where('created_at', '>=', now()->subDays(30))
        ->orderByDesc('created_at')
        ->limit(50);
}
```

```php
// Product.php
public function priceHistories(): HasMany
{
    return $this->hasMany(PriceHistory::class);
}

public function currentPrice(): HasOne
{
    return $this->hasOne(PriceHistory::class)
        ->ofMany('effective_at', 'max')
        ->where('effective_at', '<=', now());
}
```

## Authorization Patterns That Don't Hit the Database

Some authorization checks can be answered without a query at all. Before reaching for `exists()`, ask whether the answer is already on the model you have.

**Check attributes you already have:**

```php
public function viewInvoice(User $user, Order $order): bool
{
    return $user->id === $order->user_id
        && $order->status !== 'draft';
}
```

If the order's `status` column already tells you whether it's billable, there's no reason to count payments.

**Cached counts on the parent:**

Add a `payments_count` column to your `orders` table and keep it synchronized via a database trigger or an Eloquent observer:

```php
// PaymentObserver.php
public function created(Payment $payment): void
{
    Order::where('id', $payment->order_id)
        ->increment('payments_count');
}

public function deleted(Payment $payment): void
{
    Order::where('id', $payment->order_id)
        ->decrement('payments_count');
}
```

Then your policy becomes:

```php
public function viewInvoice(User $user, Order $order): bool
{
    return $user->id === $order->user_id
        && $order->payments_count > 0;
}
```

Zero queries for the check. The count is accurate because observers maintain it transactionally. This pattern makes sense when the check is on a hot path — every page load, every API response, every middleware gate.

The tradeoff: denormalized data requires discipline to keep consistent, and bulk operations (mass inserts, direct SQL) will bypass observers. Weigh that against the query savings on your specific traffic pattern.

## Capped Visibility and Pagination

When you do need to show records — not just counts — cap what you expose:

```php
// In a controller showing payment history
public function payments(Order $order): View
{
    $payments = $order->payments()
        ->orderByDesc('created_at')
        ->paginate(25);

    return view('orders.payments', compact('payments'));
}
```

Never `->get()` an unbounded relationship for display. Paginate it. If the UI needs a "total" badge, use `withCount` on the parent, not `$payments->total()` from a full collection.

For API responses that list orders with payment summaries, keep aggregates on the query:

```php
$orders = Order::query()
    ->where('user_id', $user->id)
    ->withCount('payments')
    ->withAggregate('payments as payments_sum_amount', 'amount', 'sum')
    ->withAggregate('payments as payments_max_created_at', 'created_at', 'max')
    ->orderByDesc('created_at')
    ->paginate(20);
```

The API response includes payment summaries without loading a single Payment model. The client gets what it needs; your server doesn't sweat.

## The Rule

Every time you access a relationship, ask: do I need the records, or do I need a fact about the records?

If you need a fact — does it exist, how many, what's the total — use the database to compute it. `exists()`, `withCount()`, `withAggregate()`, a cached column. Let SQL do what SQL is built for.

If you need records, scope the query. Define scoped relationships, use `whereHas` with matching eager loads, paginate the results. Never load the full graph when a slice is sufficient.

The full `$order->payments` relationship has its place — generating a complete audit trail, running a reconciliation job, building an export. But those are deliberate, batched operations, not hot-path web requests. Keep them separate, and your web requests will stay fast.
