The exception you catch is often not the exception you need.

A database driver throws a low-level exception. Laravel wraps it in a database exception. An application boundary wraps that again to add context. By the time the failure reaches your retry policy, the outer exception may say almost nothing about the condition that should decide whether the operation is safe to retry.

The usual response is one of three checks:

```php
if ($exception instanceof UniqueConstraintViolationException) {
    // retry
}
```

```php
if ($exception->getCode() === '23000') {
    // retry
}
```

```php
if ($exception->getPrevious() instanceof UniqueConstraintViolationException) {
    // retry
}
```

All three can work. None is a good general answer to wrapped exceptions.

The first checks only the outer wrapper. The second couples application policy to a raw database code that can be broad, driver-specific, or hidden on an inner exception. The third assumes the useful exception is exactly one wrapper deep.

What I wanted instead was an API that states the real question:

```php
(new ExceptionChain($exception))
    ->contains(UniqueConstraintViolationException::class);
```

This post builds that API as a small value object. Internally, it uses a generator wrapped in Laravel's `LazyCollection`. It walks only as far as the query requires, keeps collection mechanics private, supports more than a boolean check, and includes protection against a malformed cyclic chain.

---

## Wrapped exceptions are useful

Exception wrapping is not the problem.

A low-level exception can tell you exactly what a database driver rejected, but it does not know what your application was trying to do. A higher layer can add that context while preserving the original failure:

```php
try {
    $repository->store($event);
} catch (Throwable $exception) {
    throw new RuntimeException(
        message: 'The incoming event could not be stored.',
        previous: $exception,
    );
}
```

The outer exception answers:

> What application operation failed?

The inner exception answers:

> What technical condition caused it?

Both are useful. PHP preserves the relationship through `Throwable::getPrevious()`.

```text
RuntimeException
    previous -> QueryException
        previous -> UniqueConstraintViolationException
            previous -> PDOException
```

The mistake is to catch the outer exception and then pretend wrapping did not happen.

---

## Why an outer `instanceof` check is weak

This check is precise but shallow:

```php
if ($exception instanceof UniqueConstraintViolationException) {
    // ...
}
```

It succeeds only when the exact exception, or one of its subclasses, reaches this catch block without another exception around it.

That is a fragile assumption in a framework application. A package update can add a wrapper. Your own service layer can add context. A queue, HTTP, or command boundary can translate one exception into another while preserving the original as `previous`.

The retry condition has not changed. The position of the relevant exception has.

Retry policy should normally care about the cause, not the number of wrappers between the cause and the catch block.

---

## Why raw SQLSTATE checks are weak

The next common approach checks an exception code:

```php
if ((string) $exception->getCode() === '23000') {
    // Assume this is a duplicate insert.
}
```

This has several problems.

First, the code may be on an inner exception rather than the outer one.

Second, an SQLSTATE class can describe a category, not one exact condition. Treating every integrity-constraint failure as a duplicate-key race can retry foreign-key failures, nullability failures, or other invalid writes that will not become valid after a short sleep.

Third, driver details leak into application policy. Laravel already gives us a semantic exception for a unique-constraint violation. That class communicates intent better than a magic string.

This does not mean exception codes are useless. Sometimes a driver or package exposes no better type. In that case, search the chain with an explicit predicate and inspect both code and any safe structured context:

```php
$match = (new ExceptionChain($exception))->find(
    fn (Throwable $candidate): bool =>
        (string) $candidate->getCode() === '23000',
);
```

The chain abstraction still helps. The predicate is simply less expressive than a dedicated exception type.

---

## Why one `getPrevious()` call is weak

This is better than checking only the outer exception:

```php
if (
    $exception instanceof UniqueConstraintViolationException
    || $exception->getPrevious() instanceof UniqueConstraintViolationException
) {
    // ...
}
```

But it encodes a hidden rule:

> The relevant cause must be zero or one wrapper deep.

There is no reason that must stay true.

You can add more hops:

```php
$previous = $exception->getPrevious();
$previousPrevious = $previous?->getPrevious();
```

That only changes the arbitrary limit from one to two. Once the question is "does any exception in this chain match?", the code should model the chain.

---

## The smallest possible chain walker

You do not need Laravel for this problem. A direct loop is enough:

```php
/**
 * @param class-string<Throwable> $type
 */
function exceptionChainContains(Throwable $exception, string $type): bool
{
    do {
        if ($exception instanceof $type) {
            return true;
        }
    } while ($exception = $exception->getPrevious());

    return false;
}
```

This is fast, small, and correct for a normal acyclic chain.

If all you need in one codebase is one boolean check, stop here. A value object is not automatically better because it has a name and a file.

I wanted a reusable public concept for several call sites:

- retry only when a specific cause exists;
- suppress expected reports while a retry is still in progress;
- return the matching exception for inspection;
- find a cause through a custom predicate;
- keep traversal and cycle handling in one place.

That is enough responsibility to justify a small type.

---

## A generator expresses the chain

A generator separates production from consumption.

```php
/**
 * @return Generator<int, Throwable>
 */
function walkExceptionChain(Throwable $exception): Generator
{
    do {
        yield $exception;
    } while ($exception = $exception->getPrevious());
}
```

Calling `walkExceptionChain()` does not eagerly build an array. It creates a generator. The function runs until the first `yield` only when a consumer asks for the first value.

The consumer then decides when to request another value:

```php
foreach (walkExceptionChain($exception) as $candidate) {
    if ($candidate instanceof UniqueConstraintViolationException) {
        break;
    }
}
```

Once the loop breaks, the generator is not resumed. No later `getPrevious()` call is made.

That property is useful, but it needs an honest description.

The generator does not make the exception chain itself lazy. Every exception in the chain already exists in memory. Each wrapper holds its previous exception. The generator only makes traversal lazy. It avoids visiting, testing, and copying nodes that the query does not need.

---

## What Laravel's LazyCollection adds

Laravel's `LazyCollection` gives a generator the familiar collection query API:

```php
$chain = LazyCollection::make(function () use ($exception): Generator {
    do {
        yield $exception;
    } while ($exception = $exception->getPrevious());
});

$containsUniqueViolation = $chain->contains(
    fn (Throwable $candidate): bool =>
        $candidate instanceof UniqueConstraintViolationException,
);
```

`contains()` asks the generator for one exception at a time. It returns immediately after the first match.

Suppose the matching exception is at position 5 in a chain of 5,000 exceptions:

```text
position 1 -> yield -> no match
position 2 -> yield -> no match
position 3 -> yield -> no match
position 4 -> yield -> no match
position 5 -> yield -> match -> stop
```

Positions 6 through 5,000 still exist as exception objects. The lazy query does not visit them.

The complexity is:

- best case: O(1), when the outer exception matches;
- successful lookup: O(k), where `k` is the match position;
- missing lookup: O(n), because absence requires checking the full chain;
- additional traversal memory: O(k) in the cycle-safe implementation below.

For an ordinary exception chain of two to five nodes, this performance difference is not important. The main benefit is a reusable query model with natural short-circuit behavior. More on that later.

---

## Wrap LazyCollection; do not extend it

It is tempting to write this:

```php
class ExceptionChain extends LazyCollection
{
    public function contains(string $type): bool
    {
        // ...
    }
}
```

I would not.

An exception chain is not a general-purpose collection. Extending `LazyCollection` publishes a large API that has little to do with the domain:

- `chunk()`;
- `zip()`;
- `pad()`;
- `shuffle()`;
- `crossJoin()`;
- many more.

Some operations are harmless but meaningless. Some return a base collection type and lose the domain abstraction. A future framework update can also change method signatures or behavior that your subclass now has to respect.

Inheritance makes a strong claim:

> An `ExceptionChain` is a `LazyCollection`.

Composition makes the narrower and more useful claim:

> An `ExceptionChain` uses lazy collection behavior to answer exception-chain questions.

The collection should be an implementation detail. The public API should contain only operations that make sense for exceptions.

## A copy-pasteable ExceptionChain value object

Here is a generic implementation for a Laravel application:

```php
<?php

declare(strict_types=1);

namespace App\Support\Exceptions;

use Generator;
use Illuminate\Support\LazyCollection;
use Throwable;

final class ExceptionChain
{
    /** @var LazyCollection<int, Throwable> */
    private LazyCollection $exceptions;

    public function __construct(Throwable $exception)
    {
        $this->exceptions = LazyCollection::make(
            static function () use ($exception): Generator {
                $current = $exception;
                $seen = [];

                while ($current !== null) {
                    $objectId = spl_object_id($current);

                    if (isset($seen[$objectId])) {
                        return;
                    }

                    $seen[$objectId] = true;

                    yield $current;

                    $current = $current->getPrevious();
                }
            },
        );
    }

    /**
     * @param class-string<Throwable> $type
     */
    public function contains(string $type): bool
    {
        return $this->first($type) !== null;
    }

    /**
     * @template T of Throwable
     *
     * @param class-string<T> $type
     *
     * @return T|null
     */
    public function first(string $type): ?Throwable
    {
        /** @var T|null $match */
        $match = $this->exceptions->first(
            static fn (Throwable $exception): bool =>
                $exception instanceof $type,
        );

        return $match;
    }

    /**
     * @param callable(Throwable): bool $predicate
     */
    public function find(callable $predicate): ?Throwable
    {
        return $this->exceptions->first($predicate);
    }
}
```

The API is deliberately small:

```php
$chain = new ExceptionChain($exception);

$chain->contains(UniqueConstraintViolationException::class);

$uniqueViolation = $chain->first(
    UniqueConstraintViolationException::class,
);

$databaseFailure = $chain->find(
    fn (Throwable $candidate): bool =>
        str_starts_with((string) $candidate->getCode(), '23'),
);
```

`contains()` is the common yes-or-no query.

`first()` returns the first exception matching a type. Because it uses `instanceof`, asking for a parent class also matches subclasses.

`find()` supports the cases where class identity is not enough.

I prefer `first()` for class-based lookup and `find()` for predicate-based lookup. That distinction is small, but it makes call sites easy to scan.

## Why the LazyCollection source must be a closure

There is a subtle detail in the constructor:

```php
LazyCollection::make(
    static function () use ($exception): Generator {
        // yield exceptions
    },
);
```

The collection receives a generator factory, not one already-created generator instance.

That means each terminal query can create a fresh traversal:

```php
$chain = new ExceptionChain($exception);

$chain->contains(QueryException::class);
$chain->first(UniqueConstraintViolationException::class);
```

Both calls work from the outer exception.

If you store one generator object and partially consume it, later queries can start from its current position or fail because the generator is already closed. A reusable value object should hold the recipe for traversal, not a one-shot iterator.

---

## Cycle hardening

A normal PHP exception chain should be acyclic. Public constructors naturally build a one-way linked list:

```php
$root = new RuntimeException('Root failure');
$outer = new RuntimeException('Outer failure', previous: $root);
```

There is no public API for making `$root->getPrevious()` point back to `$outer`.

Still, exception objects can cross unusual boundaries. Reflection, extensions, custom deserialization, test doubles, or future code can produce a malformed object graph. A generic walker that loops forever during error handling turns one failure into a worker hang.

The implementation tracks visited object IDs:

```php
$objectId = spl_object_id($current);

if (isset($seen[$objectId])) {
    return;
}

$seen[$objectId] = true;
```

That changes additional traversal memory from O(1) to O(k), because the walker remembers each visited node until the query ends. In return, malformed cycles terminate safely.

There are other valid policies:

- throw a dedicated `CyclicExceptionChain` exception;
- stop after a fixed maximum depth;
- expose cycle information to diagnostics;
- omit the guard if every throwable is trusted and minimal overhead matters.

For an error-path helper, stopping safely is a reasonable default. Throwing a second exception while inspecting the first can obscure the original incident.

## The real Laravel race: `firstOrCreate()` is not one atomic statement

Now for the use case that motivated this abstraction.

Imagine an endpoint that receives an event. The request can be delivered twice. To make storage idempotent, the application hashes the body and puts a unique constraint on the fingerprint.

The obvious Eloquent code is:

```php
$incomingEvent = IncomingEvent::query()->firstOrCreate(
    ['fingerprint' => hash('sha256', $request->getContent())],
    ['body' => $request->json()->all()],
);
```

The database constraint is essential. The application-level lookup is not enough because two workers can interleave:

```text
Worker A: SELECT fingerprint -> not found
Worker B: SELECT fingerprint -> not found
Worker A: INSERT -> succeeds
Worker B: INSERT -> unique constraint violation
```

`firstOrCreate()` expresses the intent, but the underlying read and write are not one atomic database statement.

The unique constraint closes the correctness gap. A narrow retry closes the user-visible failure gap.

After Worker A commits, Worker B can repeat `firstOrCreate()`. Its new `SELECT` finds the row and returns it.

Check the implementation in the Laravel version you run before adding an outer retry. Newer Laravel versions use a `createOrFirst()` path that catches a unique-constraint violation and queries for the existing row. Older versions and custom repository methods can still let a wrapped violation escape. Transaction boundaries and index/query mismatches can also prevent the internal recovery from finding the row.

The exception-chain technique is useful when the semantic violation does reach your policy boundary. It is not a reason to duplicate recovery that your exact framework version already performs correctly.

## Retry only the race you understand

Laravel's `retry()` helper accepts a `when` callback. This is where the exception chain becomes useful:

```php
<?php

declare(strict_types=1);

namespace App\Actions;

use App\Models\IncomingEvent;
use App\Support\Exceptions\ExceptionChain;
use Illuminate\Database\UniqueConstraintViolationException;
use Illuminate\Http\Request;
use Throwable;

final class StoreIncomingEvent
{
    public function __invoke(Request $request): IncomingEvent
    {
        try {
            /** @var IncomingEvent $event */
            $event = retry(
                times: 3,
                callback: fn (): IncomingEvent =>
                    IncomingEvent::query()->firstOrCreate(
                        [
                            'fingerprint' => hash(
                                'sha256',
                                $request->getContent(),
                            ),
                        ],
                        [
                            'body' => $request->json()->all(),
                        ],
                    ),
                sleepMilliseconds: 150,
                when: fn (Throwable $exception): bool =>
                    (new ExceptionChain($exception))->contains(
                        UniqueConstraintViolationException::class,
                    ),
            );
        } catch (Throwable $exception) {
            report($exception);

            throw $exception;
        }

        return $event;
    }
}
```

This retry policy says:

> Retry only when some cause in the exception chain is a unique-constraint violation.

It does not retry:

- authentication failures;
- malformed data;
- unavailable dependencies;
- programming errors;
- every database exception;
- every integrity-constraint exception.

That precision matters. A broad retry can increase load during an incident and delay a failure that was never transient.

Three attempts with a short delay are not universal values. They are an operational hypothesis:

> A normal duplicate-insert race should settle within this window.

Measure it. If the winning transaction can take longer, use an appropriate backoff. If contention remains common, reconsider the storage design rather than increasing retries forever.

---

## Report gating: expected during retry, suspicious after exhaustion

A unique violation in the middle of this retry is expected. It is the signal that tells the second worker to wait and read again.

Reporting every intermediate failure creates noise:

```php
when: function (Throwable $exception): bool {
    report($exception);

    return (new ExceptionChain($exception))->contains(
        UniqueConstraintViolationException::class,
    );
},
```

Do not do this unless you explicitly want one report per attempted race.

The `when` callback should classify the failure. The outer catch should report the final outcome:

```php
try {
    return retry(
        times: 3,
        callback: $store,
        sleepMilliseconds: 150,
        when: fn (Throwable $exception): bool =>
            (new ExceptionChain($exception))->contains(
                UniqueConstraintViolationException::class,
            ),
    );
} catch (Throwable $exception) {
    report($exception);

    throw $exception;
}
```

This creates a useful boundary:

- attempt one or two hits the expected race, then succeeds: no error report;
- a non-retryable exception occurs: report immediately after `retry()` throws;
- the unique violation survives all attempts: report after exhaustion.

That last case deserves attention. It can mean the competing transaction did not commit in time, the lookup cannot see the winning row, the unique index covers more than the lookup predicate, or the assumed race model is incomplete.

Do not automatically suppress the final unique violation just because intermediate unique violations are benign.

## Unit tests for the value object

The value object can be tested without booting Laravel's application kernel. It depends on the support package, but not on facades, configuration, HTTP, or a database.

```php
<?php

declare(strict_types=1);

namespace Tests\Unit\Support\Exceptions;

use App\Support\Exceptions\ExceptionChain;
use InvalidArgumentException;
use LogicException;
use PHPUnit\Framework\Assert;
use PHPUnit\Framework\TestCase;
use RuntimeException;
use Throwable;

final class ExceptionChainTest extends TestCase
{
    public function testItMatchesTheOuterException(): void
    {
        $exception = new RuntimeException('Outer');

        Assert::assertTrue(
            (new ExceptionChain($exception))
                ->contains(RuntimeException::class),
        );
    }

    public function testItMatchesADeepException(): void
    {
        $root = new InvalidArgumentException('Root');
        $middle = new LogicException('Middle', previous: $root);
        $outer = new RuntimeException('Outer', previous: $middle);

        Assert::assertTrue(
            (new ExceptionChain($outer))
                ->contains(InvalidArgumentException::class),
        );
    }

    public function testItUsesInstanceofSemantics(): void
    {
        $exception = new InvalidArgumentException('Invalid input');

        Assert::assertTrue(
            (new ExceptionChain($exception))
                ->contains(Throwable::class),
        );
    }

    public function testItReturnsFalseWhenNoTypeMatches(): void
    {
        $root = new LogicException('Root');
        $outer = new RuntimeException('Outer', previous: $root);

        Assert::assertFalse(
            (new ExceptionChain($outer))
                ->contains(InvalidArgumentException::class),
        );
    }

    public function testFirstReturnsTheMatchingException(): void
    {
        $root = new InvalidArgumentException('Root');
        $outer = new RuntimeException('Outer', previous: $root);

        Assert::assertSame(
            $root,
            (new ExceptionChain($outer))
                ->first(InvalidArgumentException::class),
        );
    }

    public function testFindUsesACustomPredicate(): void
    {
        $root = new RuntimeException('Root', code: 23000);
        $outer = new RuntimeException('Outer', previous: $root);

        Assert::assertSame(
            $root,
            (new ExceptionChain($outer))->find(
                fn (Throwable $candidate): bool =>
                    $candidate->getCode() === 23000,
            ),
        );
    }
}
```

These tests define the important public contract:

- the outer exception is part of the chain;
- deep causes are visible;
- class checks use `instanceof`, not exact-class equality;
- missing values return `false` or `null`;
- returned matches preserve object identity;
- predicate lookup short-circuits on the first match.

## Proving short-circuit behavior

A passing "finds the middle exception" test does not prove that traversal stops there. It only proves that a match is eventually returned.

Testing the exact number of `getPrevious()` calls is awkward because PHP owns that method on built-in exception classes. A practical option is to test the lazy primitive directly:

```php
public function testLazyCollectionStopsAtTheFirstMatch(): void
{
    $visited = [];

    $exceptions = LazyCollection::make(
        static function () use (&$visited): Generator {
            foreach (range(1, 100) as $position) {
                $visited[] = $position;

                yield new RuntimeException(
                    message: "Position {$position}",
                    code: $position,
                );
            }
        },
    );

    $match = $exceptions->first(
        fn (Throwable $exception): bool =>
            $exception->getCode() === 5,
    );

    Assert::assertSame(5, $match?->getCode());
    Assert::assertSame([1, 2, 3, 4, 5], $visited);
}
```

This verifies the Laravel behavior on which `ExceptionChain` relies.

Do not build an artificial 5,000-node exception chain to prove a property of `LazyCollection`. That test is slower, harder to read, and still does not observe traversal directly.

## Testing cycle hardening

You cannot create a cyclic standard exception chain through normal constructors. That is good.

If cycle protection is important enough to test, a focused reflection test can simulate corrupted state. Keep it isolated and label why reflection is necessary:

```php
public function testItStopsWhenAChainContainsACycle(): void
{
    $outer = new RuntimeException('Outer');
    $inner = new LogicException('Inner', previous: $outer);

    $previous = new \ReflectionProperty(
        \Exception::class,
        'previous',
    );

    $previous->setValue($outer, $inner);

    $match = (new ExceptionChain($outer))->find(
        fn (Throwable $candidate): bool =>
            $candidate instanceof InvalidArgumentException,
    );

    Assert::assertNull($match);
}
```

Internal exception properties can differ by PHP version. If this fixture is not stable in the versions you support, do not force it into the suite. Test a separately injectable traversal source, use a maximum-depth policy, or rely on a review of the small cycle guard.

The production guard is valuable even when the most direct test requires unsupported object corruption.

## Test the retry policy separately

The value-object tests do not prove that your action retries the right failures.

At the action level, cover at least these cases:

1. the first insert succeeds;
2. the first attempt gets a wrapped unique violation and the second succeeds;
3. a non-unique failure is not retried;
4. repeated unique violations exhaust the attempt limit and are reported;
5. a successful retry returns the row created by the competing request.

The race itself is difficult to reproduce reliably in a unit test. Do not use sleeps and hope two test processes interleave correctly. Put the retry decision behind a real callable, mock or fake the storage boundary, and throw a realistic wrapped exception sequence.

Then keep one database integration test for the unique index and `firstOrCreate()` lookup shape. The unit test proves policy. The integration test proves schema and query alignment.

## Static analysis can make `first()` nicer

PHP itself sees this signature:

```php
public function first(string $type): ?Throwable
```

PHPStan or Psalm can understand the template docblock and infer a narrower result:

```php
/** @var UniqueConstraintViolationException|null $violation */
$violation = (new ExceptionChain($exception))->first(
    UniqueConstraintViolationException::class,
);
```

Depending on your analyser and configuration, the explicit `@var` may not be necessary. The important part is that the runtime API remains simple while static analysis can preserve the selected type.

You could split the API into methods such as `firstInstanceOf()` and `firstMatching()`. That is more explicit, but also more verbose. For a small internal value object, `first()` and `find()` are clear enough if their docblocks are strong.

## Performance honesty

It is easy to oversell the lazy version.

A generator plus `LazyCollection` is not automatically faster than a `do/while` loop. It creates objects and closures, dispatches through collection methods, and adds framework code to a problem PHP can solve directly.

For a typical exception chain with three nodes, the direct loop will probably be faster in a microbenchmark.

The lazy design gives you:

- short-circuit traversal;
- no eager array of every exception;
- reusable terminal operations;
- a familiar Laravel query model;
- one place for cycle protection;
- a clean public value-object API.

It does not give you:

- lazy creation of the exception objects;
- zero memory use;
- a meaningful performance win on tiny chains;
- free protection against expensive predicates;
- proof that retries are safe.

The cycle-safe implementation stores visited object IDs. If a missing lookup walks 5,000 nodes, it also stores 5,000 integer keys for the duration of that traversal. That is still much smaller than copying 5,000 exception objects into a new eager array, but it is not O(1) auxiliary memory.

If performance is the only goal, use the direct loop and stop at the first match. If API clarity and reusable queries are the goal, composition with `LazyCollection` is a reasonable Laravel-native design.

## Tradeoffs and alternatives

### A plain function

Use a function when you need one boolean operation and do not expect the concept to grow.

```php
exceptionChainContains($exception, SomeException::class);
```

It is difficult to beat for simplicity.

### A static helper

This is also valid:

```php
ExceptionChain::contains(
    $exception,
    SomeException::class,
);
```

It keeps construction out of the call site. I prefer the instance form because the chain is the subject:

```php
(new ExceptionChain($exception))->contains(
    SomeException::class,
);
```

It also avoids passing the same exception again when making several queries.

### A direct-loop value object

The public API does not require `LazyCollection`:

```php
final class ExceptionChain
{
    public function __construct(
        private Throwable $exception,
    ) {}

    public function contains(string $type): bool
    {
        $current = $this->exception;

        do {
            if ($current instanceof $type) {
                return true;
            }
        } while ($current = $current->getPrevious());

        return false;
    }
}
```

This is a strong choice if `contains()` is the only API. Add the collection only when its query operations pay for the extra abstraction.

### Flattening to an array

An eager array is appropriate when you know you will inspect every node several times:

```php
$exceptions = iterator_to_array(
    walkExceptionChain($exception),
);
```

For diagnostics that render the full chain, eager materialization can be simpler. Laziness is not a moral virtue.

### Framework-specific helpers

Before adding a helper, check whether your framework, database abstraction, or error-reporting tool already exposes the semantic cause you need. Do not build a parallel exception taxonomy when a maintained one exists.

## Naming and placement

`ExceptionChain` is better than a generic `ExceptionHelper`.

It names the object being queried, not a bag of unrelated utility methods. A support namespace also keeps it away from one feature:

```text
App\Support\Exceptions\ExceptionChain
```

The class should have a docblock because the implementation is simple but the reason for it is not immediately obvious:

```php
/**
 * Queries an exception and every exception linked through getPrevious().
 *
 * Use this when application or framework layers can wrap the cause that
 * decides retry, reporting, or recovery policy.
 */
final class ExceptionChain
{
    // ...
}
```

That explanation helps human reviewers and coding agents understand when to reuse the type instead of writing another one-hop check.

## The design rule

Wrapped exceptions preserve two kinds of truth:

- the outer exception explains the failed operation;
- an inner exception can explain the actionable cause.

Do not discard the outer context. Do not assume the cause is always at one fixed depth. Query the chain.

For one call site, a short-circuiting loop is enough. For a repeated Laravel pattern, a public `ExceptionChain` value object can make retry and reporting policy read like the question you are actually asking:

```php
when: fn (Throwable $exception): bool =>
    (new ExceptionChain($exception))->contains(
        UniqueConstraintViolationException::class,
    ),
```

Keep the public API narrow. Wrap `LazyCollection`; do not become one. Remember that traversal is lazy, not exception creation. Report only after an expected race fails to recover. Test the value object and the retry policy at separate levels.

The result is not a grand exception framework. It is a small, precise tool for a question that appears whenever useful failures are wrapped in useful context.
