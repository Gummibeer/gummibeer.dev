You need to send a welcome email when a customer makes their first payment. The obvious move: fire a `FirstPaymentCaptured` event.

Don't.

Before you create that event, ask: does your domain actually _produce_ a `FirstPaymentCaptured` fact, or are you inventing a new event purely because a reactor needs a trigger?

That distinction matters more than almost anything else in an event-sourced system.

---

## Three kinds of events, one common mistake

In a Spatie Laravel Event Sourcing setup, it helps to be precise about what kind of event you're dealing with.

**Storable events** are facts appended to the event stream. They are the source of truth. Replaying them reconstructs state. Examples: `OrderCreated`, `PaymentCaptured`, `SubscriptionCancelled`.

**Domain events** (non-stored) are notifications that something happened, dispatched via Laravel's event system. They don't participate in replay. They trigger side effects — emails, webhooks, third-party calls.

**Infrastructure events** are the plumbing — queue jobs completing, HTTP requests finishing. They don't belong in your domain model at all.

The mistake is treating a _consumer need_ as a domain fact. You have a new listener that cares about first payments, so you reach for a new storable event. But `FirstPaymentCaptured` isn't something your domain produces. It's a derived projection of the `PaymentCaptured` stream with an ordinal filter applied.

---

## The "fire once per business milestone" test

A storable event earns its place when it represents a state transition that is:

1. Irreversible (or at least meaningful as a distinct moment in time)
2. Not derivable from existing events without external state
3. Something other projectors or reactors might independently care about

`PaymentCaptured` passes this test. `FirstPaymentCaptured` does not — it _is_ derivable from `PaymentCaptured` by counting.

Here's the storable event you already have:

```php
final class PaymentCaptured extends ShouldBeStored
{
    public function __construct(
        public readonly string $orderId,
        public readonly int $amountInCents,
        public readonly string $currency,
        public readonly string $paymentMethodId,
    ) {}
}
```

You don't need another event. You need a reactor that checks whether this is the first one.

## Idempotency inside the reactor

The clean approach: maintain a small domain table as a "have I run this?" guard. Your reactor records that it handled the first payment for a given customer, and it checks before acting.

```php
final class WelcomeEmailReactor extends EventHandler
{
    public function __construct(
        private readonly WelcomeEmailService $mailer,
        private readonly FirstPaymentRepository $repository,
    ) {}

    public function onPaymentCaptured(PaymentCaptured $event, string $aggregateUuid): void
    {
        if ($this->repository->hasFirstPaymentBeenHandled($aggregateUuid)) {
            return;
        }

        if (! $this->repository->isFirstPayment($aggregateUuid)) {
            return;
        }

        $this->mailer->sendWelcome($aggregateUuid);

        $this->repository->markFirstPaymentHandled($aggregateUuid);
    }
}
```

Two checks. The first is an idempotency guard — if replay fires this event again, or if a retry occurs after the email was already sent, you bail out immediately. The second is the domain check — is this actually the first payment for this customer?

The `FirstPaymentRepository` wraps a simple table:

```php
final class FirstPaymentRepository
{
    public function isFirstPayment(string $aggregateUuid): bool
    {
        return ! DB::table('payments')
            ->where('order_aggregate_uuid', $aggregateUuid)
            ->where('captured_at', '<', now())
            ->exists();
    }

    public function hasFirstPaymentBeenHandled(string $aggregateUuid): bool
    {
        return DB::table('first_payment_reactor_log')
            ->where('aggregate_uuid', $aggregateUuid)
            ->exists();
    }

    public function markFirstPaymentHandled(string $aggregateUuid): void
    {
        DB::table('first_payment_reactor_log')->insertOrIgnore([
            'aggregate_uuid' => $aggregateUuid,
            'handled_at' => now(),
        ]);
    }
}
```

This is not exciting code. It's correct code. And correct beats clever every time.

## What a projector looks like for the same event

Projectors reconstruct read models from the event stream. They must be replayable — which means they can't have side effects like sending emails. But they _can_ compute derived state like "is this the first payment?"

```php
final class OrderPaymentProjector extends Projector
{
    public function onPaymentCaptured(PaymentCaptured $event, string $aggregateUuid): void
    {
        $count = DB::table('order_payments')
            ->where('order_aggregate_uuid', $aggregateUuid)
            ->count();

        DB::table('order_payments')->insert([
            'order_aggregate_uuid' => $aggregateUuid,
            'amount_in_cents' => $event->amountInCents,
            'currency' => $event->currency,
            'payment_method_id' => $event->paymentMethodId,
            'is_first_payment' => $count === 0,
            'captured_at' => now(),
        ]);
    }
}
```

Now your read model has `is_first_payment` as a computed column, derived during projection. Any query that needs to know "was this their first?" reads from this table — no event explosion required.

## When a new storable event is actually the right answer

Sometimes the existing stream genuinely doesn't carry the signal you need.

Imagine you're adding subscription billing. A customer might have many `PaymentCaptured` events across different orders. The concept of "first subscription renewal" is a distinct business milestone — it signals that the customer survived their trial, that their card works long-term, that retention metrics should start counting. No amount of counting existing events gives you that milestone cleanly without cross-aggregate queries that are fragile at scale.

In that case, `SubscriptionRenewed` is a legitimate new storable event. It fires once per renewal cycle. It has a clear business meaning. It's not a derived signal — it's a first-class fact.

The test: if removing this event from the stream would make it impossible to reconstruct an important piece of state without reaching outside the aggregate, it's a real event. If removing it just means a reactor has to do slightly more work, it's a convenience shortcut you don't need.

---

## The cost of event proliferation

Every storable event you add is a permanent commitment:

- **Replay complexity.** Your projectors and reactors must handle every event version ever emitted. A `FirstPaymentCaptured` event added in 2024 must still be handled correctly during a full replay in 2027, even after the code that fires it has changed or been deleted.
- **Documentation debt.** Events are contracts. New developers (and future you) need to understand why `FirstPaymentCaptured` exists alongside `PaymentCaptured`, what the difference is, and whether both will always be present together or just sometimes.
- **Migration surface.** If you later discover your "first payment" logic had a bug — maybe it counted failed payment attempts — you now have a corrupted fact in your event stream. Fixing a derived projection is a migration. Fixing a stored event that was emitted incorrectly is a lot messier.

Near-duplicate events are the most insidious form of this problem. `PaymentCaptured` and `FirstPaymentCaptured` look like they carry related information. Readers assume there's a meaningful distinction. Sometimes there isn't — it was just a lazy trigger for one reactor that nobody cleaned up.

---

## The decision rule

When you feel the urge to create a new event, run through this:

1. **Is this a new state transition, or is it a filter on an existing one?** Filters belong in reactors and projectors, not in the event stream.
2. **Can I compute this from existing events without cross-aggregate queries?** If yes, it's a projection concern, not a domain event.
3. **Would replaying the stream without this event lose irreplaceable information?** If no, you don't need it.
4. **Does this event have meaning independent of the consumers that currently care about it?** If you can only justify it by pointing at the one reactor it triggers, it's not a domain event — it's a glorified function call.

The event stream is a ledger. Ledgers record facts, not interpretations. Keep it clean.
