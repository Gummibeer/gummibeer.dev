Someone added an `is_eu_seller` check in the invoice mailer. Then someone else added it in the payment capture handler. Then a third person added it in the webhook processor — but they copy-pasted from the wrong place, so the condition is subtly different. You now have five implementations of "which payment processor applies here" and a production incident from the sixth spot that nobody caught.

This is flag check creep. And it is almost always the way it starts: one innocent conditional, duplicated under time pressure, diverging silently.

## The smell

Here is a representative before state. Three callsites, all answering the same question independently:

```php
// In InvoiceMailer.php
$processor = $seller->is_eu_seller
    ? new StripeProcessor()
    : new PayPalProcessor();

// In PaymentCaptureJob.php
if ($order->seller->is_eu_seller && $order->currency === 'EUR') {
    $driver = app(StripeProcessor::class);
} else {
    $driver = app(PayPalProcessor::class);
}

// In WebhookController.php
$handler = match(true) {
    $seller->is_eu_seller => StripeWebhookHandler::class,
    default               => PayPalWebhookHandler::class,
};
```

These three fragments look like they agree, but they don't. The job adds a currency check. The controller resolves a class name instead of an instance. If a third processor gets added — say, Mollie for Netherlands sellers — every one of these sites needs updating, and someone will miss one.

The condition is not the problem. The duplication of the condition is.

## The fix: designate an authority

Create a class whose only job is to answer "which processor?" and make every caller ask it instead of re-implementing the answer.

```php
final class PaymentProcessorRouter
{
    public function for(Seller $seller, string $currency): PaymentProcessorContract
    {
        if ($seller->is_eu_seller && in_array($currency, ['EUR', 'GBP', 'SEK'], strict: true)) {
            return app(StripeProcessor::class);
        }

        if ($seller->country_code === 'NL') {
            return app(MollieProcessor::class);
        }

        return app(PayPalProcessor::class);
    }
}
```

Every callsite collapses to one line:

```php
// InvoiceMailer.php
$processor = $this->router->for($seller, $invoice->currency);

// PaymentCaptureJob.php
$processor = $this->router->for($order->seller, $order->currency);

// WebhookController.php
$processor = $this->router->for($seller, $request->currency);
```

The routing logic lives in exactly one place. When Mollie gets added, removed, or its conditions change, you edit `PaymentProcessorRouter` and nothing else.

## Return the strategy object, not a string

A common half-measure is returning a string identifier or an enum case and letting the caller resolve it:

```php
// Avoid this
public function processorKeyFor(Seller $seller, string $currency): string
{
    return $seller->is_eu_seller ? 'stripe' : 'paypal';
}

// Caller still has to know what to do with 'stripe'
$key = $this->router->processorKeyFor($seller, $currency);
$processor = ProcessorFactory::make($key); // another place that knows the mapping
```

Now you have two places that hold routing knowledge: the router and the factory. Return the resolved object directly. The caller should not need to know anything about which processor it is — only that it implements the contract.

## How to migrate without a rewrite

You do not need to refactor all five callsites on day one.

Start by creating the router class and wiring it up. Then route new callsites through it from the beginning — do not add another raw conditional. For existing callsites, refactor them one at a time as you touch those files. Keep a comment on each old callsite so it is visible:

```php
// TODO: delegate to PaymentProcessorRouter
$processor = $seller->is_eu_seller
    ? new StripeProcessor()
    : new PayPalProcessor();
```

Within a few sprints the raw conditionals are gone and the router is the only authority. The incremental approach means no big-bang refactor, no feature freeze, and no risk of accidentally breaking five things at once.

## Testing

The router is worth testing in isolation because it encodes real business rules:

```php
it('routes EU sellers to Stripe', function () {
    $seller = Seller::factory()->euSeller()->make();
    $processor = app(PaymentProcessorRouter::class)->for($seller, 'EUR');

    expect($processor)->toBeInstanceOf(StripeProcessor::class);
});

it('routes Netherlands sellers to Mollie regardless of EU flag', function () {
    $seller = Seller::factory()->state(['country_code' => 'NL', 'is_eu_seller' => true])->make();
    $processor = app(PaymentProcessorRouter::class)->for($seller, 'EUR');

    expect($processor)->toBeInstanceOf(MollieProcessor::class);
});
```

The individual strategies — `StripeProcessor`, `MollieProcessor` — get their own tests that assume nothing about routing. The router tests cover the decision logic. The two concerns stay separate, and when a rule changes you know exactly which test file to look at.

## The pattern generalises

This is not a payment processor pattern. It is a routing pattern. It applies any time you have multiple implementations of a contract and some logic that decides which one to use:

- Which notification channel to send through
- Which shipping carrier to use for an order
- Which queue driver to dispatch a job on
- Which PDF renderer handles a document type

Wherever you find yourself writing `if ($thing->someFlag)` in more than one place to pick a collaborator, you have routing logic that needs a home. Give it one.
