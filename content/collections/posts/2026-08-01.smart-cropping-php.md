Image cropping sounds simple. Resize to fit. Cut off the edges. Done.

Except the edges are not always the boring parts. Paste a portrait landscape photo into a 16:9 thumbnail slot and the default center crop cuts off someone's head. The "smart" part of smart cropping is finding where the interesting stuff actually is before you cut.

This post is about how I built that for PHP — no native extensions, no paid services, no surprises — and why the approach works even on 4K source images at HTTP request time.

---

## The problem Intervention Image doesn't solve

[Intervention Image](https://image.intervention.io/) is the standard PHP image library. It handles resizing, cropping, encoding, and it runs on both GD and Imagick drivers. What it doesn't do is decide _where_ to crop when you have a focal point constraint.

The `fit()` method gives you contain/cover semantics but the positioning is a fixed anchor (center, top, etc.). There's no "figure out what's interesting and crop around that" mode.

The feature request for smart crop has been [open since 2020](https://github.com/Intervention/image/issues/1002). The maintainer acknowledged the idea but flagged a real concern: naively iterating every pixel on a 4K image is expensive. A million-plus iterations per request is not viable.

The issue was eventually closed without adding it to the core — the maintainer's final word was that it remains interesting but belongs in an extension package rather than core.

So I built one for [pixpipe](https://github.com/Astrotomic/pixpipe), a Glide wrapper I've been working on.

---

## The approach: downscale, blur, gradient

The trick that makes this fast and practical is doing the analysis on a much smaller image, then mapping the result back to full resolution.

The steps:

1. Clone the source image
2. Convert to RGB colorspace (normalises any exotic input)
3. Scale down to at most 256×256, preserving aspect ratio
4. Apply a light blur (σ≈1) to kill sensor noise and grain
5. Build a luminance map from every pixel
6. Compute the gradient magnitude at each point
7. Pick the highest-scoring point with a mild center bias
8. Map that coordinate back to the original dimensions

The result is a single `Point(x, y)` — the focal point in the original image's coordinate space. The caller then calculates a crop offset that places the focal point as close to the center of the output frame as possible.

---

## Why this works on 4K images

A 4K source is 3840×2160 — around 8.3 million pixels. That's too many to iterate in a tight PHP loop at request time.

After scaling to 256×256, you have at most 65,536 pixels. The loop runs on those, not the original. A 4K image takes slightly longer than a 1080p one because the downscale step itself takes more work, but the analysis loop is always the same bounded size. Consistent, predictable, fast.

VIPS (the image library used in Intervention's vips driver) does something similar internally — it works on a reduced image pyramid and uses its own "interestingness" detection. If you're using the VIPS driver, you can actually delegate to VIPS's native `smartcrop` and skip the PHP loop entirely. For GD and Imagick drivers, the pure-PHP implementation is the fallback.

The blur step is important. Without it, entropy-based approaches will happily decide that a noisy concrete wall is the most interesting part of the photo, because it has the highest pixel variance. A light Gaussian blur collapses that noise while keeping real structure (faces, text, high-contrast subjects) intact.

## The code

Here's the full `FocusPointAnalyzer`:

```php
<?php

namespace Astrotomic\Pixpipe\Analyzers;

use Intervention\Image\Colors\Rgb\Colorspaces\RgbColorspace;
use Intervention\Image\Geometry\Point;
use Intervention\Image\Interfaces\AnalyzerInterface;
use Intervention\Image\Interfaces\ImageInterface;
use Spatie\Color\Color;

class FocusPointAnalyzer implements AnalyzerInterface
{
    private int $width;
    private int $height;
    private ImageInterface $image;

    public function analyze(ImageInterface $image): mixed
    {
        $this->height = $image->height();
        $this->width = $image->width();

        // Working copy: normalise colorspace, scale down, light blur
        $this->image = (clone $image)
            ->setColorspace(new RgbColorspace)
            ->scaleDown(256, 256)
            ->blur(1);

        $w = $this->image->width();
        $h = $this->image->height();

        // Edge case: very small images or degenerate input
        if ($w < 3 || $h < 3 || $this->width < 1 || $this->height < 1) {
            return new Point(
                max(0, intdiv($this->width, 2)),
                max(0, intdiv($this->height, 2))
            );
        }

        // Build luminance map (Rec. 709), weighted by alpha
        $lum = [];
        for ($y = 0; $y < $h; $y++) {
            $row = [];
            for ($x = 0; $x < $w; $x++) {
                $c = Color::create($this->image->pickColor($x, $y)->toHex());
                $r = $c->red()->value();
                $g = $c->green()->value();
                $b = $c->blue()->value();
                $a = $c->alpha()->normalize(); // 0..1

                // Perceived luminance — transparent pixels count less
                $row[] = (0.2126 * $r + 0.7152 * $g + 0.0722 * $b) * $a;
            }
            $lum[$y] = $row;
        }

        // Score every non-border pixel: gradient magnitude + mild center bias
        $cx = ($w - 1) / 2.0;
        $cy = ($h - 1) / 2.0;
        $sigma = max(1.0, min($w, $h) / 3.0);

        $bestScore = -1.0;
        $bestX = (int) floor($cx);
        $bestY = (int) floor($cy);

        for ($y = 1; $y < $h - 1; $y++) {
            for ($x = 1; $x < $w - 1; $x++) {
                $dx = $lum[$y][$x + 1] - $lum[$y][$x - 1];
                $dy = $lum[$y + 1][$x] - $lum[$y - 1][$x];
                $grad = abs($dx) + abs($dy);

                $dist2 = ($x - $cx) ** 2 + ($y - $cy) ** 2;
                $centerBias = exp(-$dist2 / (2.0 * $sigma * $sigma));

                $score = $grad * (1.0 + 0.3 * $centerBias);

                if ($score > $bestScore) {
                    $bestScore = $score;
                    $bestX = $x;
                    $bestY = $y;
                }
            }
        }

        // Flat image (no edges at all) — fall back to center
        if ($bestScore <= 0) {
            return new Point(
                max(0, min($this->width - 1, intdiv($this->width, 2))),
                max(0, min($this->height - 1, intdiv($this->height, 2)))
            );
        }

        // Map back to original dimensions
        $scaleX = $this->width / $w;
        $scaleY = $this->height / $h;

        return new Point(
            max(0, min($this->width - 1, (int) round($bestX * $scaleX))),
            max(0, min($this->height - 1, (int) round($bestY * $scaleY)))
        );
    }
}
```

And the `Size` manipulator that uses it:

```php
public function resolveCropOffset(ImageInterface $image, int $width, int $height): array
{
    if (! $this->isSmartcrop()) {
        return parent::resolveCropOffset($image, $width, $height);
    }

    /** @var Point $focus */
    $focus = $image->analyze(new FocusPointAnalyzer);

    // Center the crop around the focal point, clamped to image bounds
    $offsetX = (int) round($focus->x() - ($width / 2));
    $offsetY = (int) round($focus->y() - ($height / 2));

    $offsetX = max(0, min($image->width() - $width, $offsetX));
    $offsetY = max(0, min($image->height() - $height, $offsetY));

    return [$offsetX, $offsetY];
}
```

The manipulator extends Glide's `Size` manipulator. When `fit=smartcrop` is passed as a Glide parameter, it runs the analyzer and overrides the crop offset calculation. Everything else — the actual resize, encode, cache — flows through Glide as normal.

## The luminance and gradient choices

A few things I want to spell out because they're not obvious from the code:

**Why luminance and not raw RGB?** Gradient computation on three channels is more expensive and doesn't give meaningfully better results for this use case. Human perception of "interesting" correlates better with luminance contrast than raw colour differences. The Rec. 709 weights (0.2126 R, 0.7152 G, 0.0722 B) match the sensitivity of the human visual system.

**Why central differences for gradient?** `dx = lum[y][x+1] - lum[y][x-1]` is a three-point stencil. It's a simple approximation of the Sobel operator and it's fast. A full Sobel convolution would be slightly more accurate but the difference at this analysis scale (after downscale and blur) is negligible.

**Why the center bias?** When two regions score similarly on gradient magnitude, the one closer to center produces a more natural-feeling crop. It's a small nudge, not a dominant factor — the 0.3 multiplier means a dead-center flat region will always lose to an off-center interesting one.

**Why alpha weighting?** Images with transparency (PNGs, images on white backgrounds cropped to shape) shouldn't have their focal point land in a transparent region. Multiplying luminance by the alpha channel's normalised value collapses transparent pixels to near-zero, so they don't win the scoring.

---

## What it doesn't do

This is gradient magnitude detection, not face detection or saliency mapping. It finds high-contrast edges and structure. For most content — products, landscapes, text-on-image, architecture — that's exactly the right signal.

For portraits, it often works fine because faces tend to have the highest-contrast edges (hairline, eye contours, mouth). But it can be fooled by a very busy background behind a flat-lit face.

If portraits are your primary use case, you'd want to front this with a face detection pass — OpenCV via the `php-opencv` extension, or an external API — and fall back to the gradient approach when no face is found. That's a harder dependency to justify for a general-purpose library, which is why I left it out.

## Production considerations

**Caching is required.** Running this on every request would be wasteful even at 256×256. Put a cache layer in front of image transformation — Glide has one built in. The focal point analysis happens once per source image, then the cached derivative is served for all subsequent requests.

**The VIPS driver is a special case.** VIPS has native smartcrop support (`vips_smartcrop`) that is significantly faster than this PHP implementation. If your environment runs the VIPS Intervention driver, you can delegate to VIPS directly and skip the analyzer entirely. The PHP path is the fallback for GD and Imagick deployments.

**The 256px ceiling is a default, not a requirement.** For very wide aspect ratios (e.g., 21:9 banners), scaling to 256 on the longer side means the shorter side might be as small as 110px. That's still enough pixels to get a meaningful gradient signal, but you can tune the constant to 512 or 384 if quality matters more than speed for your use case. The performance difference on modern hardware is small.

---

## Why this ended up in pixpipe and not in Intervention itself

The Intervention maintainer closed the issue with a clear position: smart crop is interesting but belongs in an extension package, not in core. The reasoning is sound — core libraries should stay lean, and smart crop involves algorithm choices (gradient? entropy? face detection?) that belong in userland.

The [Intervention v4 extension API](https://image.intervention.io/v4/modifying-images/custom-extensions) makes this practical. You can register custom manipulators and analyzers without forking the library. That's exactly what pixpipe uses.

If you're building a Glide-based image pipeline and want smart crop without a paid CDN or a sidecar microservice, this is a usable implementation. The code is in the [Astrotomic/pixpipe](https://github.com/Astrotomic/pixpipe) repo.
