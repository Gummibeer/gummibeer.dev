Your package has `@phpstan-ignore-next-line` in 14 places and a baseline file with 60 entries. It "passes" at level 6. It's lying to you.

The baseline exists to silence errors you haven't fixed. The inline ignores exist to silence errors you gave up on. The CI badge is green, but the underlying code is still wrong — you've just told PHPStan not to look.

This is a guide for fixing that. Not by bumping numbers in a config file, but by actually resolving the errors those ignores were hiding. I'll use [astrotomic/laravel-translatable](https://github.com/Astrotomic/laravel-translatable) as a running example because it hits every category: traits, magic properties, Eloquent relation generics, and contracts that PHPStan can't infer without help.

---

## Pick Your Level Deliberately

Larastan's levels are cumulative. Each level adds stricter checks on top of what came before. Here's what actually matters for package work:

| Level | What it enforces                              |
| ----- | --------------------------------------------- |
| 0     | Basic syntax, obviously wrong calls           |
| 1     | Possibly undefined variables                  |
| 2     | Unknown methods and properties on known types |
| 3     | Return type checking                          |
| 4     | Dead code, unused parameters                  |
| 5     | Argument type checking                        |
| 6     | Union types, strict typechecks                |
| 7     | Unknown dynamic properties                    |
| 8     | `mixed` type propagation — the painful one    |
| 9     | Strict mixed usage                            |

For most Laravel packages, **level 6 is the minimum that actually catches real bugs**. Level 8 is where you earn your static analysis merit badge — every `mixed` must be explicitly handled.

Don't set a level you can only hit by filling a baseline. If level 8 requires 40 suppressions, you're at level 5 with extra steps.

Start by running without a baseline:

```bash
vendor/bin/phpstan analyse --no-progress 2>&1 | grep "errors:"
```

Then find the highest level you can reach with zero errors and zero baseline entries. That's your honest starting point. Everything above it is the work ahead of you.

## Your `phpstan.neon` Starting Point

For a Laravel package, this is the minimum useful config:

```neon
includes:
    - vendor/larastan/larastan/extension.neon

parameters:
    level: 6
    paths:
        - src
        - tests
    checkGenericClassInNonGenericObjectType: false
    treatPhpDocTypesAsCertain: false
```

`treatPhpDocTypesAsCertain: false` prevents PHPStan from trusting your `@var` casts as gospel, which surfaces actual type mismatches instead of hiding them. Leave it on.

`checkGenericClassInNonGenericObjectType: false` suppresses noise from Eloquent's non-generic base classes that Larastan hasn't fully annotated yet. Enable it when you're ready — it's loud.

No baseline. If you have one, your first job is deleting it entry by entry.

## Trait False Positives

Traits are where most packages accumulate their first pile of ignores.

In `laravel-translatable`, the `Translatable` trait adds methods like `getTranslation()`, `setAttribute()`, and `getAttribute()` that get called on the consuming model. PHPStan sees a method defined in a trait that's never called from within that trait, and depending on config, complains about it.

The worse problem: the trait calls `$this->morphMany()`, `$this->hasMany()`, and other Eloquent methods that don't exist on the trait itself. They exist on `Model`, which the trait assumes it will be mixed into.

The wrong fix is `@phpstan-ignore-next-line`. The right fix is telling PHPStan what `$this` actually is.

```php
/**
 * @mixin \Illuminate\Database\Eloquent\Model
 */
trait Translatable
{
    // ...
}
```

This tells PHPStan that every `$this` call inside the trait can resolve against `Model`. You get full method resolution for `$this->hasMany()`, `$this->morphMany()`, and Eloquent's magic scopes — without suppressing anything.

If your trait is more restrictive — it only works with models that implement a specific contract — be explicit:

```php
/**
 * @mixin \App\Contracts\HasTranslationsContract
 */
trait Translatable
```

The `@mixin` annotation is load-bearing. It's not a comment, it's a type assertion that PHPStan uses to resolve method calls inside the trait body.

## Relation Return Type Generics

This is the one that produces the most cascade errors in Eloquent-heavy packages.

PHPStan's Larastan extension ships with generic annotations on Eloquent's relation classes. `HasMany`, `BelongsTo`, `MorphMany`, and friends are all generic over their related model type. When you declare a relation without the generic, PHPStan infers the loosest possible type — often `mixed` or `Model` — and every downstream call becomes an error.

Wrong:

```php
public function translations(): HasMany
{
    return $this->hasMany(Translation::class);
}
```

PHPStan sees `HasMany` with no type parameter. At level 5+, it will infer the items as `Model`, not `Translation`. Calling `$model->translations->first()->locale` then fails because `locale` isn't on `Model`.

Right:

```php
public function translations(): HasMany
{
    return $this->hasMany(Translation::class);
}
```

Wait — the return type alone isn't enough. You need the generic:

```php
/** @return HasMany<Translation> */
public function translations(): HasMany
{
    return $this->hasMany(Translation::class);
}
```

Or if you're on PHP 8.2+ and Larastan's generics are stable enough for your package:

```php
/** @return HasMany<Translation, $this> */
public function translations(): HasMany
{
    return $this->hasMany(Translation::class);
}
```

The two-parameter form (`HasMany<TRelatedModel, TDeclaringModel>`) is the full signature. Larastan uses it to resolve `$this->translations()` calls back to the model that declared the relation.

For `BelongsTo`, the generic is the related model type:

```php
/** @return BelongsTo<TranslationModel, $this> */
public function translatable(): BelongsTo
{
    return $this->belongsTo(TranslationModel::class);
}
```

In `laravel-translatable`, the complication is that the translation model class is dynamic — it's resolved from config at runtime. The package has a `getTranslationModelName()` method that returns a string class name. Static analysis can't follow that.

The solution here is a stub. More on that in a moment.

## Magic Property Annotations

Eloquent models expose properties dynamically through `__get` and `__set`. PHPStan at level 7+ will flag access to any property not explicitly declared on the class.

For your own models in a consumer app, `@property` annotations in the docblock are the right fix:

```php
/**
 * @property string $locale
 * @property string $name
 * @property int $translatable_id
 * @property string $translatable_type
 */
class TranslationModel extends Model
```

For a package where the translation model is meant to be extended or swapped by the consumer, you have a different problem: you can't annotate properties that don't exist yet.

Two patterns work here.

**Pattern 1: Abstract base with `@property` annotations**

Ship an abstract `TranslationModel` in the package with documented properties, let consumers extend it and add their own:

```php
/**
 * @property string $locale
 */
abstract class BaseTranslation extends Model
{
    // base implementation
}
```

Consumers do:

```php
/**
 * @property string $name
 * @property string $description
 */
class PostTranslation extends BaseTranslation
{
    protected $table = 'post_translations';
}
```

**Pattern 2: Internal stubs for static analysis only**

When the model is truly dynamic (resolved by string from config), you write a stub that only PHPStan sees. This is common in Laravel packages where models are swappable.

Create a `stubs/` directory in the package root:

```
stubs/
  TranslationModel.stub.php
```

```php
<?php
// This file is used for static analysis only — it is never loaded at runtime.

namespace Astrotomic\Translatable;

/**
 * @property string $locale
 * @property int $translatable_id
 * @property string $translatable_type
 */
class TranslationModel extends \Illuminate\Database\Eloquent\Model {}
```

Wire it into `phpstan.neon`:

```neon
parameters:
    stubFiles:
        - stubs/TranslationModel.stub.php
```

PHPStan loads these stubs during analysis and uses them to resolve types. The file never ships to end users — add it to your published package but not to the autoloader:

```json
{
    "autoload": {
        "psr-4": {
            "Astrotomic\\Translatable\\": "src/"
        }
    }
}
```

The `stubs/` directory is never in `autoload` or `autoload-dev`.

## Eliminating Inline Suppressions

Once you've added `@mixin` to traits, proper generics to relations, and stubs or annotations for magic properties, go through every remaining `@phpstan-ignore-next-line` and classify it:

**Legitimate — Larastan limitation:** Some Eloquent magic genuinely can't be resolved yet. If there's an open Larastan issue and the suppression is unavoidable, keep it. Add a comment explaining why and link the issue:

```php
// @phpstan-ignore-next-line — Larastan doesn't resolve dynamic morphMap yet
// See: https://github.com/larastan/larastan/issues/XXXX
$this->morphTo();
```

**Illegitimate — fixable with proper types:** Most ignores fall here. Return to the call site, add the right generic or annotation, remove the ignore.

**Illegitimate — wrong assumption:** Some ignores exist because someone guessed the type was ambiguous and gave up. Often the fix is a one-line `@var` assertion or a narrowed return type.

Run `grep -rn 'phpstan-ignore' src/` before and after. Count the lines. The diff is your actual progress.

## Running PHPStan on a Test App

Package CI should cover two things: your package source, and your package integrated into a real Laravel app.

For the second part, scaffold a minimal Laravel app in your CI environment and run PHPStan against it with your package installed. This catches type errors that only appear when Eloquent resolves your trait at the consumer level.

Here's a working GitHub Actions setup:

```yaml
name: Static Analysis

on: [push, pull_request]

jobs:
    phpstan:
        runs-on: ubuntu-latest

        strategy:
            matrix:
                php: ['8.2', '8.3']
                laravel: ['10.*', '11.*']

        name: PHPStan — PHP ${{ matrix.php }} / Laravel ${{ matrix.laravel }}

        steps:
            - uses: actions/checkout@v4

            - uses: shivammathur/setup-php@v2
              with:
                  php-version: ${{ matrix.php }}
                  tools: composer:v2
                  coverage: none

            - name: Install dependencies
              run: composer require "laravel/framework:${{ matrix.laravel }}" --no-update && composer update --prefer-dist --no-progress

            - name: Run PHPStan
              run: vendor/bin/phpstan analyse --no-progress
```

If your package is complex enough to warrant a test application (a separate Laravel project that installs your package via path repository), add a second job:

```yaml
phpstan-test-app:
    runs-on: ubuntu-latest

    steps:
        - uses: actions/checkout@v4
          with:
              path: package

        - uses: shivammathur/setup-php@v2
          with:
              php-version: '8.3'
              coverage: none

        - name: Create test Laravel app
          run: composer create-project laravel/laravel test-app --prefer-dist --no-progress

        - name: Add path repository
          working-directory: test-app
          run: |
              composer config repositories.local '{"type":"path","url":"../package"}' --file composer.json
              composer require "your-vendor/your-package:*" --prefer-source

        - name: Run PHPStan against test app
          working-directory: test-app
          run: |
              cp ../package/phpstan.neon.test ./phpstan.neon
              vendor/bin/phpstan analyse app --no-progress
```

Ship a `phpstan.neon.test` in your package root that the CI test app picks up. It should cover the test models and any package-level stubs.

## The Baseline Is Not Progress

One more thing before you call the cleanup done.

The PHPStan baseline is useful for exactly one scenario: you're inheriting an existing codebase and you need CI to not fail on issues that predate your ownership, while still catching new issues. It's a starting line, not a destination.

If your package's baseline has been growing over time — entries added to unblock CI — that's not static analysis, it's static analysis theater.

Delete the baseline. Fix the errors. If you can't fix an error, understand _why_ you can't fix it. If the answer is "Larastan doesn't support this yet," file the issue, add the suppression with a comment, and move on. That's a real suppression with real justification.

If the answer is "I don't know what type this is," that's the error you actually needed to fix. Static analysis is most valuable at that exact moment — when you realize the codebase has a type you can't name.

## Checklist

Before shipping a package and claiming PHPStan at level N:

- [ ] `phpstan.neon` has no `baseline:` entry
- [ ] `grep -rn 'phpstan-ignore' src/` returns only commented, justified suppressions
- [ ] All traits have `@mixin` or equivalent type assertions
- [ ] All relation methods have `/** @return HasMany<Model> */` generics
- [ ] Magic properties are documented with `@property` or covered by stubs
- [ ] CI runs PHPStan in the matrix against all supported PHP and Laravel versions
- [ ] Level is the highest achievable with zero suppressions and zero baseline

If all of those are true, you've earned the green badge.
