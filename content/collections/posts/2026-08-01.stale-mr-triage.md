You open the merge request list and see six open MRs. Two from last month. One from two months ago. One titled "lumperading fees" with a description that says "Description here." Another with a full description that's clearly about what the author was thinking six weeks ago, not what the diff actually contains. One is in draft but you can't remember why.

This is MR debt. It accumulates when the cost of cleaning up a stale MR exceeds the energy available on any given day, so it rolls over. The problem is that "clean it up" isn't a single action — it's about five different actions depending on what category of stale you're dealing with, and most teams don't have a workflow for figuring out which is which.

## First: Sort Before You Fix

The impulse when looking at a stale MR backlog is to start at the top and work down. Don't. Spend the first pass just categorising, because the remediation for each category is completely different.

Three categories cover almost everything:

**Obsolete.** The feature shipped via a different branch, or the bug it was fixing was already addressed on main, or the business context changed and nobody who knows this is looking at the MR queue. These are candidates for close, not for cleanup.

**Blocked.** The work is real and the MR is valid, but it stopped moving because of a merge conflict, a failing CI job that nobody has time to fix, or an unresolved review thread that requires a decision before the code can change. These aren't stale — they're stuck, and stuck things need a different intervention than forgotten things.

**Forgotten-but-ready.** The author shipped it, moved on to other work, and never came back to follow up. The code might be completely fine. CI might even be green. These are the ones you want to find first because they're close to shippable with minimal effort.

The first action for any MR is figuring out which of these it is. That's a five-minute job per MR if you look at the right signals: when was the branch last updated vs. when was the same code last touched on main, what do the CI logs say, and is there an unresolved review thread or just silence?

## Regenerate the Description From the Diff

MR descriptions go stale even when the code doesn't. An author writes "fixes the payment filter" at 3pm when the context is in their head, pushes, and moves on. Six weeks later, nobody reading that description — including the original author — can reconstruct which payment filter, why it needed fixing, or what the previous behavior was.

If an MR has a generic or placeholder description, the right source of truth is the diff, not the author's memory. Read what actually changed. The description you write should answer three things: what was wrong before, what changed, and why this approach rather than another one.

For the MR titled "lumperading fees" — a six-week-old branch whose title was a typo that never got corrected — the diff told the real story: it centralized a `getHumanizedReservationLines()` method from `ReservationResource` into a shared trait so it could be reused across multiple aggregates. That's a meaningful refactor with a clear rationale. Nothing in "lumperading fees" communicates any of that. The description took three minutes to write from the diff and is now the thing a reviewer will actually read.

"Regenerate from original intent" is the wrong framing. The intent may have shifted during implementation, the codebase context has changed since the branch was created, and the original notes are buried in a commit message or a Slack thread you'll spend twenty minutes finding. Read the diff. Write what it says.

## The "Fix Only What's In Scope" Discipline

Rebasing a stale MR onto current main surfaces all the ways the branch has diverged from where the codebase has gone. Some of those divergences are real conflicts. Some are noise. And some are concerns raised by automated tools about code that was never part of this MR's intention.

The discipline: fix what's in scope, push back on everything else.

"In scope" means: the code changed by this MR, in service of the thing this MR was created to do. If CI fails because a test the MR touches is now asserting the wrong thing after a main-side refactor — fix it. If CI fails because an unrelated file has a new PHPStan violation that this MR happened to touch in passing — that's a separate issue, not this MR's problem.

One of the MRs in a recent triage session had a clean rebase — CI passed, description updated, done. Another surfaced a conflict in a tax settings handler where main had evolved the comparison logic while the branch was adding test coverage for it. Both versions needed to survive; the right merge preserved both intents rather than choosing one. That's in scope: making the branch compatible with current main without changing what the branch does.

If fixing it would require understanding and changing code outside the MR's original scope, it doesn't belong in this cleanup pass.

## When to Disagree With Automated Reviewers

Automated review tools — bots, linters, static analysis — will flag things. Some are real. Some are out of scope. Some are wrong for this specific case even if the rule is right in general.

Triage bot comments the same way you triage MR categories: fix it (valid and in scope), push back with a comment (out of scope or wrong here), or note it (valid, but belongs in a separate ticket).

When you push back, be explicit. Not "this is fine" — that tells a future reviewer nothing. Something like: "This flags the unused variable in the old implementation; the variable is being removed in this MR as part of the cleanup." Or: "Flagged as a complexity warning, but this complexity comes from a compatibility constraint with the existing interface — refactoring it is tracked separately."

The purpose isn't to win an argument with a bot. It's to leave a record that the concern was seen and considered, so a human reviewer doesn't have to relitigate it. Automated comments with no response look like things nobody checked. Automated comments with a short explanation look like things that were handled.

## The Human-Owned Signal

At what point does the MR move from "cleaned up" to "ready for review"?

This is where automation reliably gets it wrong. CI goes green. Bugbot is satisfied. The tooling marks the MR as ready. But the only person who knows whether the code is in the right state to present to a reviewer is the person who did the cleanup.

During one recent triage session, the workflow was set up to automatically add a "ready for review" label every time CI passed. That got interrupted partway through, and correctly so: CI green and "ready for a real reviewer" aren't the same signal. CI green means the tests pass. Ready for review means someone has looked at the code and is prepared to stand behind it.

Keep the ready-for-review signal human-owned. Add it yourself, or ask the MR author to add it. Don't wire it to CI pass or bot sign-off. The label's job is to communicate intent to a reviewer — that intent has to come from a person.

## The Minimum Viable Cleanup

For every MR in the backlog, three things have to be true before it's worth anyone else's time.

**Green CI first.** A failing pipeline is a stop-work condition for a reviewer. Get CI passing on the rebased branch before anything else.

**A description that says what the code does.** Not what you were thinking when you started, not the Linear ticket title, not "fixes stuff." What the diff actually implements and why.

**The right person pinged.** After CI is green and the description is updated, find the person who should review it and ask them explicitly — not "assigned it in the UI" but a direct message that creates an expectation. Stale MRs got stale because the implicit follow-up mechanism didn't work. An explicit ask bypasses that.

In that order. Green CI, then description, then ping. A description without green CI is noise. A ping without a description puts the reviewer in the position of figuring out what the MR even is.

The cleanup for six stale MRs took about half a day — not because any individual MR was hard, but because triage work has coordination overhead that implementation work doesn't. You're making decisions about what to keep, what to change, and what to push back on, and doing that for multiple branches in sequence is slower than it looks.

The benefit is that work that was done but forgotten gets its fair shot, and the reviewer queue stops being a mix of ready things and not-ready things that look identical. Not a clean backlog as a metric. A queue where what you see is actually what it is.
