You swap `statsd()->increment()` for `Sentry::metrics()->increment()`. You deploy. The numbers don't match. Of course they don't.

StatsD has been sampling your traffic since day one. You set `sample_rate: 0.1` on your high-frequency counter three years ago, added a comment saying "adjust before prod," and forgot about it. Sentry doesn't sample by default — it counts every call. Now your StatsD dashboard shows 500 events per minute and Sentry shows 5,000.

That's the first surprise. It's not the only one.

---

## The Sampling Problem

StatsD sampling is a client-side decision. When you call:

```php
$statsd->increment('http.requests', 1, 0.1);
```

Only 10% of calls actually fire a UDP packet. The StatsD server multiplies the received count by the inverse of the sample rate to estimate the true total. It's an approximation designed to reduce UDP traffic under load.

Sentry Metrics doesn't have this concept. When you call:

```php
\Sentry\metrics()->increment('http.requests');
```

Every call is recorded. Sentry aggregates locally in a 10-second window before flushing, so the network overhead is amortised — but the count is exact.

**Before you touch a single import statement**, audit every metric call in your codebase for its sample rate:

```bash
grep -rn 'statsd' src/ --include="*.php" | grep -E 'sample_rate|, 0\.'
```

For each metric with a sample rate below 1.0, the post-migration number will be higher — by exactly `1 / sample_rate`. A counter with `sample_rate: 0.5` will appear to double. Document this before you migrate, or you'll spend days convinced your new instrumentation is broken.

## Metric Types: The Mapping That Isn't Quite 1:1

StatsD has counters, gauges, timers, and sets. Sentry has counters, gauges, distributions, and sets. The names are similar enough to cause mistakes.

### Counter

StatsD `c` → Sentry `increment()`. Straightforward.

```php
// StatsD
$statsd->increment('orders.placed');

// Sentry
\Sentry\metrics()->increment('orders.placed');
```

### Timer → Distribution

StatsD timers (`ms`) are not the same as Sentry distributions. StatsD computes percentiles server-side from raw samples. Sentry distributions ship pre-aggregated histograms — they're accurate but the aggregation happens in the SDK, not on the backend.

```php
// StatsD
$statsd->timing('payment.duration', $durationMs);

// Sentry
\Sentry\metrics()->distribution(
    'payment.duration',
    $durationMs,
    MeasurementUnit\Duration::Millisecond,
);
```

The `MeasurementUnit` argument is worth paying attention to. Sentry uses it to display and convert values correctly in the UI. If you're measuring bytes, use `MeasurementUnit\Information::Byte`. If you omit it, Sentry treats the value as unitless and you lose axis labelling.

### Gauge

Same semantics — last-write-wins within an aggregation window. No surprises here.

```php
// StatsD
$statsd->gauge('queue.depth', $depth);

// Sentry
\Sentry\metrics()->gauge('queue.depth', $depth);
```

### Set

Both track unique values per interval. Sets are rarely used but the semantics are identical — unique count of distinct values flushed per window.

## Cardinality Explosion

StatsD tags (if your server supports them, e.g. DogStatsD) are typically low-cardinality: `env:prod`, `region:eu`. You keep them in check because StatsD backends can fall over with high-cardinality tag combinations.

Sentry has a hard limit on tag cardinality, but it's easy to blow past it when migrating. The temptation is to add tags that felt too expensive in StatsD — user IDs, request IDs, order IDs. Don't.

```php
// This will create a new metric series per user. Don't do it.
\Sentry\metrics()->increment('checkout.started', categories: [
    'user_id' => (string) $user->id,
]);

// This is fine.
\Sentry\metrics()->increment('checkout.started', categories: [
    'plan' => $user->plan,
    'country' => $user->country_code,
]);
```

Sentry enforces a limit on unique tag value combinations per metric. Exceed it and Sentry will start dropping data silently. Before migrating each metric, check the cardinality of every tag you plan to attach. If a tag has more than a few hundred distinct values in production, it doesn't belong on a metric — it belongs in a span or a log.

## Running Both in Parallel

Don't cut over all at once. Especially not across six services simultaneously.

The safest pattern is a thin wrapper that emits to both sinks during a transition window:

```php
final class Metrics
{
    public function increment(
        string $key,
        int $value = 1,
        array $tags = [],
        float $sampleRate = 1.0,
    ): void {
        // Existing StatsD call — preserve sample rate for parity
        statsd()->increment($key, $value, $sampleRate);

        // New Sentry call — only when sample rate is 1.0 to avoid count inflation
        if ($sampleRate === 1.0) {
            \Sentry\metrics()->increment($key, $value, tags: $tags);
        }
    }

    public function distribution(
        string $key,
        float $value,
        MeasurementUnit $unit,
        array $tags = [],
    ): void {
        // StatsD received timings in milliseconds, normalise here
        statsd()->timing($key, (int) $value);

        \Sentry\metrics()->distribution($key, $value, $unit, tags: $tags);
    }
}
```

The key decision in the wrapper above: if a metric has a sample rate below 1.0, skip the Sentry emission until you've resolved the sampling discrepancy. Either remove the sample rate (and accept the load) or document that the post-migration numbers will be higher and treat it as a known delta.

## Coordinating Across Multiple Services

This is where migrations fail in practice. You have six services. You update one. Now your StatsD dashboard aggregates all six, and your Sentry dashboard only shows one. Neither view is complete. Your oncall engineer looks at the wrong dashboard at 2am.

A few things that help:

**Tag metrics with a migration status.** Add a `source` tag during the parallel window — `source:statsd_only`, `source:dual`, `source:sentry_only`. This lets you filter in dashboards and know at a glance which services have migrated.

**Migrate one metric at a time across all services, not all metrics in one service.** If `http.requests` is your most critical metric, migrate it across all six services in a single coordinated deploy, verify parity, then move to the next metric. Migrating service by service leaves you with fragmented coverage for every metric.

**Create a migration tracking table.** Before writing a line of code:

| Metric             | Services               | Sample Rate | Tags           | Sentry Status |
| ------------------ | ---------------------- | ----------- | -------------- | ------------- |
| `http.requests`    | api, worker, scheduler | 0.1         | method, status | parallel      |
| `queue.depth`      | worker                 | 1.0         | queue_name     | cutover       |
| `payment.duration` | api                    | 1.0         | gateway        | not started   |

This table is the source of truth for your migration. Update it as MRs land. It prevents two engineers from independently migrating the same metric with different tag schemas.

## Verifying Parity: What "Close Enough" Means

For metrics with `sample_rate: 1.0`, exact parity is achievable. Sentry's local aggregation introduces a small delay (up to 10 seconds) and may bucket differently from your StatsD flush interval, but over a 5-minute window the counts should match within 1–2%.

For sampled metrics, you're comparing an estimate (StatsD) against an exact count (Sentry). Don't expect the numbers to match — expect the ratio to be stable. If StatsD reports 500 and Sentry reports 5,000 for a `sample_rate: 0.1` metric, that's parity. Build your verification around ratios, not absolutes.

A pragmatic parity check for counters:

```
sentry_count / statsd_count ≈ 1 / sample_rate  (±5%)
```

For distributions, compare p50 and p95 over a one-hour window. Minor divergence is expected because StatsD computes percentiles from raw samples and Sentry uses histogram buckets — but large divergence (>10% on p95) indicates a problem worth investigating before cutover.

---

## Cutting Over

Once a metric has passed the parity check across all services, remove the StatsD emission from the wrapper. Don't leave dual emission running indefinitely — it burns resources and keeps you dependent on the StatsD infrastructure you're trying to retire.

Cutover order matters. Start with low-traffic, low-criticality metrics to build confidence. End with the metrics that feed your SLOs. By the time you're cutting over the critical ones, you'll have already debugged the edge cases on the cheap ones.

After cutover, update your dashboards and alerts to point at Sentry before removing the StatsD infrastructure. "We'll do the dashboards later" is how you end up with stale alerts pointing at a dead host six months later.

---

The migration itself is a few hours of work per service. The coordination, verification, and dashboard updates are where the time actually goes. Plan for it.
