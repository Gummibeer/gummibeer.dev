You called `Queue::fake()`. You have a mock. Your test passes locally and explodes on CI. Welcome to the intersection of Laravel fakes and PHPUnit mocks.

This isn't a race condition. It isn't a flaky environment variable. It's a predictable set of failure modes that stem from how Laravel fakes interact with the service container — and most of them can be avoided once you know what's actually happening.

## What `Queue::fake()` Actually Does

Calling `Queue::fake()` swaps the bound `Illuminate\Queue\QueueManager` in the container for an instance of `Illuminate\Support\Testing\Fakes\QueueFake`. That fake records dispatched jobs in memory instead of pushing them onto a real queue.

The critical word is _swaps_. The container is not paused. Any other binding that was registered before or after `Queue::fake()` is still live. If your code under test resolves a service that internally dispatches a job, it will hit the fake — but only if that resolution happens _after_ you called `Queue::fake()`.

This matters more than it sounds.

```php
// This works — fake is in place when the controller dispatches
Queue::fake();
$this->post('/orders', $payload);
Queue::assertPushed(ProcessOrder::class);
```

```php
// This breaks in subtle ways — the service was resolved before the fake was registered
$service = app(OrderService::class); // container resolves and caches instance
Queue::fake();
$service->place($payload);           // might use a cached queue connection
Queue::assertPushed(ProcessOrder::class); // fails
```

Laravel's container does not cache resolved instances for transient bindings by default, so in practice this second case is rarer than it looks. But singletons are a different story. If `OrderService` is bound as a singleton and it receives a `QueueManager` dependency at construction time, it holds a reference to the _real_ manager — and `Queue::fake()` replacing the binding won't affect it.

**Fix:** Call `Queue::fake()` in `setUp()`, before anything touches the container. Or — if you need the singleton rebound — call `$this->app->forgetInstance(OrderService::class)` after faking.

## The Assertion Order Trap

This one is embarrassingly common, including in code I've written myself.

```php
public function test_order_dispatches_processing_job(): void
{
    Queue::fake();
    Queue::assertPushed(ProcessOrder::class); // asserts BEFORE the code runs
    $this->post('/orders', $this->validPayload());
}
```

That assertion will pass on an empty queue because... nothing has been pushed yet, so `assertPushed` does nothing? Actually no — `assertPushed` throws when the job was _not_ found. So this test fails immediately. But swap the condition to `assertNotPushed` and you have a green test that is testing absolutely nothing.

The rule is simple: **run the code first, assert after.**

```php
public function test_order_dispatches_processing_job(): void
{
    Queue::fake();
    $this->post('/orders', $this->validPayload());
    Queue::assertPushed(ProcessOrder::class);
}
```

## `Bus::fake()` and `Queue::fake()` Are Not the Same Thing

This is the confusion that trips people up most. `Queue::fake()` intercepts jobs pushed via the queue (think `dispatch()` or `SomeJob::dispatch()`). `Bus::fake()` intercepts commands dispatched through the command bus (think `Bus::dispatch()` or the `Dispatchable` trait's `dispatch` static method, which _also_ goes through the bus).

The overlap is non-obvious because `SomeJob::dispatch()` calls `Bus::dispatch()` under the hood — which means `Bus::fake()` _also_ catches queue-dispatched jobs. `Queue::fake()` does not catch synchronous commands dispatched via `Bus::dispatchNow()` or `Bus::dispatchSync()`.

Here is what each fake catches:

| Dispatch method                | `Queue::fake()` | `Bus::fake()` |
| ------------------------------ | --------------- | ------------- |
| `dispatch(new MyJob)`          | yes             | yes           |
| `MyJob::dispatch()`            | yes             | yes           |
| `Bus::dispatch(new MyJob)`     | yes             | yes           |
| `Bus::dispatchNow(new MyJob)`  | no              | yes           |
| `Bus::dispatchSync(new MyJob)` | no              | yes           |
| `Queue::push(new MyJob)`       | yes             | no            |

If you are testing a controller that dispatches a job to a specific queue using `Queue::push()` directly, `Bus::fake()` will not catch it. If you care about sync dispatch, reach for `Bus::fake()`.

If you need both — use both. They compose without conflict:

```php
Queue::fake();
Bus::fake();
```

Just be aware that your assertions need to match which fake intercepted the dispatch.

## Mocking the Job vs Asserting Dispatch

There are two distinct things you might want to verify:

1. That a job was dispatched with the right arguments
2. That the job's logic does the right thing when it runs

These are separate concerns and should live in separate tests. Mixing them in one test creates friction.

**Assert dispatch in integration tests:**

```php
public function test_places_order_and_dispatches_processing_job(): void
{
    Queue::fake();

    $this->post('/orders', [
        'product_id' => 42,
        'quantity'   => 2,
    ]);

    Queue::assertPushed(ProcessOrder::class, function (ProcessOrder $job): bool {
        return $job->orderId === Order::latest()->first()->id;
    });
}
```

The closure on `assertPushed` lets you inspect the job's public properties and confirm the right data was passed in. This is usually enough.

**Mock the job when you need to prevent real side effects:**

If your test is not about the job at all — you're testing something else that happens to dispatch a job — mocking the job class can be cleaner than faking the entire queue:

```php
$this->mock(ProcessOrder::class)
     ->shouldReceive('handle')
     ->once();
```

But this only works for synchronous dispatch (`dispatchNow`/`dispatchSync`). For async dispatch through the queue, the job instance is serialized and re-instantiated — your mock is gone. Use `Queue::fake()` for async dispatch and reserve mocking for sync.

## Isolated Job Tests: Calling `handle()` Directly

Sometimes the cleanest option is to skip fakes and mocks entirely and just call the job:

```php
public function test_process_order_sends_confirmation_email(): void
{
    Mail::fake();

    $order = Order::factory()->create();
    (new ProcessOrder($order->id))->handle(
        app(OrderRepository::class),
        app(MailService::class),
    );

    Mail::assertSent(OrderConfirmation::class, fn ($mail) => $mail->hasTo($order->email));
}
```

This is fast. It's readable. It doesn't care about how the job was dispatched — only what it does.

The tradeoff is that `handle()` is not called the same way the queue worker calls it. The worker uses the container to inject dependencies, handles exceptions differently, processes `$middleware` on the job class, respects `$tries` and `$backoff`, and so on. Calling `handle()` directly skips all of that.

For unit-testing the job's business logic, direct invocation is fine. For testing that retries work correctly or that middleware is applied, you need a running queue worker — which is a different kind of test entirely.

## Putting It Together: A Pattern That Holds Up

Here is a structure that avoids the common failure modes:

```php
use Illuminate\Support\Facades\Queue;
use Tests\TestCase;

class PlaceOrderTest extends TestCase
{
    protected function setUp(): void
    {
        parent::setUp();
        Queue::fake(); // always before anything touches the container
    }

    public function test_dispatches_processing_job_on_success(): void
    {
        $this->post('/orders', $this->validPayload())
             ->assertCreated();

        Queue::assertPushed(
            ProcessOrder::class,
            fn (ProcessOrder $job) => $job->orderId > 0
        );
    }

    public function test_does_not_dispatch_job_when_validation_fails(): void
    {
        $this->post('/orders', []) // missing required fields
             ->assertUnprocessable();

        Queue::assertNotPushed(ProcessOrder::class);
    }

    private function validPayload(): array
    {
        return ['product_id' => 1, 'quantity' => 1];
    }
}
```

And separately, the job's own test:

```php
class ProcessOrderTest extends TestCase
{
    public function test_marks_order_as_processed_and_sends_email(): void
    {
        Mail::fake();

        $order = Order::factory()->create(['status' => 'pending']);

        (new ProcessOrder($order->id))->handle(
            app(OrderRepository::class),
        );

        $this->assertDatabaseHas('orders', ['id' => $order->id, 'status' => 'processed']);
        Mail::assertSent(OrderConfirmation::class);
    }
}
```

Dispatch verification lives in the HTTP/service test. Job behavior verification lives in the job test. Each test knows exactly what it is responsible for.

## The Short Version

- Call `Queue::fake()` in `setUp()`, not mid-test.
- Assert _after_ the code runs, not before.
- Know which fake intercepts which dispatch method — `Queue::fake()` and `Bus::fake()` have different coverage.
- Don't mock job classes for async dispatch — the mock won't survive serialization.
- Use `(new MyJob())->handle()` for fast job logic tests, but know its limits.

Queue testing in Laravel is not hard. It becomes hard when you mix concerns and trust that the fakes are magic. They're not — they're container swaps, and the container still follows its rules.
