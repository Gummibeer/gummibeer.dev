I play tabletop RPGs. I also write software for a living. These two facts occasionally collide in interesting ways.

[Archivist AI](https://www.myarchivist.ai) is a TTRPG campaign memory platform. It listens to your sessions — Discord, uploaded audio, raw notes — transcribes them, extracts characters, factions, locations, items, quests, beats, moments, and builds a living searchable compendium of your campaign. 16,000+ sessions processed, 230,000+ compendium entries, 130,000+ questions answered. It's genuinely good.

What I wanted was to bring my campaign data into the AI tools I already live in — Claude, Cursor — not to click through a web UI when I needed context. The [Model Context Protocol](https://modelcontextprotocol.io) exists for exactly this use case. Archivist had a REST API. The connection was obvious.

This is the story of building [mcp.myarchivist.ai](https://github.com/Astrotomic/mcp.myarchivist.ai).

---

## The setup

Archivist has a developer API — campaigns, characters, sessions, beats, moments, factions, locations, items, quests, journals, entity links. Full CRUD, plus a RAG `/v1/ask` endpoint that answers natural-language questions about your campaign via their internal vector search.

An MCP server is a process that speaks the Model Context Protocol, exposing _tools_ (functions the LLM can call), _resources_ (documents it can read), and _prompts_ (pre-built prompt templates). The MCP client — Claude Desktop, Cursor, Windsurf, ChatGPT — handles the plumbing. The server just has to speak the protocol.

The missing piece between the Archivist API and an MCP client was a thin proxy that translates MCP tool calls into authenticated API calls and returns the structured results.

I've been maintaining [Astrotomic](https://astrotomic.info), an open-source developer collective for Laravel packages, for years. Laravel was the obvious choice for the server. Taylor Otwell had just open-sourced [laravel/mcp](https://github.com/laravel/mcp), a first-party package for building MCP servers in Laravel. New package, minimal docs, but it was PHP and it was Laravel, so I'd figure it out.

## Before writing a line of code: the API key conversation

Before touching the keyboard I pinged Greg — the person behind Archivist AI — to let him know what I was planning. His reaction:

> "I did NOT know this lol. That's awesome, though! Let me know if I can help at all with that. This is the kind of stuff I was hoping would happen when we got the developer API up."

First thing I flagged was the trust model. An MCP server that holds your API key is technically a man-in-the-middle. The Archivist API key at the time was unscoped — full read/write access. Anyone hosting an MCP server with your key could do anything the API permitted.

My answer to this was structural: the MCP server is a stateless proxy. No database. No persistent storage. The API key lives only in memory for the duration of a single tool call — milliseconds. There's nothing to exfiltrate. But I also made the decision early: **read-only only, v1**. No write endpoints until people actually need them, and until we've had more time to think through the permission model.

Greg's response was that they have OAuth built internally (it powers their Alexa skill and some in-development features), and it would be a better auth method than raw API keys long-term. That went on the roadmap.

For now: API key in the `Authorization: Bearer` header, stateless proxy, read-only.

## The stack

- **Framework:** Laravel 13
- **MCP package:** [laravel/mcp](https://github.com/laravel/mcp)
- **Transport:** Streamable HTTP
- **Architecture:** pure proxy — no own database, no own data storage
- **Auth:** Bearer token (v1), OAuth 2.0 PKCE (added later)

`laravel/mcp` follows the same conventions as the rest of Laravel. Tools are classes. Resources are classes. The server registers them and handles all the protocol-level plumbing. You focus on implementing `handle()`.

A tool looks like this:

```php
<?php

namespace App\Mcp\Tools\Characters;

use App\Mcp\Actions\Characters\GetCharacterAction;
use Laravel\Mcp\Server\Tool;
use Laravel\Mcp\Server\Content\TextContent;

class GetCharacterTool extends Tool
{
    public function name(): string
    {
        return 'get_character';
    }

    public function description(): string
    {
        return 'Get a character by ID including aliases, backstory, and speaker linkage.';
    }

    public function inputSchema(): array
    {
        return [
            'type' => 'object',
            'required' => ['campaign_id', 'character_id'],
            'properties' => [
                'campaign_id' => [
                    'type' => 'string',
                    'description' => 'The campaign ID this character belongs to.',
                ],
                'character_id' => [
                    'type' => 'string',
                    'description' => 'The character ID to fetch.',
                ],
            ],
        ];
    }

    public function handle(array $arguments): array
    {
        return [
            TextContent::make(
                json_encode(
                    app(GetCharacterAction::class)->execute(
                        campaignId: $arguments['campaign_id'],
                        characterId: $arguments['character_id'],
                    ),
                    JSON_PRETTY_PRINT
                )
            ),
        ];
    }
}
```

The action delegates to the Archivist REST API with the user's bearer token extracted from the incoming MCP request's authorization header. The tool just calls the action, serializes the result, and returns it as a text content block.

The server registration wires it all up:

```php
<?php

namespace App\Providers;

use App\Mcp\Tools;
use Illuminate\Support\ServiceProvider;
use Laravel\Mcp\Facades\McpServer;

class McpServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        McpServer::name('Archivist AI')
            ->version('1.0.0')
            ->tool(Tools\Campaigns\ListCampaignsTool::class)
            ->tool(Tools\Campaigns\GetCampaignTool::class)
            ->tool(Tools\Campaigns\GetCampaignStatsTool::class)
            ->tool(Tools\Characters\ListCharactersTool::class)
            ->tool(Tools\Characters\GetCharacterTool::class)
            ->tool(Tools\Sessions\ListSessionsTool::class)
            ->tool(Tools\Sessions\GetSessionTool::class)
            ->tool(Tools\Sessions\GetSessionCastAnalysisTool::class)
            // ... 17 more tools
        ;
    }
}
```

## The token efficiency problem

Getting the basic tools working was the easy part. Making them _good_ was harder.

The biggest problem: the Archivist API, at the time, had almost no filtering or sorting parameters. No `order_by`, no `limit`, no `search` on most collection endpoints.

This creates a real problem for MCP tools. When an LLM is asked "what happened in the last three sessions?", the tool has to either:

1. Fetch every session (all 55 of them), pass them all to the LLM, and have the LLM sort through them — burning dozens of tokens on session objects the question didn't need, or
2. Implement the filtering on the tool side using PHP collections, adding latency and keeping response sizes down

Option 2 is the practical choice until the API adds native filter support. But it means the tool layer becomes more than a dumb proxy.

Character search exists in the API. Location search doesn't. To find a location by name, the LLM currently has to paginate through every location in the compendium and search locally. That's a token footgun.

I flagged this to Greg:

> "The location list has no search while the character list has. So to get a location by name the LLM has to fetch all pages and search locally — massive token waste."

Greg confirmed this is something they want to fix at the API level. In the meantime, the tool-level collection approach works, just not as cleanly as a server-side filter would.

The conversation about filters opened into something broader:

> "I think if I'm thinking from MCP perspective there will be all kind of things needed. Like give me last X. Or first Y. But also give me all with CharB. Give me all after date Z."

These are very natural LLM queries that require very different capabilities from a REST API designed around pagination. MCP makes these requirements visible in a way that a traditional API client wouldn't.

## The auth story: why Claude Desktop requires OAuth

Bearer token auth works fine for Cursor, Windsurf, and ChatGPT. But Claude Desktop specifically only supports OAuth connections for remote MCP servers. No OAuth, no Claude Desktop.

This matters because a large chunk of the target audience for an Archivist MCP are exactly the kind of people who use Claude Desktop. So OAuth wasn't optional.

Greg had OAuth infrastructure already — it powers their Alexa skill. The question was how to wire it up for MCP.

MCP's OAuth flow uses the [Authorization Code with PKCE](https://oauth.net/2/pkce/) pattern. The server exposes a `/.well-known/oauth-authorization-server` metadata endpoint. The client discovers the auth server, redirects the user to sign in, exchanges the code for a token, and uses that token on subsequent requests. The server validates the token on every request.

The final auth setup:

- **OAuth 2.0 with PKCE** — recommended for interactive clients (Claude Desktop, etc.)
- **Bearer token** — for programmatic access and clients that support it natively
- Supported scopes: `profile`, `worlds_read`, `sessions_read`, `characters_read`
- Metadata endpoint: `https://mcp.myarchivist.ai/.well-known/oauth-authorization-server`

One practical note on security that came up in conversation: because the MCP server is stateless and doesn't store anything, the "full access API key" concern is somewhat mitigated. But the shift to OAuth also gives proper scope boundaries — users can grant the MCP read-only access to specific data types without the key being able to touch write endpoints at all.

## Finding and fixing bugs in laravel/mcp

Shipping a real project with a new package will always shake out gaps. I hit three in `laravel/mcp` during development and filed issues.

### `TestResponse::dump()` doesn't return `$this` — issue #222

Laravel's HTTP test infrastructure lets you chain `->dump()` before assertions to inspect the response without breaking the chain:

```php
$response->dump()->assertOk();
```

`laravel/mcp`'s `TestResponse::dump()` returned `void`, which breaks the chain:

```php
McpServer::tool(GetSessionTool::class, ['session_id' => 'abc'])
    ->dump()
    ->assertOk(); // TypeError: null->assertOk()
```

[Filed the issue](https://github.com/laravel/mcp/issues/222), submitted [PR #223](https://github.com/laravel/mcp/pull/223) with the fix, and Taylor closed both within the hour.

### Resource testing with URI templates fails — issue #221

MCP resources can have URI templates — `sessions/{id}/summary` — that take path parameters. When testing a resource with an argument:

```php
McpServer::resource(SessionSummaryResource::class, ['id' => 'abc']);
```

...it threw `Invalid params: The id field must be a string.` even when `'abc'` is clearly a string.

The bug was in `Resource::toMethodCall()`, which returned the raw URI template without resolving the variables. The `ReadResource::handle()` method then tried to match the unresolved template against the resolved URI from the test arguments, and they didn't match.

[Filed issue #221](https://github.com/laravel/mcp/issues/221). A contributor picked it up in [PR #225](https://github.com/laravel/mcp/pull/225) and Taylor closed it the same day.

### Embedded resource responses — issue #224 (open)

MCP allows tool responses to include _embedded resources_ — structured content blocks that reference a resource URI and include the resolved content inline. This is useful for prompts that want to pull in a session summary or character sheet as part of the context.

The `laravel/mcp` package already supports resource _links_ (a reference to a resource URI) but not embedded resources (a reference plus the resolved content). I implemented it locally for the Archivist MCP and [filed issue #224](https://github.com/laravel/mcp/issues/224) with the proposed API and working implementation:

```php
Response::embeddedResource(
    resource: app(SessionSummaryResource::class),
    arguments: ['session_id' => $session_id],
)
```

The underlying implementation resolves the URI template, calls the resource's `handle()` method, and packages the result as an `EmbeddedResource` content block:

```php
public static function embeddedResource(Resource $resource, array $arguments = []): self
{
    $uri = $resource->uri();
    if ($resource instanceof HasUriTemplate) {
        $uri = strtr(
            $uri,
            collect($arguments)
                ->keyBy(fn (mixed $_, string $key): string => Str::of($key)->start('{')->finish('}'))
                ->all(),
        );
    }

    $text = $resource->handle(new Request($arguments))->content();

    return new self(new EmbeddedResource(
        uri: $uri,
        text: $text,
        mimeType: $resource->mimeType(),
    ));
}
```

This is still open. The package needs a few more variations for the public API (different resource input formats, resource instances vs class names), but the mechanics work.

## API inconsistencies surfaced by the test suite

I built a full test suite against the live API using my own campaign data. The tests assert the shape of every response — every property in every DTO. This is the kind of thing that's very easy to skip when you're building a happy-path integration, and it found real problems.

When I ran the Gummibeer test suite against Greg's own API key, three entity types failed with `Property [approved] does not exist`:

- `GetFactionToolTest`
- `GetItemToolTest`
- `GetLocationToolTest`

And `GetQuestToolTest` failed with `Property [objective_count] does not exist`.

The root issue: the `list` endpoints for factions, items, and locations included an `approved` attribute in the response. The `get` endpoint for the same entities didn't include it. Both should be consistent, but it turned out `approved` was a server-side filter — it controls whether an entity is visible to users — and wasn't something consumers of the API would ever need to act on. Greg confirmed it would be removed from the public API entirely.

`objective_count` was a similar story — an internal aggregation field that had leaked into the list response but wasn't being hydrated on the single-entity get.

This is exactly the kind of drift that happens between list and detail endpoints in any non-trivial API, and it's easy to miss without a test harness that compares both shapes. Greg's reaction was to use the test output as input for an in-progress API reconciliation effort:

> "I def want to remove the internal artifacts, standardize naming conventions (e.g. `world_id` vs `campaign_id`), hydrate the objects in the summary endpoints, etc."

The test suite became a useful tool for the API team, not just for the MCP server.

## What 25 tools actually looks like

The full tool surface:

**Campaigns** — `list_campaigns`, `get_campaign`, `get_campaign_stats`

**Characters** — `list_characters` (filter by name, type, approval), `get_character` (includes aliases, backstory, speaker linkage)

**Sessions** — `list_sessions` (filter by type, public-only), `get_session` (optional beats and moments), `get_session_cast_analysis` (talk-share breakdown)

**Story structure** — `list_beats`, `get_beat`, `list_moments`, `get_moment`

**World building** — `list_factions`, `get_faction`, `list_locations` (nested: cities, taverns, dungeons), `get_location`, `list_items`, `get_item`

**Quests** — `list_quests` (filter by status, category), `get_quest` (objectives, progress, related entities, session provenance)

**Journals** — `list_journals`, `get_journal` (full content with permissions), `list_journal_folders`, `get_journal_folder`

**Relationships** — `list_links` (filter by source/target entity and alias)

All tools are read-only and idempotent. The LLM can call `get_character` a hundred times and nothing changes on the server.

The journal tools are the ones I haven't tested against my own data yet — I don't have any journal entries in my campaign. They exist in the codebase and the schema is right, but the test coverage for that group is lower than the rest.

## Early user feedback

The first non-me tester (Treagon from the Archivist Discord) set it up on Claude Desktop and reported it working well. I asked for specifics:

> "Could you share some prompts you did? And which tools Claude picked and how well it performed finding the facts/answering your questions? If possible also the token consumption? Right now I assume it being pretty wasteful on tokens."

Token consumption is the thing I'm most uncertain about. The current tools return full API responses — no trimming, no field selection. For a simple "who is this character?" prompt, you get the full character object including everything the API returns. That's correct and complete, but it's not minimal.

The right answer long-term is probably smarter tool descriptions that guide the LLM to only call what it needs, plus API-level filter support so list tools return fewer items. For now, it works and the answers are good.

## What's next

Three things are on the roadmap, roughly in order:

**Filters and sorting at the API level.** The MCP makes the gaps in the REST API very visible. "Last 3 sessions", "all quests in progress", "characters mentioning this faction" — these are natural LLM queries that currently require either fetching everything or implementing collection-level filtering in the tool. Moving that to the API saves tokens and makes the tools cleaner.

**Write operations (v2).** All the dangerous endpoints — create character, update quest, add beat — are deliberately excluded from v1. Once the read-only version has been in the wild long enough to establish trust and identify the real use cases, write tools can be added incrementally. The most useful first candidate is probably session notes or journal entries, where the LLM could help a GM write up a session summary after a game.

**oauth support stabilization.** The OAuth flow works, but there are rough edges around token refresh and client registration. This needs more real-world usage to shake out fully.
