Every internal service in our stack calls the same monolith. Same base URL, same auth, same retry policy, same timeouts. For a while, each call site configured all of that itself.

This post is about the macro we eventually landed on, and specifically about the one design detail that made it work cleanly for both one-shot requests and concurrent pools.

---

## The first pass: just centralize the configuration

The starting point was simple. We had a service provider that registered an `Http::monolith()` macro — a factory for a pre-configured `PendingRequest`. Call it, chain the endpoint, done.

```php
Http::macro('monolith', function (): PendingRequest {
    return Http::baseUrl(config('services.monolith.url'))
        ->acceptJson()
        ->asJson()
        ->throw()
        ->connectTimeout(5)
        ->timeout(15)
        ->retry(
            times: 2,
            sleepMilliseconds: 500,
            when: fn (Throwable $exception): bool =>
                $exception instanceof ConnectionException
                || ($exception instanceof RequestException
                    && in_array($exception->getCode(), [502, 503, 504], true))
        )
        ->withBasicAuth(
            username: config('services.internal.user'),
            password: config('services.internal.password')
        )
        ->when(
            value: app()->environment('local'),
            callback: fn (PendingRequest $request): PendingRequest => $request->withoutVerifying()
        );
});
```

Single requests got beautifully slim:

```php
$response = Http::monolith()
    ->timeout(20)
    ->get('internal/listings/' . $listingId);
```

Configuration in one place, every call site just focuses on the endpoint and any per-request overrides. This was an improvement.

Then we needed concurrent requests.

---

## The pool problem

Fetching data for a list of IDs is a common pattern in service-oriented apps. The naive approach fetches them sequentially — or worse, fires N individual requests one at a time using a `foreach`. Laravel's `Http::pool()` exists precisely to run those concurrently.

The first pooled implementation of our batch fetcher looked roughly like this:

```php
public function execute(Collection $ids): Collection
{
    if ($ids->isEmpty()) {
        return collect();
    }

    $chunks = $ids->chunk(self::CHUNK_SIZE);
    $totalChunks = $chunks->count();

    $result = collect();

    $chunks->each(function (Collection $chunk, int $index) use ($result, $totalChunks): void {
        // Process each chunk sequentially with a 1-second delay between them
        // to avoid overwhelming the upstream service
        $responses = Http::pool(fn (Pool $pool) => $chunk->map(
            fn (int $id) => $pool
                ->as((string) $id)
                ->baseUrl(config('services.monolith.url'))
                ->acceptJson()
                ->asJson()
                ->throw()
                ->connectTimeout(5)
                ->timeout(20)
                ->retry(
                    times: 2,
                    sleepMilliseconds: 500,
                    when: fn (Throwable $e): bool =>
                        $e instanceof ConnectionException
                        || ($e instanceof RequestException
                            && in_array($e->getCode(), [502, 503, 504], true))
                )
                ->withBasicAuth(
                    username: config('services.internal.user'),
                    password: config('services.internal.password')
                )
                ->when(
                    value: app()->environment('local'),
                    callback: fn (PendingRequest $request): PendingRequest => $request->withoutVerifying()
                )
                ->get("internal/listings/{$id}")
        )->toArray());

        // ... parse responses ...

        if ($index < $totalChunks - 1) {
            usleep(1_000_000);
        }
    });

    return $result;
}
```

The macro existed. We just couldn't use it here.

`Http::pool()` gives you a `Pool` instance. `$pool->as($key)` returns a `PendingRequest` that's wired into the pool's execution. A `PendingRequest` you got somewhere else — like from `Http::monolith()` — is a different instance entirely. Passing it into the pool after the fact doesn't work. The pool needs to own the request from the start.

So the entire client configuration was inlined on every pool slot. Retry policy, auth, base URL, SSL override — all of it, duplicated.

---

## The fix: accept the PendingRequest from the caller

The insight was simple: if `Http::pool()` needs to own the `PendingRequest`, then the macro should configure an existing one rather than always creating a new one.

```php
Http::macro('monolith', function (?PendingRequest $request = null): PendingRequest {
    return ($request ?? Http::createPendingRequest())
        ->baseUrl(config('services.monolith.url'))
        ->acceptJson()
        ->asJson()
        ->throw()
        ->connectTimeout(5)
        ->timeout(15)
        ->retry(
            times: 2,
            sleepMilliseconds: 500,
            when: fn (Throwable $exception): bool =>
                $exception instanceof ConnectionException
                || ($exception instanceof RequestException
                    && in_array($exception->getCode(), [502, 503, 504], true))
        )
        ->withBasicAuth(
            username: config('services.internal.user'),
            password: config('services.internal.password')
        )
        ->when(
            value: app()->environment('local'),
            callback: fn (PendingRequest $request): PendingRequest => $request->withoutVerifying()
        );
});
```

When called without arguments, `Http::createPendingRequest()` produces a fresh one — same as before. When called with a `$pool->as($key)` slot, it applies all the configuration to that slot and returns it. The pool still owns the request object. The macro just dressed it.

Single requests are unchanged:

```php
$response = Http::monolith()
    ->timeout(20)
    ->get('internal/listings/' . $listingId);
```

Pool slots are now:

```php
$responses = Http::pool(function (Pool $pool) use ($ids): array {
    return $ids
        ->chunk(self::CHUNK_SIZE)
        ->map(fn (Collection $chunk, int $index): PendingRequest =>
            Http::monolith($pool->as((string) $index))
                ->timeout(30)
                ->get('internal/listings/batch', [
                    'ids' => $chunk->values()->all(),
                ])
        )
        ->values()
        ->all();
});
```

The client configuration is in exactly one place. The pool slot gets it via the macro. Single-request callers get it the same way they always did. The call sites are minimal and identical in shape regardless of which mode they're using.

## What the batch action looks like in full

```php
<?php

namespace App\Actions;

use App\ValueObjects\Listing;
use Illuminate\Http\Client\Pool;
use Illuminate\Http\Client\RequestException;
use Illuminate\Http\Client\Response;
use Illuminate\Support\Collection;
use Illuminate\Support\Facades\Http;
use Illuminate\Support\Facades\Log;
use Throwable;

class FetchListingsByIds extends Action
{
    private const int CHUNK_SIZE = 100;

    /**
     * Maximum concurrent requests per pool. Pools are executed sequentially
     * to cap total concurrency against upstream.
     *
     * TODO: Once we upgrade to Laravel 12, collapse this to a single pool
     * with the native concurrency limit.
     */
    private const int POOL_CONCURRENCY = 10;

    /**
     * @param  Collection<int, int>  $ids
     * @return Collection<int, Listing>
     */
    public function execute(Collection $ids, bool $includeDeleted = false): Collection
    {
        if ($ids->isEmpty()) {
            return collect();
        }

        return $ids
            ->chunk(self::CHUNK_SIZE * self::POOL_CONCURRENCY)
            ->flatMap(function (Collection $superChunk) use ($includeDeleted): array {
                /** @var array<int, Response|Throwable> $responses */
                $responses = Http::pool(function (Pool $pool) use ($superChunk, $includeDeleted): array {
                    return $superChunk
                        ->chunk(self::CHUNK_SIZE)
                        ->map(fn (Collection $chunk, int $index): PendingRequest =>
                            Http::monolith($pool->as((string) $index))
                                ->timeout(30)
                                ->get('internal/listings/batch', [
                                    'ids' => $chunk->values()->all(),
                                    'include_deleted' => $includeDeleted ? '1' : '0',
                                ])
                        )
                        ->values()
                        ->all();
                });

                return $responses;
            })
            ->flatMap(fn (Response|Throwable $response): Collection => $this->parseResponse($response))
            ->keyBy(fn (Listing $listing): int => $listing->getId());
    }

    /**
     * @return Collection<int, Listing>
     */
    private function parseResponse(Response|Throwable $response): Collection
    {
        if ($response instanceof RequestException && $response->response->notFound()) {
            return collect();
        }

        if ($response instanceof Throwable) {
            report($response);

            return collect();
        }

        if ($response->notFound()) {
            return collect();
        }

        if (! $response->successful()) {
            Log::warning('Failed to batch-fetch listings', [
                'status' => $response->status(),
            ]);

            return collect();
        }

        return collect($response->json('data', []))
            ->map(function (array $data): ?Listing {
                try {
                    return Listing::fromArray($data);
                } catch (Throwable $e) {
                    report($e);

                    return null;
                }
            })
            ->filter()
            ->values();
    }
}
```

The `POOL_CONCURRENCY` cap is a workaround for Laravel 11, which has no native concurrency limit on `Http::pool()`. The outer `chunk(CHUNK_SIZE * POOL_CONCURRENCY)` creates groups of up to 1000 IDs that each become a single pool of up to 10 concurrent requests. Groups run sequentially. When Laravel 12 lands with a native pool concurrency limit, the outer layer collapses.

## Testing the macro

In tests, `Http::fake()` handles the endpoint matching and you don't need to verify the macro configuration specifically. But when you want to confirm the macro is wired correctly across features, a minimal stub works:

```php
Http::macro('monolith', function (?PendingRequest $request = null): PendingRequest {
    return ($request ?? Http::createPendingRequest())
        ->baseUrl('http://monolith.test');
});
```

This gives you a valid `PendingRequest` that the pool can own, without the retry/auth/SSL configuration that would interfere with test doubles.

## What this pattern generalises to

The optional `?PendingRequest` parameter isn't specific to pools. Any caller that already holds a `PendingRequest` — a middleware that's already started configuring a request, a test that built a stub, a factory that creates clients in a specific way — can pass it in, and the macro applies its configuration on top.

The macro becomes a "configure this request as if it's talking to Service X" function rather than a "create a request to Service X" function. The distinction matters when the caller needs ownership of the underlying object.

We have the same pattern on our other service macros. The signature is always the same:

```php
Http::macro('payments', function (?PendingRequest $request = null): PendingRequest {
    return ($request ?? Http::createPendingRequest())
        ->baseUrl(config('services.payments.url'))
        // ...
});
```

Every service, same shape. `Http::payments($pool->as($key))` works everywhere a pool slot needs it.

## The one-line version of this post

`Http::macro` accepts `?PendingRequest $request = null`, uses `$request ?? Http::createPendingRequest()` as its base, and suddenly the same macro handles both `Http::monolith()->get(...)` and `Http::monolith($pool->as($key))->get(...)`. All configuration in one place. Pool and single-request call sites are identical in shape.
