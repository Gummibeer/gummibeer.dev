All identifiers, URLs, page structures, and command examples in this article are synthetic or explicit placeholders. No campaign or session content from the source workflow appears here.

I keep my tabletop RPG session data in Archivist and my campaign wiki in Notion.

Archivist is where the raw material becomes structured campaign memory: a session title, summary, handout, beats, moments, and transcript. Notion is where the campaign becomes useful at the table: session pages, personal notes, links to characters and locations, review status, and a structure that has grown with the campaign.

The obvious problem was that these two systems did not share a publish button.

My first solution used an AI agent as the integration layer. The agent read one session through MCP, inspected an existing Notion page, transformed the data, and wrote the result back. It worked. Then I tried to process a batch of old sessions and learned the important distinction between a successful agent task and a reliable data pipeline.

The final workflow now has three layers:

1. A Cursor skill resolves the user's intent and invokes the correct operation.
2. A deterministic Python script owns the Archivist-to-Notion sync.
3. A separate Laravel Zero command offers an interactive, read-only export to Notion-ready Markdown.

This is the story of how the workflow evolved, why the agent moved out of the data plane, and what I learned about syncing structured data into a human-edited Notion wiki without destroying the parts that make it human.

## The real requirement was publishing, not exporting

At first, "copy the session from Archivist into Notion" sounded like a normal export task. Fetch JSON, render Markdown, write a page.

That description missed most of the hard parts.

The target was not an empty folder or a generated static site. It was an existing campaign wiki. Every session page already had meaning:

- a page title and date
- a link back to the source session
- collapsible sections for the summary, handout, timeline, and personal notes
- a relation to a transcript database
- a status icon that showed whether I had reviewed the imported content
- links to other wiki pages
- notes I had written manually

The sync therefore had to distinguish between machine-owned and human-owned areas.

The machine could update the title, source link, summary, handout, timeline, and transcript relation. It could not replace the whole page. It could not decide that my notes were obsolete. It could not mark a session as reviewed. It could not invent prose for missing fields just because an empty section looked unfinished.

That changes the architecture. This is not:

```text
API response -> Markdown file
```

It is:

```text
user intent
    -> resolve source session and target page
    -> fetch structured source data
    -> transform only known fields
    -> update only machine-owned page sections
    -> preserve human-owned content
    -> verify the final page
```

The update boundary is the most important part of the pipeline.

## Version one: let the agent do everything

The first working version was intentionally direct.

I gave the agent a Notion session page and an Archivist session. It used the Archivist MCP tools to fetch the session, handout, and transcript. It used the Notion tools to inspect a few completed session pages, infer the house style, create or update the transcript page, fill the empty sections, set the properties, and then fetch the result again.

For one session, this was excellent.

The agent was useful because the format was not yet a specification. It was a collection of conventions hidden in existing pages. The summary lived in a quote block. The handout belonged inside a Markdown code block within a toggle. Timeline items had a specific nested-list shape. The transcript was a linked database page. Some pages contained notes that had to remain untouched.

An agent is good at this discovery phase. It can compare examples, explain the differences, and turn an informal layout into explicit rules.

The first run also found Notion-specific behavior that I would not have predicted from a simple Markdown renderer:

- A heading with toggle metadata only behaves correctly when its children use the expected indentation.
- Several quote lines can become several separate quote blocks. One quote line with explicit line breaks keeps the summary in one block.
- Wiki-style links can be escaped during an update and displayed as literal brackets.
- Large transcript bodies may exceed the comfortable size of one update and require chunking.
- Replacing a complete page is easy, but it also replaces content that was never part of the import.

The prototype did its job. It proved that the two systems could be connected, and it extracted the first version of the mapping rules.

It was not yet something I wanted to run across a campaign archive.

## Batch processing exposed the wrong abstraction

The first session required many small steps: fetch source data, inspect target data, build section files, create a transcript page, update properties, replace individual sections, fix escaped links, and verify the final page.

Repeating that sequence for a batch produced a mess of temporary files, payload builders, chunk files, manifests, partial outputs, and agent tasks. Some work could run in parallel. Some work had to remain sequential because of API limits and update dependencies. A failed tool call could leave one session half-finished while the next session started.

The biggest problem was not speed. It was state.

For every session, I needed to know:

- Was the source session fetched?
- Was the handout available?
- Was the target page resolved?
- Did a transcript page already exist?
- Which page sections were empty?
- Which sections had already been updated?
- Did the final content still contain the personal notes heading?
- Was the failure caused by source authentication, target authentication, formatting, or a missing relation?

An agent transcript is not a good job ledger. A pile of generated helper scripts is not a workflow.

The batch also exposed an authentication misconception. A parent agent can have access to an MCP connection while a subagent does not. Moving a fetch into a subagent does not transfer credentials, session state, or tool availability. The subagent may see the instructions and still receive an unauthenticated response.

This is worth stating plainly:

> A subagent is a concurrency boundary, not an authentication boundary.

It can isolate context and do independent work. It does not create credentials, inherit every integration, or make a protected service public. If a batch design depends on "send each session to a subagent," credential availability must be part of the design, not an assumption.

The failed batch attempt was useful because it made the architecture problem obvious. The agent was acting as an interpreter, transformer, transport client, retry mechanism, state machine, and verifier. Those responsibilities needed to be separated.

## Extract the deterministic middle

Once the first sessions had established the mapping rules, most of the work no longer required an LLM.

Given the same session JSON and handout JSON, the pipeline should always produce the same:

- title
- summary toggle
- handout toggle
- nested timeline
- transcript shell metadata

That is a deterministic transform. Keeping it inside an agent prompt would make it slower, harder to test, and easier to change by accident.

I moved the transformation into a small Python renderer. Its input is source JSON. Its output is one Markdown fragment per managed section plus a small metadata file.

Conceptually, the interface is:

```text
build_sections(session, handout)
    -> title
    -> summary section
    -> handout section
    -> timeline section
```

This gave me a clean seam. I could test the rendering without calling either API. I could inspect the output before a write. I could keep source fetching, rendering, and target mutation as separate phases.

It also made the "blank, not invented" rule enforceable.

If Archivist does not provide a field, the renderer does not ask an LLM to complete it. It emits an empty section or omits the optional subsection. Missing data remains visibly missing.

That rule sounds conservative, but it matters in campaign records. A fluent paragraph is not evidence. A guessed encounter detail can become false canon after it is copied into a wiki and read six months later.

There is a related workflow for reconstructing a genuinely missing session from player notes and surrounding sessions. That is idea 41, and it is deliberately separate. It uses bounded narrative interpolation with explicit source constraints. It must not be smuggled into a publishing sync.

## The Notion template is a data contract

The target page format eventually became explicit enough to treat as a contract.

The simplified shape looks like this:

````markdown
### Summary {toggle="true"}

    > Session summary stays in one quote block.

### Handout {toggle="true"}

    ```markdown
    Structured handout content
    ```

### Timeline {toggle="true"}

    - **Major beat**
    	- **Child beat**

### Notes {toggle="true"}

### Transcripts {toggle="true"}
````

The exact words can change between workspaces. The useful part is the ownership model:

- `Summary`, `Handout`, and `Timeline` are managed sections.
- `Notes` is a preservation boundary.
- `Transcripts` is represented by a relation, not by pasting a large body into the session page.

The summary renderer uses one blockquote line and inserts explicit line breaks between source paragraphs. This is less pretty than ordinary Markdown, but it maps to the desired Notion block structure. Rendering every paragraph with its own `>` marker created multiple quote blocks.

The timeline renderer rebuilds the beat tree from `parent_id` relationships. It groups beats by parent, sorts siblings by their source index, and recursively renders children with one additional indentation level. This is not a language task. It is a tree traversal.

The handout renderer maps known source groups in a stable order: outline, summary, moments, encounters, character highlights, entity highlights, items, valuable information, party status, and next steps. Optional groups are included only when present.

Wiki links required another rule. A valid source string such as `[[CHARACTER_NAME]]` must reach Notion without becoming `\[\[CHARACTER_NAME\]\]`. A global search-and-replace after the write is risky because it can touch unrelated content. The safer approach is to replace the complete managed timeline section with a correctly rendered fragment and then verify the result.

This is a recurring pattern in integrations: the serialized format is not the data model. Markdown is only an interchange syntax for Notion blocks. You have to inspect what Notion created, not only what you sent.

## Resolve identifiers from the target when possible

The early workflow required both a source session ID and a Notion page ID. That is precise but unpleasant. The user already has the Notion page open. The page already has an Archivist URL property. Asking for the same information again creates opportunities to choose the wrong session.

The sync now accepts a target page URL such as:

```text
https://notion.example/SESSION_PAGE
```

It extracts `NOTION_PAGE_ID`, fetches the page properties, reads the Archivist source link, and parses `SESSION_ID` from that link.

An explicit `--session-id SESSION_ID` remains available as an override. It is useful for a new page whose source property has not been set, or for repair work where the stored link is wrong.

The precedence rule is simple:

1. Use an explicit session ID when supplied.
2. Otherwise, resolve it from the target page's source property.
3. Stop with a precise error if neither exists.

The script does not search the full source catalog unless it must. This keeps normal execution fast and makes the selected mapping visible.

For batch work, a manifest provides the same mapping:

```json
[
    {
        "page_id": "NOTION_PAGE_ID",
        "session_id": "SESSION_ID"
    }
]
```

The manifest is not a dump of credentials or source content. It is only an explicit list of intended pairings.

## Pagination belongs in the client, not in hope

The separate Laravel Zero command started as a convenient way to choose a session and print the mapped Markdown without changing Notion.

Its first user experience was:

1. Ask for a campaign ID.
2. Fetch sessions for that campaign.
3. Show a session choice.
4. Fetch the selected session, beats, and moments.
5. fill the template.
6. Print to standard output or write a file.

The campaign ID prompt was soon replaced with another API-backed choice. If there is one campaign, the command selects it automatically. If there are several, it shows a numbered list. An explicit command option still overrides the interactive flow.

This makes the command useful both for a human at a terminal and for automation:

```bash
php TOOL_NAME export-session
```

or:

```bash
php TOOL_NAME export-session \
  --campaign-id CAMPAIGN_ID \
  --output session.md
```

Then came a classic API-client bug: the beat list used only the first page.

A session could appear to export correctly while silently losing later beats. This is worse than a hard failure because the output looks complete. The fix was not special handling for one endpoint. All list methods needed the same pagination contract.

The client now:

- requests a page with an explicit size
- appends the returned items
- reads the pagination metadata
- continues until the last page
- applies session filtering after collecting all relevant pages when the API requires client-side filtering
- sorts beats by their source index before rendering

Campaigns, sessions, moments, and beats all use that rule. Any new collection endpoint should use the same helper.

Pagination is part of correctness. If an API says "list," never assume the first response means "all."

## The Python sync owns writes

The deterministic sync script does more than render Markdown. It owns the complete write transaction for one session.

The flow is:

```text
Notion page URL
    -> normalize NOTION_PAGE_ID
    -> resolve SESSION_ID
    -> check existing transcript relation
    -> fetch session and handout from Archivist
    -> build managed Markdown fragments
    -> optionally stop for dry run
    -> create linked transcript shell when needed
    -> update title, source link, and review icon
    -> replace each managed section
    -> fetch and verify the final page
```

The script processes a batch one session at a time. Parallel API calls would be faster, but sequential writes are easier to reason about and kinder to Notion's rate limits. This is a personal publishing pipeline, not a high-throughput ingestion service. Predictable recovery matters more than peak throughput.

Transient network failures use bounded retries with increasing delays. HTTP errors stop with the method, URL category, and a limited response detail. A missing handout can fall back to the session summary when that state is expected. Missing authentication, an invalid page identifier, or an unresolved source session stops before any write.

There is also a dry-run mode. It fetches and builds the sections, reports what it would write, and leaves Notion unchanged. Dry runs are especially useful after a template change.

## Idempotency means preserving intent

Calling an operation twice without creating two pages is only the smallest part of idempotency.

For this workflow, idempotency means:

- the same source data produces the same managed sections
- an existing transcript relation prevents another transcript page from being created
- rerunning the sync updates managed content in place
- personal notes remain unchanged
- unrelated properties remain unchanged
- the page stays in "needs review" state after every machine update

The transcript rule is important. A transcript page can be large, and it may contain edits or annotations later. The normal sync checks the relation first. If one exists, transcript creation is skipped. A force option exists for deliberate repair work, but it is not the default.

When no transcript exists, the sync creates a linked transcript shell. The new database page gets a title, source label, source link, and relation back to the session. Its body can remain an empty fenced block:

```markdown

```

That shell is enough to preserve the data model. The transcript body can be populated by a separate operation, manually, or not at all. The session sync does not need to transfer a very large transcript to be considered successful.

For page content, the script never uses whole-page replacement. It first tries to replace the known empty placeholder for a managed section. If the section already contains imported content, it fetches the live Markdown, extracts exactly that section up to the next managed heading or the notes heading, and replaces only that range.

This protects the human-owned content below the boundary.

## Status icons are workflow state

The icon is not decoration.

The machine sets an hourglass after a sync. That means the source content has been imported but not reviewed. It never sets the completion icon. Only a human can do that after checking the page.

This distinction prevents a successful HTTP response from being mistaken for editorial approval.

The same principle applies beyond Notion. Automation may move an artifact into "ready for review." It should not move it into "approved" unless approval itself is automated and backed by an explicit rule.

## Verification is a separate phase

The first prototype verified pages by looking at them through the Notion tool. The script now performs the same check directly.

Verification fetches both page properties and rendered Markdown. It checks:

- the title is present
- the Archivist source URL is present
- the icon is the expected review-pending icon
- the summary contains real quoted content
- the handout contains a non-empty fenced block
- the timeline contains at least one rendered beat
- the notes heading is still present
- the transcript relation count is reported

The result can be printed for a human or returned as JSON:

```json
{
    "ok": true,
    "title": "SESSION_TITLE",
    "icon": "REVIEW_PENDING",
    "sections": {
        "summary": { "filled": true },
        "handout": { "filled": true },
        "timeline": { "filled": true }
    },
    "notes_preserved": true
}
```

Verification is intentionally structural. It proves that the expected content reached the expected places and that the preservation boundary survived. It does not claim that every sentence is good or that every wiki link points to the right lore page. That remains part of human review.

## The Cursor skill became the control plane

After moving fetching, rendering, writing, and verification into the script, the Cursor skill became much smaller.

Its job is now to interpret what the user supplied:

- a Notion session URL
- an Archivist session URL
- a date
- a batch manifest

It resolves only the missing identifier, invokes the Python REST sync script, runs verification, and reports the result.

The skill explicitly tells the agent not to reproduce the sync with a long sequence of MCP calls during the normal path. MCP remains a useful fallback for unusual page layouts, missing token capabilities, or oversized manual repairs. It is no longer the default transport.

This division fits the strengths of each component:

- The agent understands intent and resolves ambiguous inputs.
- The skill defines the workflow and its safety rules.
- The Python script performs deterministic work.
- The APIs remain the source and destination transports.
- The human owns review and editorial changes.

The skill also states its invariants: never replace the full session page, never overwrite notes, never mark the page complete, never create a second transcript by default, and never reimplement the pipeline in chat.

That last rule sounds strict. It exists because the agent is capable of rebuilding a plausible one-off workflow from the same APIs. The result would work once and bypass the tested safety behavior in the script.

## Secrets should not be function arguments

The Laravel Zero command found a subtle secret-handling issue during a failed API request.

The first implementation passed the API token through helper method arguments. When a request threw an exception, the development stack trace could include method arguments. The token was therefore at risk of appearing in terminal output or copied error logs.

The fix was to configure the authenticated HTTP client once and keep the secret out of repeated call arguments. The command catches request failures at the boundary and prints a safe message that describes the failed operation without dumping headers, request objects, or raw exception traces.

The Python sync follows the same general rules:

- load tokens from placeholder variables such as `ARCHIVIST_TOKEN` and `NOTION_TOKEN`, or from a local environment file
- never put them in a manifest
- never print them
- never include authorization headers in diagnostics
- stop early when a required token is missing
- keep response excerpts bounded because vendor errors can echo request context

An agent or subagent should not be used to "hide" a token. The security boundary is the process and its credential handling, not the fact that a model call happened in another context.

## Two paths, two jobs

The Python sync and Laravel Zero command overlap in their source data and Markdown mapping, but they serve different use cases.

| Need                                                         | Use                                   | Why                                                                    |
| ------------------------------------------------------------ | ------------------------------------- | ---------------------------------------------------------------------- |
| Publish one known session into its existing Notion page      | Cursor skill plus Python sync         | Resolves the mapping, performs safe updates, and verifies the result   |
| Publish many known source-to-page pairs                      | Python sync with a manifest           | Sequential, repeatable, and safe for reruns                            |
| Preview the generated content without changing Notion        | Python sync in dry-run mode           | Exercises the real renderer and source fetch                           |
| Browse campaigns and sessions interactively                  | Laravel Zero command                  | Better terminal experience with automatic single-campaign selection    |
| Produce Notion-ready Markdown for copying or editing         | Laravel Zero command                  | Read-only output to standard output or a file                          |
| Repair an unusual page whose managed anchors cannot be found | MCP-assisted fallback                 | An agent can inspect the live structure and make a targeted repair     |
| Reconstruct a missing narrative from sparse notes            | Separate constrained writing workflow | Creative interpolation must not be mixed with deterministic publishing |

I would not merge the two implementations only to remove duplication. Shared concepts do not always mean shared deployment or shared user experience. The sync is a write-capable publishing tool controlled by a Cursor skill. The CLI is a standalone PHP utility for interactive selection and Markdown output. Their risk profiles are different.

What should stay aligned is the contract: source field mapping, pagination behavior, blank-field policy, and template structure.

## What I would build first now

If I started again, I would still begin with the one-session agent prototype.

That was the fastest way to discover the real target format. Writing a complete sync script before understanding Notion's toggle and block behavior would have encoded the wrong assumptions more efficiently.

But I would stop the agent-led approach sooner.

My sequence would be:

1. Use the agent for one representative session.
2. Inspect the final Notion blocks, not only the sent Markdown.
3. Write down the ownership boundary between managed and personal content.
4. Extract the source-to-template mapping into a deterministic renderer.
5. Add dry-run and structural verification.
6. Add idempotent transcript handling.
7. Wrap the script in a small intent-resolving skill.
8. Add batch manifests only after one-session reruns are safe.

The key question is not "Can an agent do this?" It clearly can.

The better question is "Which part still benefits from interpretation?"

Resolving "sync the session page I have open" benefits from an agent. Turning a beat tree into a nested list does not. Deciding whether an unusual Notion page matches the standard template benefits from an agent. Reading page two of an API response does not. Drafting a missing narrative may benefit from an agent under strict constraints. Copying a known summary must not involve invention.

That boundary turned a clever demo into a workflow I can trust.

## The useful result was not the integration

The obvious output is a populated Notion page.

The more useful result is the small publishing system around it:

- source and target identifiers can be resolved without repeated manual input
- pagination is handled consistently
- formatting quirks are encoded once
- personal notes have an explicit preservation boundary
- transcript pages are linked without unnecessary duplication
- imported pages remain pending until a human reviews them
- missing source data stays missing
- credentials stay in the process that needs them
- verification can run without another agent conversation

The MCP prototype was not a failed first version. It was a discovery tool. The painful batch was not wasted effort. It showed exactly which responsibilities did not belong in the agent.

The final design uses less AI than the prototype, and that is why it is more useful.
