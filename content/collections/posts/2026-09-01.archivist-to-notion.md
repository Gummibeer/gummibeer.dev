Our TTRPG campaign is running for more than six years now.

Way before MyArchivist. Way before MCP. And definitely way before I used an LLM for anything around it.

Since the beginning I use Notion for my campaign notes. Sessions, characters, locations, handouts, my own notes - six years of structure that grew together with the campaign.

So when I started using [MyArchivist](https://www.myarchivist.ai/) roughly a year ago, moving everything over was never an option.

MyArchivist is great at a different job. It records the session and gives me things I absolutely don't want to create by hand after a four-hour game: the raw transcript, a session summary, handout, extracted entities, moments, beats and more.

The annoying part was what happened afterwards.

I still wanted all of that inside Notion.

And copying the transcript, summary, handout and timeline over after every session, while making sure I don't overwrite my own notes or break the existing page structure, got old very quickly.

## First try: just write the integration

My first idea was boring and obvious: write it myself.

I started a small PHP script using [Notion for Laravel](https://notionforlaravel.com/) and the Archivist API.

Fetching the data wasn't the problem. Neither was setting a title, URL property or some other basic attributes.

The problem was everything around it.

My Notion session pages aren't a flat dump of properties. They have toggles, nested lists, a transcript relation, a handout rendered in a specific shape, and sections I own manually and never want an import to touch.

So suddenly I was hand-mapping Archivist's response into Notion blocks, normalizing all the different structures, handling existing content, keeping the template intact and dealing with all the little Notion-specific oddities.

I got far enough to fill properties and the default template.

Then I stopped.

Not because it was impossible. It simply wasn't interesting enough to justify building the whole mapping layer by hand.

## Then MCP made the ugly part easy

Notion already had MCP support.

And I had built [Archie, my MyArchivist MCP server](/blog/2026/building-myarchivist-mcp).

So I tried the most obvious LLM version of the workflow.

I gave the model the MyArchivist session and the Notion page and told it what the finished result should look like.

It could read the structured session data through Archie, inspect existing Notion pages, understand where the summary belongs, how I structure the timeline, where the transcript relation goes and what must stay untouched.

And it worked.

Actually, for the first few sessions it worked really well.

This was the part where an LLM made a lot of sense because I didn't have a real specification yet. I had six years of existing Notion pages.

The model could look at those and infer the rules from the actual data instead of me first translating all of that into a technical mapping document.

It also meant every run was supervised.

I checked the result. Fixed things. Told it what was wrong. Ran the next session. Found another edge case. Repeated.

That was pretty nice for backfilling older sessions.

But it was also obviously not the final solution.

## LLMs are a pretty stupid copy command

Once the workflow was understood, there wasn't much intelligence left in it.

Fetch this session.

Read this Notion page.

Put the summary here.

Render these beats as a nested timeline.

Create the transcript relation if it doesn't exist.

Don't touch my notes.

Verify that the result still looks like the template.

That's not an AI problem.

And running the whole thing through an LLM every time had some very real downsides.

It was slow because every run needed a bunch of MCP calls.

It was wasteful because the model had to read data, understand the same mapping again and send everything back through tools.

And there was always this tiny bit of distrust in the back of my head.

Copying text without changing it is not exactly what LLMs are best at. 😅

I don't want the model to make a session summary "nicer". I don't want it to rephrase a handout. I don't want it to decide that one of my notes would fit better somewhere else.

I just want the data copied into the right structure.

After a bunch of supervised runs the model had enough context to know exactly what "right structure" meant.

So I asked it to write the script.

## And that was the useful AI part

The first generated version was Python.

And it basically nailed the workflow in one shot.

Not because "one-shot code generation" is magical.

It worked because the model had already done the job several times.

It had seen the source data.

It had seen my target pages.

It had seen the edge cases.

It had been corrected when it got something wrong.

By the time I asked for code, all the messy human knowledge around the workflow was already in context.

The LLM didn't invent an automation from a vague sentence.

It compressed a workflow we had already executed and reviewed several times into deterministic code.

That's a much more interesting use of AI for me.

Human idea first.

Then an LLM helps explore the workflow.

A human keeps checking the result.

The repeated parts become clearer with every run.

And once the task is boring enough, the LLM writes the boring code so it doesn't have to be involved anymore.

## What the script does now

The normal workflow is stupidly small.

I create the new session page in Notion from my existing template, add the MyArchivist link and run:

```bash
python3 sync_archivist_to_notion.py --notion-page ABC
```

That's it.

If I don't pass a MyArchivist session ID explicitly, the script reads it from the `Archivist` URL property on the Notion page.

It fetches the session and handout from MyArchivist, builds the Notion Markdown for the managed sections, creates the transcript relation when needed, updates the known page properties and finally verifies the result again.

The important part is that it only owns the sections it is supposed to own.

`Zusammenfassung`, `Handout` and `Timeline` can be replaced by the sync.

`Notizen` is mine.

The script never replaces the whole page just because that's easier.

The hourglass icon is also intentional. A successful sync means "imported and needs review", not "done". Only I can turn that into whatever I use as the reviewed state afterwards.

So the final split is pretty simple:

- MyArchivist owns the captured and generated session data.
- Notion stays my campaign wiki and long-term source of truth.
- The Python script owns the deterministic mapping between both.
- An LLM is useful when that mapping changes or another weird edge case appears.
- I still review the result.

That's a lot less exciting than "an autonomous agent manages my campaign knowledge".

Which is probably why I trust it more.

## Why I like this workflow more than the agent version

The final version uses less AI than the first working version.

For me that's the point, not a regression.

The LLM was extremely useful while the problem was still fuzzy. It could jump between MyArchivist and Notion, inspect examples, understand my existing conventions and help turn "make this look like my other six years of notes" into actual rules.

But once those rules existed, keeping the LLM in the middle would only make the workflow slower and less predictable.

There are a lot of automations where I think this pattern fits.

Don't start by trying to perfectly specify every edge case.

Do the task with the model a few times.

Watch what it does.

Correct it.

Let the ugly requirements surface from real runs.

And when you notice that the model is basically repeating the same deterministic sequence again and again, ask it to turn its own work into code.

Then remove the model from the hot path.

For this sync I ended up with something much better than my first PHP attempt and much safer than running a full MCP agent workflow after every session.

And after six years of campaign notes, "boring and deterministic" is exactly what I want from the thing touching them.
