Fourteen open merge requests. Some months old. Stale descriptions, merge conflicts against a main branch that had moved on without them, failed CI pipelines nobody had looked at, and a queue of Bugbot comments waiting for triage. The usual approach is to block off a Friday afternoon and grind through them one by one. The new approach is to write down the workflow once as a skill file and let an agent loop run it until everything is green.

That's what I did, and this is what happened.

_This is part two of a two-part series. If you want the underlying triage framework — how to categorise stale MRs, regenerate descriptions from diffs, and keep the ready-for-review signal human-owned — start with [Stale MR Triage](/blog/stale-mr-triage)._

## The two entry points

The skill — called `ralph-loop` after the [Ralph Wiggum](https://awesomeclaude.ai/ralph-wiggum) concept of an agent that keeps looping until it's done — has two starting positions.

The first is for net-new work: start from a Linear issue, explore the codebase, write an implementation plan, implement, open an MR with a proper description (what / why / how / testing), and fall through to the loop. The second is for existing MRs: jump straight into the loop. The six stale ones went through the second path; three sub-issues that still needed code written went through the first.

Both paths converge on the same loop. Pipeline green, all threads resolved, no conflicts, not a draft — done.

## What the loop does

Each iteration starts with a snapshot: three parallel API calls to get the latest pipeline status, all open discussion threads, and the MR's merge status.

```bash
# Pipeline status
glab api "/projects/:id/merge_requests/:iid/pipelines" \
  | jq 'first | {status, web_url, id}'

# Open threads
glab api "/projects/:id/merge_requests/:iid/discussions" \
  | jq '[.[] | select(.resolved == false) | {id, resolved, notes: [...]}]'

# Merge status
glab api "/projects/:id/merge_requests/:iid" \
  | jq '{state, merge_status, has_conflicts, draft, detailed_merge_status}'
```

Then it classifies every open thread: Bugbot issues are treated as real unless there's a specific reason to dismiss them; human comments with a clear fix get fixed and resolved; ambiguous comments stop the loop and surface to me; and disagreements get a polite reply explaining the reasoning, then get left for me. The loop doesn't collapse under reviewer pressure, but it also doesn't make semantic product decisions on its own.

After comments it checks for conflicts, rebases, and resolves — but only when the intent on both sides is clearly the same. Two authors adding different things to the same file: merge both. Two different implementations of the same concept: stop and ask. Then it watches CI at 90-second intervals, fixes lint and type failures, retries flaky infrastructure jobs once, and surfaces anything ambiguous. After each push it goes back to the beginning.

## The actual session

For the six existing MRs, the agent launched six parallel "understand" agents before touching any code. Each read the diff, traced the affected code paths, and returned a brief summary of what the MR was doing and whether it was still needed. All six came back as still needed.

Then the rebasing started, and that's where it got interesting.

One MR had a conflict in a payments pipe where the base branch had added exclusion filters (to drop unknown-status payments from comparisons) after the MR was branched off. The MR had introduced a different partitioning strategy — primary vs ad-hoc payments. The loop resolved it by applying the exclusion filters to the primary-payment set after partitioning. Both intents were clearly preserved, no semantic decision required.

Another MR had a more complex situation: an add/add conflict in a test file. Both sides had created the file. The loop took the base branch's more complete version and layered the MR's new test cases on top of it. Mechanical, but correct.

The worst one had conflicts across six files: `composer.json`, a Helm values file, and two large handler classes. A feature-flag client had been added to both sides with slightly different config. One handler had a `withDefaultSubject()` helper on one side and a `compareTaxSettings()` method on the other — both needed because the `get()` method called both. The loop read both sides, confirmed both methods were referenced, and merged them. When it found a PostHog config block that already existed earlier in the same file, it dropped the duplicate and moved on.

After the rebases, five of the six pipelines failed. The loop read the job logs, classified the failures, and went to work.

## What Bugbot found

Bugbot — the static analysis bot that runs on every push — had a full queue of comments across the six MRs.

Some of them the loop fixed without hesitation. A `distinctId` parameter was typed as `int` when PostHog's client expected `string`. A null-safety issue in a CLI command where `--site-id` could be omitted but `$this->option('site-id')` was being passed directly to a method that required a value. An unused import left over from a test that was removed during conflict resolution. A timeout missing from a Helm worker configuration. All fixed, pushed, threads resolved.

Some Bugbot comments the loop pushed back on. For an Adyen refund MR, Bugbot flagged that including `REFUND_FAILURE` payments in the refundable total was risky — "payments with failed refunds may have underlying issues preventing refunds." The loop posted a reply explaining that `REFUND_FAILURE` in Adyen means the refund instruction failed, not that the underlying capture failed. The money is still there. The inclusion is deliberate. Thread left open for a human reviewer to decide, not silently resolved.

For a shadow-comparison handler, Bugbot flagged that the `$includeDeleted` parameter was accepted by the method but never used in the query. The loop posted a reply explaining that this is an interface-compliance parameter — the model-based handler doesn't have a soft-delete concept yet, and implementing full parity wasn't the scope of the MR (which was purely for shadow logging during a rollout). Left for human review.

The distinction matters: the loop doesn't dismiss Bugbot findings by default, but it also doesn't treat every static-analysis comment as a mandatory code change. Context matters, and when it has enough context to push back, it does.

## What the loop got wrong

On one MR, the loop encountered a test regression introduced by the rebase. A test was asserting that a specific alteration produced a payment of a specific amount. After rebasing, a payment-terms calculation upstream had changed behavior — the empty-terms fast path that the test was exercising no longer fired for this specific reservation because a cutoff-date calculation in main had been updated.

The loop spent several iterations trying to understand whether the test was still valid. It checked git history, traced the cutoff-calculation change, and concluded — correctly — that the test expectation was written against old behavior that no longer applied. But it made the call to remove the test unilaterally during conflict resolution rather than stopping and asking me. The test was actually wrong for the current state of main, so the outcome was fine, but that's a judgment call that should have come to me. The stopping conditions exist for exactly this reason. Removing a regression test without human sign-off is on the edge.

The loop also hit a `flexible()` method call that didn't exist in the installed Laravel version — the MR had been written against a feature added in Laravel 12, and the codebase was still on 11. The loop caught this from PHPStan output, understood it, and replaced `->flexible()` with `->remember()` with a comment explaining the difference. That one I was fine with.

## The personal-feedback rule

One thing that made the loop's decisions more accurate from the start: a rule file called `personal-feedback.mdc`, generated from 503 past chat transcripts. It contains extracted patterns like "treat `REFUND_FAILURE` as a real captured state" and "prefer explicit `if` over `->when()` for PHPStan clarity" and "do not propose vague error messages." The loop reads this rule automatically on every session. It's not magic — it's just accumulated context that would otherwise have to be re-explained every time.

The loop pushed back on Bugbot's `$allowMixedActions` comment in a way that matched my actual opinion about the codebase pattern. It wasn't because it reasoned its way to that conclusion from scratch. It was because the rule file had enough prior context to narrow the decision space.

## What stayed human

The final merge click — every time. The loop reports "MR is merge-ready" and lists anything it intentionally left for me. It doesn't merge.

Any thread that touched money calculations or user-facing behaviour stayed flagged. Not because the loop can't read the code, but because those are the threads where being slightly wrong costs something real. The loop knows the difference between "this string formatting is wrong" and "this changes how refunds are calculated for a specific cancellation flow."

The decision to close vs. rescue an MR is also human. None of these six were closed, but the loop checked explicitly and would have added a "closed by cleanup" label rather than closing them if any had been truly superseded.

## Whether it's worth it

The skill file is about 250 lines. Writing it took a couple of hours. The six existing MRs took a full session — back and forth, a few stops for input, a couple of git history rabbit holes. The three new-feature MRs took another session.

The backlog is clear. All nine are either merged or at "ready for review" with no open threads, green CI, and an updated description.

What the loop bought me wasn't raw speed so much as continuity. I could work on something else while it was watching CI. The cycle of push, wait eight minutes, read a failure, fix, repeat is brutal to do manually. Having something handle that cycle and only surface genuine decisions is the actual value.

The skill isn't general-purpose. It's tuned to a specific codebase, a specific CI setup, a specific way Bugbot behaves in this project. You'd need to adapt it. But the underlying structure — snapshot, triage, rebase, watch, check, repeat until done, stop when you need a human — is what transfers.
