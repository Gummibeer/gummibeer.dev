It started with a tweet.

I shared a tiny Laravel macro — `URL::macro('toSpa', ...)` — that generated links pointing at a separate SPA frontend from backend code. Simple config value, string concatenation, done. It worked. For a while, that was enough.

Then real usage kicked in, and the cracks appeared in sequence.

## Pain point one: parameters end up in the path

Laravel's built-in `url()->to($path, $parameters)` appends parameters to the path. That's the right behaviour when you're routing to a backend controller. It's the wrong behaviour when you're building a frontend URL.

```php
url()->to('/success', ['type' => 'verify_email']);
// → https://app.example.com/success/verify_email
```

What I wanted was a query string:

```
https://app.example.com/success?type=verify_email
```

A subtle difference, but it meant every call site needed manual `http_build_query` glue, which negated the point of the macro entirely.

## Pain point two: no placeholder substitution

Routes like `/users/{user}/settings` exist everywhere in SPA apps. When backend code needs to link to one of them — in an email, in a redirect, in an API response — you want to substitute `{user}` with a real value without assembling strings by hand.

```php
// what I was doing
$url = config('services.spa.url') . '/users/' . $user->id . '/settings';

// what I wanted
$url = url()->toSpa('/users/{user}/settings', ['user' => $user->id]);
```

The second form is readable. It's also testable as a single unit — the path template is explicit, the values are separate, and the substitution lives in one place.

## Pain point three: the backend-action-to-frontend-destination flow

This one was the most persistent. Some flows are backend-first: an email verification link, an OAuth callback, a payment confirmation webhook redirect. The user clicks something that hits a backend URL, the backend does its work, and then the user should land on a nice SPA page.

Without a dedicated helper, every controller doing this had the same boilerplate:

```php
public function verify(Request $request): RedirectResponse
{
    // ... verification logic ...

    $url = rtrim(config('services.spa.url'), '/') . '/auth/verified?type=verify_email';

    return redirect()->to($url);
}
```

Repeated in every controller that had a backend action with a frontend destination. Not terrible, but not good either. Change the frontend URL structure or the config key, and you're hunting across files.

## The evolution

Two focused building blocks replaced all of this.

**First: a `toSpa` macro that handles placeholders and query strings properly.**

```php
use Illuminate\Support\Facades\URL;
use Illuminate\Support\Str;

URL::macro('toSpa', function (string $path, array $parameters = [], array $query = []): string {
    $path = strtr(
        $path,
        collect($parameters)->keyBy(
            fn (mixed $_, string $key): string => Str::of($key)->start('{')->finish('}')
        )->all(),
    );

    $url = rtrim(config('services.spa.url'), '/') . '/' . ltrim($path, '/');

    if (Str::contains($url, '?')) {
        $existingQuery = [];
        parse_str(Str::after($url, '?'), $existingQuery);
        $query = array_merge($existingQuery, $query);
    }

    if (! empty($query)) {
        $url = Str::before($url, '?') . '?' . http_build_query($query);
    }

    return $url;
});
```

Placeholders in the path get replaced by name. Query params passed separately stay as query params. If the path already contains a query string (e.g. a template like `/success?tab=profile`), those are merged with any explicitly passed `$query` values — with the explicit values winning on collision.

**Second: `redirect()->toSpa()` for backend action endpoints.**

```php
use Illuminate\Routing\Redirector;

app(Redirector::class)->macro('toSpa', function (string $path, array $parameters = [], array $query = []): \Illuminate\Http\RedirectResponse {
    /** @var Redirector $this */
    return $this->to(url()->toSpa($path, $parameters, $query));
});
```

Same signature as `url()->toSpa()` — same path templates, same placeholder substitution, same query handling. It delegates directly so the logic lives in one place.

## What this looks like in practice

```php
// Query stays a query — no accidental path segments
$url = url()->toSpa('/success', query: ['type' => 'verify_email']);
// → https://spa.example.com/success?type=verify_email

// Placeholder substitution + explicit query params
$url = url()->toSpa('/users/{user}/settings', ['user' => $user->id], ['tab' => 'security']);
// → https://spa.example.com/users/42/settings?tab=security

// Backend action → clean SPA redirect, same signature as url()->toSpa()
public function verify(EmailVerificationRequest $request): RedirectResponse
{
    $request->fulfill();

    return redirect()->toSpa('/auth/verified', query: ['type' => 'verify_email']);
}
```

That last one is the one I'm most glad about. The verification controller was six lines of concatenation. Now it's one line that reads like English: "redirect to the SPA's verified page, with this context." And because `redirect()->toSpa()` shares the same signature as `url()->toSpa()`, there's nothing new to learn — placeholders and query params work identically.

## Where to register the macros

I register both in a service provider — a dedicated `FrontendUrlServiceProvider` that gets added to `config/app.php`. Keeping them separate from `AppServiceProvider` makes them easy to find, test in isolation, and remove if the architecture ever changes.

```php
namespace App\Providers;

use Illuminate\Routing\Redirector;
use Illuminate\Support\Facades\URL;
use Illuminate\Support\ServiceProvider;
use Illuminate\Support\Str;

class FrontendUrlServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        URL::macro('toSpa', function (string $path, array $parameters = [], array $query = []): string {
            // ... (full implementation above)
        });

        app(Redirector::class)->macro('toSpa', function (string $path, array $parameters = [], array $query = []): \Illuminate\Http\RedirectResponse {
            return $this->to(url()->toSpa($path, $parameters, $query));
        });
    }
}
```

## The actual benefit

The benefit isn't "three fewer lines per controller". It's consistency.

Before: URL generation for the frontend was scattered. Some controllers used `config('services.spa.url')` directly. Some used the original macro. Some had raw concatenation. Each had slightly different handling of edge cases — query params, trailing slashes, placeholder values. Each was a potential source of drift.

After: one canonical way to build a frontend URL (`url()->toSpa()`), one canonical way to redirect to one (`redirect()->toSpa()`). Edge cases — query merging, placeholder substitution — live in one tested place. Add a new controller, pick up the same behaviour for free.

In a backend + SPA setup where the two sides evolve at different speeds, that consistency is worth more than any individual feature.
