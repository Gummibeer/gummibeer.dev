A price summary had been correct for years.

Then someone used a zero-decimal currency.

The detailed rows were correct. The final total was correct. One collapsed summary row was 100 times too small. A synthetic tax of 4,000 JPY appeared as 40 JPY. The calculation behind the page was fine. Only the display was wrong.

The cause was one innocent-looking line in the frontend:

```typescript
const total = taxes.reduce(
    (sum, tax) => sum + Number(tax.amount) / 100,
    0,
)
```

The code assumed that every monetary amount used two decimal places. That works for currencies such as USD and EUR. Their ISO 4217 minor unit exponent is 2. An integer of `1000` minor units therefore represents a synthetic major value of `10.00`.

It does not work for JPY. JPY has an exponent of 0. An integer of `10000` minor units represents a synthetic major value of `10000`, not `100.00`.

It also does not work for currencies with an exponent of 3, such as KWD. An integer of `10000` minor units represents a synthetic major value of `10.000`.

There is no universal `/ 100` for money.

The immediate fix was small. Stop doing currency conversion in the UI and use the currency-aware value that the backend already provided.

But the interesting lesson was larger: the bug did not start in that line of TypeScript. It started when an amount crossed a system boundary as a string with no enforced meaning. The UI had to guess its unit. The guess happened to work for the common currencies. That made the mistake look safe.

The general rule I took from this is:

> Wrap money and percentages in value objects at the first system boundary. Do not let their primitive encodings travel through the stack.

This post works through that rule, why it matters, and how to adopt it without a large rewrite.

All monetary values in this article are synthetic, round examples. Currency exponent facts are public ISO 4217 facts.

---

## Minor units are not cents

People often use "minor units" and "cents" as if they mean the same thing. They do not.

A minor unit is the smallest unit used by a currency for accounting. The relationship between a major amount and a minor amount depends on the currency's ISO 4217 exponent.

| Currency | Public ISO exponent | Synthetic major value | Synthetic minor value |
|---|---:|---:|---:|
| JPY | 0 | `10000` | `10000` |
| USD | 2 | `10.00` | `1000` |
| KWD | 3 | `10.000` | `10000` |

The conversion is:

```text
minor = major × 10^exponent
major = minor ÷ 10^exponent
```

The important part is not the formula. The important part is who owns the exponent.

This code does not:

```php
$major = $minor / 100;
```

Neither does this:

```typescript
const major = minor / 100
```

Both lines contain a hidden type:

```text
integer amount in a currency that definitely has exponent 2
```

PHP sees an `int`. TypeScript sees a `number`. The developer sees "money." The missing information sits only in the developer's head.

That is primitive obsession in its most expensive form.

## Why the bug stayed hidden

The hardcoded division passed normal testing because most examples used two-decimal currencies. For those examples, the incorrect model and the real model produced the same answer.

That is a dangerous kind of test coverage. The tests execute the line, but they do not challenge its assumption.

The defect often appears during a migration:

1. An old API returns major units as a decimal string.
2. A new API returns minor units as an integer string.
3. Most backend call sites move to a money object or a formatted value.
4. One frontend summary still expects the old shape.
5. Someone adds `/ 100` to preserve the old display.
6. Two-decimal currencies continue to look correct.
7. A zero-decimal or three-decimal currency exposes the mismatch.

This is migration drift. Different parts of the system have different ideas about the contract.

The detailed rows may use a backend field such as `display`. The total may also come from the backend. A single summary row may still sum raw values in the browser. The page then has two money systems:

- a currency-aware backend system;
- an implicit exponent-2 frontend system.

The second system is only a few lines long. It is still a money system. It still needs all the same rules about currency, precision, rounding, and serialization.

This is why UI-side division is dangerous. It looks like formatting. It is actually domain logic.

## First aid: remove the guess

If the backend already supplies a currency-aware major value, the smallest safe fix is to use it.

Suppose the API returns this generic contract:

```json
{
  "tax_total": {
    "currency": "JPY",
    "minor": "4000",
    "minor_unit_exponent": 0,
    "major": "4000",
    "display": "JPY 4,000"
  }
}
```

Every amount above is synthetic.

The UI can render `display`:

```typescript
type AmountPayload = {
    currency: string
    minor: string
    minor_unit_exponent: number
    major: string
    display: string
}

function TaxTotal({ amount }: { amount: AmountPayload }) {
    return <span>{amount.display}</span>
}
```

No division is needed.

If the UI must format for the user's locale, it can parse the `major` decimal string only at the final formatting point. It must not use that parsed value for arithmetic:

```typescript
const formatter = new Intl.NumberFormat(locale, {
    style: 'currency',
    currency: amount.currency,
})

return formatter.format(Number(amount.major))
```

For values that can exceed JavaScript's safe numeric range, even this final conversion can lose precision. A safer API can supply `display`, or the frontend can use a decimal library.

If the UI must add, subtract, allocate, or compare amounts, it needs a real frontend money type. It should use `BigInt` minor units together with the currency and exponent:

```typescript
type Amount = Readonly<{
    currency: string
    minor: bigint
    exponent: number
}>

function amountFromPayload(payload: AmountPayload): Amount {
    return {
        currency: payload.currency,
        minor: BigInt(payload.minor),
        exponent: payload.minor_unit_exponent,
    }
}
```

Even then, the best question is often: why is the UI calculating this total at all?

If a value affects a charge, refund, invoice, tax, ledger, or contractual total, the backend should own the calculation. The frontend should display the result. A browser can calculate an estimate for responsiveness, but the server result must remain authoritative.

## The real fix starts at the boundary

Removing `/ 100` fixes the visible defect. It does not prevent the next one.

The next caller can still accept:

```php
public function calculate(int $amount, string $currency): int
```

The method has three problems:

1. The amount and currency can drift apart.
2. The unit of `$amount` is not stated.
3. The return value loses the currency and unit again.

A docblock can describe the intent:

```php
/**
 * @param int $amount Amount in minor units.
 * @param string $currency ISO 4217 currency code.
 * @return int Amount in minor units.
 */
```

That is better than nothing. It is not enforcement.

The pair should become one object as soon as it enters the application:

```php
public function calculate(Amount $amount): Amount
```

The same rule applies to percentages:

```php
public function applyDiscount(Amount $amount, float $percentage): Amount
```

What does `4` mean?

- 4 percent?
- a ratio of 4, which means 400 percent?
- 4 basis points, which means 0.04 percent?
- 4 parts per ten thousand?

The parameter name does not answer that question. A `Percent` value object with named factories does.

## What counts as the first boundary?

A boundary is the first point where untrusted, serialized, or loosely typed data enters a typed part of the system.

Common Laravel boundaries include:

- validated request data;
- a decoded API response;
- a message consumed from a queue;
- a stored event being deserialized;
- an Eloquent attribute or database row;
- a console command argument;
- a CSV import row;
- an environment or configuration value.

Convert there.

Do not wait until three action classes later.

Here is a request DTO:

```php
final readonly class CreateQuoteData
{
    public function __construct(
        public Amount $subtotal,
        public Percent $taxRate,
    ) {}

    /**
     * @param array{
     *     subtotal_minor: int|string,
     *     currency: string,
     *     tax_rate_percentage_points: int|string
     * } $data
     */
    public static function fromValidated(array $data): self
    {
        return new self(
            subtotal: Amount::fromMinor(
                minor: $data['subtotal_minor'],
                currency: $data['currency'],
            ),
            taxRate: Percent::fromPercentagePoints(
                $data['tax_rate_percentage_points'],
            ),
        );
    }
}
```

The controller performs the conversion once:

```php
final class CreateQuoteController
{
    public function __invoke(CreateQuoteRequest $request, QuoteCalculator $calculator): JsonResponse
    {
        $data = CreateQuoteData::fromValidated($request->validated());
        $quote = $calculator->calculate($data);

        return response()->json(QuoteResource::make($quote));
    }
}
```

Everything below the DTO receives `Amount` and `Percent`. No lower layer needs to remember request field names or primitive encodings.

This is the same discipline used for dates and enums:

```php
final readonly class ScheduleData
{
    public function __construct(
        public CarbonImmutable $startsAt,
        public ScheduleStatus $status,
    ) {}
}
```

We do not normally pass an ISO date string through five services and hope the last one parses its timezone correctly. Money and percentages deserve the same treatment.

## Designing an `Amount` value object

There is no single correct money value object. The correct design depends on the libraries and storage model in the application.

At minimum, an `Amount` should keep these values together:

- the exact amount;
- the currency code;
- the amount's unit.

I prefer a canonical internal representation in minor units. The amount is an integer. The currency is an ISO 4217 code. Currency metadata determines the exponent.

The examples below use `brick/math` concepts to avoid binary floating-point arithmetic. A mature application should normally use an established money library instead of building all currency behavior itself.

```php
<?php

declare(strict_types=1);

use Brick\Math\BigDecimal;
use Brick\Math\RoundingMode;

final readonly class Amount
{
    private function __construct(
        private int $minor,
        private string $currency,
    ) {}

    public static function fromMinor(int|string $minor, string $currency): self
    {
        $normalizedMinor = filter_var($minor, FILTER_VALIDATE_INT);

        if ($normalizedMinor === false) {
            throw new InvalidArgumentException('The minor amount must be an integer.');
        }

        return new self(
            minor: $normalizedMinor,
            currency: strtoupper($currency),
        );
    }

    public static function fromMajor(
        string $major,
        string $currency,
        CurrencyMetadata $metadata,
    ): self {
        $currency = strtoupper($currency);
        $exponent = $metadata->minorUnitExponent($currency);

        $minor = BigDecimal::of($major)
            ->multipliedBy(BigDecimal::of(10)->power($exponent))
            ->toScale(0, RoundingMode::UNNECESSARY)
            ->toInt();

        return new self($minor, $currency);
    }

    public function minor(): int
    {
        return $this->minor;
    }

    public function currency(): string
    {
        return $this->currency;
    }

    public function plus(self $other): self
    {
        $this->guardSameCurrency($other);

        return new self(
            minor: $this->minor + $other->minor,
            currency: $this->currency,
        );
    }

    public function minus(self $other): self
    {
        $this->guardSameCurrency($other);

        return new self(
            minor: $this->minor - $other->minor,
            currency: $this->currency,
        );
    }

    private function guardSameCurrency(self $other): void
    {
        if ($this->currency !== $other->currency) {
            throw new LogicException('Amounts with different currencies cannot be combined.');
        }
    }
}
```

The named factories are important.

These calls state the input unit:

```php
$yen = Amount::fromMinor(10000, 'JPY');
$dollars = Amount::fromMajor('10.00', 'USD', $metadata);
$dinars = Amount::fromMajor('10.000', 'KWD', $metadata);
```

All three values are synthetic.

This call does not state the unit:

```php
$amount = new Amount(10000, 'USD');
```

Is `10000` a synthetic 100.00 USD in minor units or a synthetic 10,000.00 USD in major units? A public constructor forces every reader to inspect implementation details. Named factories put the unit in the method name.

Useful factories often include:

- `fromMinor()`;
- `fromMajor()`;
- `zero()`;
- `fromMoney()` when adapting a library type;
- a narrowly named legacy factory during migration.

Avoid a generic `from()` factory that accepts several encodings and guesses from the input shape.

## Do not use floats for major amounts

Binary floating-point numbers cannot represent many decimal fractions exactly.

This is not a PHP defect. It is how IEEE 754 floating-point works.

This is unsafe:

```php
Amount::fromMajor(10.00, 'USD', $metadata);
```

The synthetic value looks harmless, but a float has already lost the decimal contract before the factory receives it.

Use decimal strings:

```php
Amount::fromMajor('10.00', 'USD', $metadata);
```

Use integer minor units for storage and arithmetic where possible:

```php
Amount::fromMinor(1000, 'USD');
```

For JSON, serialize large minor values as strings. JavaScript numbers are only exact integers up to `Number.MAX_SAFE_INTEGER`.

```json
{
  "currency": "USD",
  "minor": "1000"
}
```

That is a synthetic 10.00 USD.

## Designing a `Percent` value object

Percentages have the same boundary problem as money. Their ambiguity is about scale rather than currency.

These values can all describe the same rate:

| Encoding | Value for the same synthetic rate |
|---|---:|
| Percentage points | `4` |
| Decimal ratio | `0.04` |
| Basis points | `400` |
| Parts per million | `40000` |

The rate is a synthetic 4 percent in every row.

A bare `float $rate` does not say which row it uses.

A `Percent` object should select one canonical internal representation and provide named factories for every accepted boundary encoding.

One option is an exact decimal ratio:

```php
<?php

declare(strict_types=1);

use Brick\Math\BigDecimal;

final readonly class Percent
{
    private function __construct(
        private BigDecimal $ratio,
    ) {
        if ($ratio->isLessThan(BigDecimal::zero())) {
            throw new InvalidArgumentException('A percentage cannot be negative.');
        }
    }

    public static function fromRatio(int|string $ratio): self
    {
        return new self(BigDecimal::of($ratio));
    }

    public static function fromPercentagePoints(int|string $points): self
    {
        return new self(
            BigDecimal::of($points)->exactlyDividedBy(100),
        );
    }

    public static function fromBasisPoints(int $basisPoints): self
    {
        return new self(
            BigDecimal::of($basisPoints)->exactlyDividedBy(10000),
        );
    }

    public static function fromPartsPerMillion(int $partsPerMillion): self
    {
        return new self(
            BigDecimal::of($partsPerMillion)->exactlyDividedBy(1000000),
        );
    }

    public function ratio(): BigDecimal
    {
        return $this->ratio;
    }
}
```

Now the boundary is explicit:

```php
$fromForm = Percent::fromPercentagePoints('4');
$fromApi = Percent::fromRatio('0.04');
$fromLedger = Percent::fromBasisPoints(400);
```

Each line represents the same synthetic 4 percent rate.

Downstream code does not care how the rate arrived:

```php
public function tax(Amount $subtotal, Percent $rate): Amount
{
    return $rate->applyTo($subtotal, RoundingMode::HALF_UP);
}
```

The method signature is now meaningful. It is not possible to pass the amount where the percentage belongs. It is much harder to apply a percentage twice. The encoding conversion is centralized.

The factory names also make code review easier. A reviewer can challenge `fromRatio('4')` immediately. Without a named factory, the same error may hide in arithmetic several layers later.

## Rounding is part of the contract

Exact money arithmetic still produces fractional minor units when you multiply by a rate or divide an amount.

A synthetic 10.00 USD multiplied by a synthetic 4 percent rate produces an exact synthetic 0.40 USD. No rounding decision is needed there.

But many real calculations do need one. Allocation is a simple example. A synthetic 10.00 USD cannot be split equally into three integer-cent shares without a remainder.

The wrong response is to let each caller use `round()` in its preferred way.

Rounding needs an owner:

- the `Percent` operation;
- the `Amount` operation;
- or a domain service that knows the business rule.

It also needs an explicit mode:

```php
public function applyTo(Amount $amount, RoundingMode $roundingMode): Amount
{
    $minor = BigDecimal::of($amount->minor())
        ->multipliedBy($this->ratio)
        ->toScale(0, $roundingMode)
        ->toInt();

    return Amount::fromMinor($minor, $amount->currency());
}
```

Do not hide an arbitrary default if the domain has different rules for charges, refunds, taxes, and allocations.

For allocation, a money library can distribute the remainder deterministically:

```php
[$first, $second, $third] = $amount->allocate([1, 1, 1]);
```

The important invariant is:

```php
$first->plus($second)->plus($third)->equals($amount);
```

Formatting also has a rounding policy, but formatting must not change the stored value. A display rounded to two visible digits is not a new amount.

## A serialized API contract should name the unit

An API field named `amount` is incomplete.

This contract is ambiguous:

```json
{
  "amount": "1000",
  "currency": "USD"
}
```

Does the synthetic `1000` mean 10.00 USD or 1,000.00 USD?

The field name should state the unit:

```json
{
  "amount": {
    "currency": "USD",
    "minor": "1000",
    "minor_unit_exponent": 2,
    "major": "10.00",
    "display": "USD 10.00"
  }
}
```

Every amount is synthetic.

The fields have different purposes:

- `minor` is the exact machine value;
- `currency` gives the monetary unit;
- `minor_unit_exponent` makes the relationship explicit for consumers;
- `major` is an exact decimal string for display and decimal-aware clients;
- `display` is optional presentation text.

The server must derive and validate the exponent from trusted currency metadata. It must not accept a client-provided exponent as authoritative.

A Laravel resource can own this mapping:

```php
final class AmountResource extends JsonResource
{
    public function toArray(Request $request): array
    {
        /** @var Amount $amount */
        $amount = $this->resource;
        $metadata = app(CurrencyMetadata::class);
        $formatter = app(AmountFormatter::class);

        return [
            'currency' => $amount->currency(),
            'minor' => (string) $amount->minor(),
            'minor_unit_exponent' => $metadata->minorUnitExponent(
                $amount->currency(),
            ),
            'major' => $formatter->decimal($amount),
            'display' => $formatter->display($amount, $request->getLocale()),
        ];
    }
}
```

There is a tradeoff here. `display` gives clients a ready value, but it couples the response to a locale. `major` gives the client control, but the client needs safe decimal formatting. Many APIs provide both.

What matters is that no client has to infer whether `amount` means minor or major units.

Percentages need the same clarity:

```json
{
  "tax_rate": {
    "ratio": "0.04",
    "percentage_points": "4"
  }
}
```

This is one synthetic 4 percent rate in two explicit representations.

For write APIs, choose one canonical representation. Do not accept both unless there is a strong compatibility reason. If you accept several legacy forms, use different field names and reject conflicting combinations.

## Frontend and backend ownership

The backend should own:

- authoritative money arithmetic;
- currency compatibility checks;
- currency exponent lookup;
- tax and fee calculations;
- rounding rules;
- allocation and remainder handling;
- persisted values;
- event payloads.

The frontend should own:

- locale selection;
- visual formatting when the backend does not supply it;
- input editing state;
- clearly marked provisional estimates when needed.

The frontend should not silently become a second accounting engine.

If a summary needs the total of several rows, prefer this:

```json
{
  "taxes": [
    {
      "name": "Synthetic tax A",
      "amount": {
        "currency": "JPY",
        "minor": "2000",
        "minor_unit_exponent": 0,
        "major": "2000",
        "display": "JPY 2,000"
      }
    },
    {
      "name": "Synthetic tax B",
      "amount": {
        "currency": "JPY",
        "minor": "2000",
        "minor_unit_exponent": 0,
        "major": "2000",
        "display": "JPY 2,000"
      }
    }
  ],
  "tax_total": {
    "currency": "JPY",
    "minor": "4000",
    "minor_unit_exponent": 0,
    "major": "4000",
    "display": "JPY 4,000"
  }
}
```

All values are synthetic.

The UI renders `tax_total`. It may still verify that rows look coherent in development, but it does not invent the authoritative total.

If the frontend must calculate, make the operation currency-aware:

```typescript
function add(left: Amount, right: Amount): Amount {
    if (
        left.currency !== right.currency ||
        left.exponent !== right.exponent
    ) {
        throw new Error('Cannot add amounts with different currencies')
    }

    return {
        currency: left.currency,
        exponent: left.exponent,
        minor: left.minor + right.minor,
    }
}
```

This is more code than `a + b`. That is a feature. The extra code represents rules that `a + b` cannot express.

## Event payloads make boundary mistakes permanent

An HTTP response can be changed with versioning and coordinated deployment. A stored event may be replayed for years.

That changes the migration strategy.

Suppose an old event payload contains this:

```json
{
  "schema_version": 1,
  "amount": "1000",
  "currency": "USD",
  "percentage": "4"
}
```

The values are synthetic. The payload is also ambiguous unless historical code defines whether `amount` is minor units and whether `percentage` means percentage points.

A new event should make both contracts explicit:

```json
{
  "schema_version": 2,
  "amount": {
    "minor": "1000",
    "currency": "USD"
  },
  "percentage": {
    "encoding": "percentage_points",
    "value": "4"
  }
}
```

This represents a synthetic 10.00 USD and a synthetic 4 percent rate.

Do not make every projector and reactor understand both payloads. Convert both versions at the deserialization boundary:

```php
final readonly class PriceChanged
{
    public function __construct(
        public Amount $amount,
        public Percent $percentage,
    ) {}

    /**
     * @param array<string, mixed> $payload
     */
    public static function fromPayload(array $payload): self
    {
        return match ($payload['schema_version'] ?? 1) {
            1 => new self(
                amount: Amount::fromMinor(
                    minor: $payload['amount'],
                    currency: $payload['currency'],
                ),
                percentage: Percent::fromPercentagePoints(
                    $payload['percentage'],
                ),
            ),
            2 => new self(
                amount: Amount::fromMinor(
                    minor: $payload['amount']['minor'],
                    currency: $payload['amount']['currency'],
                ),
                percentage: self::percentFromPayload($payload['percentage']),
            ),
            default => throw new UnexpectedValueException('Unsupported event schema version.'),
        };
    }
}
```

After `fromPayload()`, the rest of the application sees only `Amount` and `Percent`.

That is the boundary rule again.

A safe event migration normally uses:

1. dual-read;
2. single-write;
3. an explicit schema version;
4. production-slice replay tests with sanitized fixtures;
5. no rewrite of historical events unless there is a separate, proven need.

Dual-read means the application understands old and new payloads. Single-write means all newly stored events use only the new contract.

Avoid a permissive `fromArray()` that guesses based on which fields happen to exist. Silent fallbacks make malformed payloads look valid. They also make it hard to know when the old form is no longer used.

Use an explicit version or discriminator.

## Test the assumptions, not only the examples

The smallest currency matrix that can catch the `/ 100` class of bug contains exponents 0, 2, and 3.

```php
use PHPUnit\Framework\Assert;

it('creates amounts from major units', function (
    string $currency,
    string $major,
    int $expectedMinor,
) use ($metadata): void {
    $amount = Amount::fromMajor($major, $currency, $metadata);

    Assert::assertSame($currency, $amount->currency());
    Assert::assertSame($expectedMinor, $amount->minor());
})->with([
    'zero-decimal JPY' => ['JPY', '10000', 10000],
    'two-decimal USD' => ['USD', '10.00', 1000],
    'three-decimal KWD' => ['KWD', '10.000', 10000],
]);
```

Every monetary value is synthetic.

Test serialization with the same matrix:

```php
it('serializes explicit money units', function (
    Amount $amount,
    int $expectedExponent,
    string $expectedMajor,
) use ($serializer): void {
    $payload = $serializer->serialize($amount);

    Assert::assertSame((string) $amount->minor(), $payload['minor']);
    Assert::assertSame($amount->currency(), $payload['currency']);
    Assert::assertSame($expectedExponent, $payload['minor_unit_exponent']);
    Assert::assertSame($expectedMajor, $payload['major']);
})->with([
    'zero-decimal JPY' => [
        Amount::fromMinor(10000, 'JPY'),
        0,
        '10000',
    ],
    'two-decimal USD' => [
        Amount::fromMinor(1000, 'USD'),
        2,
        '10.00',
    ],
    'three-decimal KWD' => [
        Amount::fromMinor(10000, 'KWD'),
        3,
        '10.000',
    ],
]);
```

Test every accepted percentage encoding against the same canonical ratio:

```php
it('normalizes percentage encodings', function (Percent $percent): void {
    Assert::assertTrue(
        $percent->ratio()->isEqualTo('0.04'),
    );
})->with([
    'percentage points' => Percent::fromPercentagePoints('4'),
    'ratio' => Percent::fromRatio('0.04'),
    'basis points' => Percent::fromBasisPoints(400),
    'parts per million' => Percent::fromPartsPerMillion(40000),
]);
```

Each dataset row is the same synthetic 4 percent rate.

The cross-product matters too. Apply every percentage encoding to every currency exponent:

```php
it('applies the same rate across currency exponents', function (
    Amount $amount,
    Percent $percent,
    int $expectedMinor,
): void {
    $result = $percent->applyTo($amount, RoundingMode::HALF_UP);

    Assert::assertSame($amount->currency(), $result->currency());
    Assert::assertSame($expectedMinor, $result->minor());
})->with([
    'JPY from percentage points' => [
        Amount::fromMinor(10000, 'JPY'),
        Percent::fromPercentagePoints('4'),
        400,
    ],
    'USD from ratio' => [
        Amount::fromMinor(1000, 'USD'),
        Percent::fromRatio('0.04'),
        40,
    ],
    'KWD from basis points' => [
        Amount::fromMinor(10000, 'KWD'),
        Percent::fromBasisPoints(400),
        400,
    ],
]);
```

All amounts are synthetic.

For the frontend, add the regression at the contract level:

```typescript
describe.each([
    {
        currency: 'JPY',
        minor: '10000',
        exponent: 0,
        major: '10000',
    },
    {
        currency: 'USD',
        minor: '1000',
        exponent: 2,
        major: '10.00',
    },
    {
        currency: 'KWD',
        minor: '10000',
        exponent: 3,
        major: '10.000',
    },
])('$currency amount payload', ({ currency, minor, exponent, major }) => {
    it('preserves the backend value without a fixed divisor', () => {
        const amount = amountFromPayload({
            currency,
            minor,
            minor_unit_exponent: exponent,
            major,
            display: `${currency} ${major}`,
        })

        expect(amount.minor).toBe(BigInt(minor))
        expect(amount.exponent).toBe(exponent)
    })
})
```

Again, all amounts are synthetic.

Finally, prove the tests catch the regression. Temporarily put the fixed `/ 100` assumption back into the focused code path. The JPY and KWD cases must fail for the expected reason. Restore the correct implementation and confirm the same tests pass.

A green test that also passes with the bug restored is not a regression test.

## Laravel integration patterns

Laravel gives you several good places to enforce early conversion.

### Form Requests and DTOs

Validate primitive transport fields in the `FormRequest`. Convert them into value objects in a DTO immediately after validation.

Do not pass `$request->validated()` through the domain as an array.

### Eloquent casts

A custom cast can turn persisted money columns into an `Amount`:

```php
protected function casts(): array
{
    return [
        'subtotal' => AmountCast::class,
    ];
}
```

This works best when the amount and currency columns have a stable relationship. Be careful when a cast needs several attributes. The model must not permit one half of the value to change without the other.

### API clients

Map response JSON into a typed response DTO in the client adapter:

```php
final readonly class QuoteResponse
{
    public function __construct(
        public Amount $total,
        public Percent $taxRate,
    ) {}
}
```

Do not return a decoded associative array from the infrastructure layer and parse money inside a controller.

### Queue jobs

Serialize an explicit payload. Reconstruct the VO in the job's boundary code. Do not place an arbitrary object graph on the queue unless the serialization behavior is stable and intentional.

### Events

Store explicit primitives with a schema version. Expose value objects from event getters or constructors after deserialization.

The stored format is a contract. The in-memory format should be the strict type.

## Tradeoffs

Value objects are not free.

### More code

`Amount::fromMinor()` is longer than passing an integer. Currency guards and serializers add more code.

That code replaces assumptions that already existed. The assumptions were simply invisible before.

### Serialization work

Laravel, queue workers, event stores, and API resources need clear mappings. You cannot rely on accidental object serialization.

That work is useful. It forces the wire contract to become explicit.

### Library decisions

Money and decimal arithmetic contain many edge cases. A custom VO should usually wrap a maintained library rather than replace one.

The wrapper still has value. It gives the application one type and one vocabulary even if the underlying library changes.

### Cross-language duplication

A PHP `Amount` does not automatically give TypeScript the same safety. The API contract must carry enough information for the frontend to build its own type.

Generated schemas can help. They do not remove the need to decide who owns arithmetic.

### Performance

Decimal libraries and object creation cost more than primitive integer operations.

For most business applications, correctness matters more than this small cost. In a measured hot path, keep integer minor-unit operations inside the VO and optimize with evidence.

### Currency metadata changes

ISO metadata is data, not a constant invented by the application. Use a maintained source and record the currency with every amount.

If historical interpretation depends on metadata at the time of an event, include the needed version or exponent in the stored contract. Do not let future metadata changes reinterpret old values silently.

---

## No big bang is required

The rule is "wrap at the first boundary." It is not "rewrite the full application this quarter."

A practical migration can be small and safe.

### 1. Stop adding new primitive signatures

New actions, DTOs, and event getters should accept or return `Amount` and `Percent`.

### 2. Add boundary adapters

Keep legacy payloads at the edge:

```php
public function handleLegacy(
    int|string $minor,
    string $currency,
    int|string $percentagePoints,
): Result {
    return $this->handle(
        Amount::fromMinor($minor, $currency),
        Percent::fromPercentagePoints($percentagePoints),
    );
}
```

The compatibility method should be thin. It should not leak primitive values deeper into the system.

### 3. Migrate one path end to end

Choose a path with a known bug or active change. Convert:

- request or event input;
- DTO;
- action parameters;
- result;
- API resource;
- frontend contract;
- focused tests.

Do not convert unrelated paths in the same change.

### 4. Use dual-read and single-write

Read old and new serialized forms. Write only the new explicit form.

Add a counter for legacy reads so you know when the old contract is no longer active. Do not remove compatibility based only on age.

### 5. Remove adapters when evidence permits

After all producers use the new contract and historical data remains readable through versioned deserialization, remove the unused transport adapter.

### 6. Repeat when touching nearby code

The strict types spread through normal work. No feature freeze is needed.

This approach respects Chesterton's Fence. Old encodings may exist because of stored events, external consumers, or release ordering. Understand those constraints before deleting the compatibility path.

## A review checklist

When money or percentages appear in a change, ask:

- Does the field name state minor or major units?
- Is the currency attached to every amount?
- Does code assume an exponent of 2?
- Are decimal values transported as strings instead of floats?
- Is the percentage encoding explicit?
- Does conversion happen at the first boundary?
- Do method parameters and return types use `Amount` and `Percent`?
- Is rounding mode explicit where fractional minor units can occur?
- Does the backend own authoritative calculations?
- Is the JSON contract safe for JavaScript integer limits?
- Are stored events versioned?
- Can old events still deserialize into current value objects?
- Do tests cover exponent 0, 2, and 3?
- Do tests cover percentage points, ratios, and basis points?
- Has the regression test been proven to fail with the defect restored?

If a reviewer has to ask what a number means, the type or field name is incomplete.

## The lesson behind the line

The broken line was easy to fix:

```typescript
minor / 100
```

Remove the fixed divisor. Use a currency-aware value.

But "remember that some currencies have no decimal places" is too narrow a lesson. It asks every future developer to remember the same fact at every future call site.

The stronger lesson is structural:

- An amount without its currency is incomplete.
- An amount without its unit is ambiguous.
- A percentage without its encoding is ambiguous.
- A raw number crossing several layers invites each layer to invent its own meaning.

Wrap the value once, at the boundary. Give constructors names that state the encoding. Keep arithmetic and rounding with the type that owns them. Serialize a contract that names its units. Make the backend authoritative. Test the uncommon currency exponents, not only the common path.

Then a zero-decimal currency is not an edge case that wakes up an old bug.

It is just another valid input.
