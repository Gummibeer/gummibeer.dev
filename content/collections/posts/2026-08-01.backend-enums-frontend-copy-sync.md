Your backend has a `ReservationStatus` enum with 12 cases. Your frontend has a translation key for each. They're in sync — until they're not. An engineer adds `ReservationStatus::PendingReview` to the backend, ships it, and forgets to add the translation key. The status badge renders `pending_review` in production.

This isn't a process failure. It's an architecture failure. The label for a status badge isn't a translation concern — it's a fact about the enum case. It belongs next to the enum definition, not mirrored in a separate file that nothing forces you to keep complete.

## The Translation File Problem

The typical setup looks like this. PHP enum on the backend:

```php
enum ReservationStatus: string
{
    case Pending = 'pending';
    case Confirmed = 'confirmed';
    case CheckedIn = 'checked_in';
    case Cancelled = 'cancelled';
    case PendingReview = 'pending_review';
}
```

Angular translation file on the frontend:

```json
{
    "reservation_status": {
        "pending": "Awaiting confirmation",
        "confirmed": "Confirmed",
        "checked_in": "Checked in",
        "cancelled": "Cancelled"
    }
}
```

`pending_review` is missing. Nothing in either codebase complains. The frontend falls back to the raw key or an empty string, depending on how your i18n library handles misses, and the badge silently breaks.

The duplication isn't just a maintenance hazard. It's a design signal: you've split a single concern — what does this status mean to a human — across two separate files in two separate languages with no link between them.

## Metadata Maps on the Enum

The fix is to make the PHP enum the authoritative source of all display metadata and then share that data with the frontend.

```php
enum ReservationStatus: string
{
    case Pending = 'pending';
    case Confirmed = 'confirmed';
    case CheckedIn = 'checked_in';
    case Cancelled = 'cancelled';
    case PendingReview = 'pending_review';

    /**
     * @return array{label: string, color: string, description: string}
     */
    public function metadata(): array
    {
        return match ($this) {
            self::Pending => [
                'label' => 'Awaiting confirmation',
                'color' => 'yellow',
                'description' => 'The reservation has been submitted and is waiting for host confirmation.',
            ],
            self::Confirmed => [
                'label' => 'Confirmed',
                'color' => 'green',
                'description' => 'The host has confirmed the reservation.',
            ],
            self::CheckedIn => [
                'label' => 'Checked in',
                'color' => 'blue',
                'description' => 'The guest has checked in.',
            ],
            self::Cancelled => [
                'label' => 'Cancelled',
                'color' => 'red',
                'description' => 'The reservation was cancelled.',
            ],
            self::PendingReview => [
                'label' => 'Under review',
                'color' => 'orange',
                'description' => 'The reservation is under review before confirmation.',
            ],
        };
    }

    public function label(): string
    {
        return $this->metadata()['label'];
    }

    public function color(): string
    {
        return $this->metadata()['color'];
    }
}
```

The `match` inside `metadata()` is exhaustive. Add a new case without updating `metadata()` and PHP throws an `UnhandledMatchError` at runtime — and PHPStan or Psalm flags it statically before that. You can't forget it.

## Enforcing Completeness With a Test

Static analysis is your first line of defence, but a unit test is explicit and runs in CI regardless of whether the project has a static analysis setup:

```php
final class ReservationStatusTest extends TestCase
{
    public function test_all_cases_have_complete_metadata(): void
    {
        foreach (ReservationStatus::cases() as $status) {
            $metadata = $status->metadata();

            $this->assertArrayHasKey('label', $metadata, "Missing label for {$status->value}");
            $this->assertArrayHasKey('color', $metadata, "Missing color for {$status->value}");
            $this->assertArrayHasKey('description', $metadata, "Missing description for {$status->value}");
            $this->assertNotEmpty($metadata['label'], "Empty label for {$status->value}");
            $this->assertNotEmpty($metadata['color'], "Empty color for {$status->value}");
        }
    }
}
```

When someone adds `ReservationStatus::Disputed` and forgets `metadata()`, this test fails loudly with the name of the missing case. No production incident, no mystery badge.

## Sharing the Map With the Frontend

The metadata lives on the PHP enum. The Angular app needs it. There are three practical options:

**1. API endpoint.** Add a route that serialises all cases with their metadata. The frontend fetches it once and caches it:

```php
// routes/api.php
Route::get('/enums/reservation-status', function () {
    return collect(ReservationStatus::cases())
        ->mapWithKeys(fn ($status) => [
            $status->value => $status->metadata(),
        ]);
});
```

Response:

```json
{
    "pending": { "label": "Awaiting confirmation", "color": "yellow", "description": "..." },
    "confirmed": { "label": "Confirmed", "color": "green", "description": "..." }
}
```

**2. Generated JSON file.** Run a command at build time that writes the metadata to a static JSON file checked into the frontend repo. Slower feedback loop, but works with fully static frontends.

**3. Shared package.** For monorepos or teams that want type safety on both sides, publish the metadata as a typed package. Most teams don't need this.

The API endpoint is the right default for a Laravel + Angular stack. It's live, it's always in sync with the deployed backend, and it requires no build step.

## Consuming the Metadata in Angular

The frontend fetches the metadata once and stores it. A status badge component then uses it directly:

```typescript
// reservation-status.types.ts
export interface StatusMetadata {
    label: string;
    color: string;
    description: string;
}

export type ReservationStatusMap = Record<string, StatusMetadata>;
```

```typescript
// reservation-status.service.ts
@Injectable({ providedIn: 'root' })
export class ReservationStatusService {
    private http = inject(HttpClient);
    private metadata$ = this.http.get<ReservationStatusMap>('/api/enums/reservation-status').pipe(shareReplay(1));

    getMetadata(status: string): Observable<StatusMetadata | undefined> {
        return this.metadata$.pipe(map((map) => map[status]));
    }
}
```

```typescript
// status-badge.component.ts
@Component({
    selector: 'app-status-badge',
    template: `
        @if (metadata$ | async; as meta) {
            <span class="badge badge--{{ meta.color }}">{{ meta.label }}</span>
        }
    `,
})
export class StatusBadgeComponent {
    status = input.required<string>();
    private service = inject(ReservationStatusService);
    metadata$ = toObservable(this.status).pipe(switchMap((s) => this.service.getMetadata(s)));
}
```

When the backend ships `PendingReview`, the API endpoint includes it automatically. The Angular component gets the label, the color, and the description without a single frontend code change.

## The Trade-off Worth Naming

This pattern creates coupling: the frontend now depends on a specific API shape that the backend controls. That's intentional. The status metadata _is_ a backend concern — the backend defines what the statuses are, what they mean, and what colour a designer approved for them. Coupling the frontend to that source of truth is correct.

The alternative — duplicating the data in a translation file — creates the illusion of decoupling while actually creating hidden coupling that breaks silently. At least with an API endpoint, a missing case is immediately visible.

What you lose: the ability to customise copy per locale without backend involvement. If you need localised labels, the `metadata()` method can return a translation key instead of a hardcoded string, and the frontend resolves those keys through its i18n library. The enum remains the source of truth for _which_ key to use; the translation file handles the locale variants.

## Checklist When Adding a New Enum Case

1. Add the case to the PHP enum.
2. Add a `metadata()` arm for the case.
3. Run `php artisan test --filter ReservationStatusTest` — confirm it passes.
4. Deploy. The API endpoint includes the new case automatically.
5. Done.

No translation file to update. No grep across the Angular repo. No production badge showing raw enum values.

The backend enum is the definition of the status. The metadata is part of that definition. Put them together.
