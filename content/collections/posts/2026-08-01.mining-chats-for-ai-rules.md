I had corrected the same behaviour six times. Different sessions, different days, different projects — but the same mistake. The agent would add a `composer install` step to a CI job that already had one, I'd say "that's already there, don't add it," and the next session it would do it again from a blank slate. No memory. No continuity.

At some point I stopped being annoyed and got curious. I had a record of every correction I'd ever made — hundreds of JSONL files sitting in `~/.cursor/projects/*/agent-transcripts/`. The signal was all there. The problem was that it wasn't doing anything.

That was the starting point for building a self-improving rule file fed by my own transcript history.

## The File That Changed Everything

Cursor supports user-level `.mdc` rule files in `~/.cursor/rules/` that apply globally across every project and session. Mine is called `personal-feedback.mdc`, and it starts like this:

```
---
description: Accumulated personal feedback and corrections from Tom Witkowski to avoid repeating the same mistakes
alwaysApply: true
---

# Personal Feedback & Corrections

Extracted from 503 past chat transcripts. Items marked [HIGH FREQ] appeared in 3+ transcripts.
```

The file is now 174 items across five categories: Workflow, Communication, Code, Tool Use, and Style. The agent reads it at the start of every conversation. The repeat corrections stopped.

Getting there required figuring out how to actually mine 503 transcripts without losing my mind or blowing through a context window the size of an apartment.

## Two Kinds of Signal

The obvious signal is explicit: I said "don't do X" and the agent said "noted." Those are easy to find — search for negation patterns in user messages. "No.", "stop", "don't", "wrong", "actually", "that's not right." Grep for them and you'll surface most of the direct corrections.

The harder signal is implicit, and it's higher value. When I fixed something manually and then told the agent — "I updated the file, read it" — the agent would read it and summarise what changed. That summary, right there in the assistant message, is a clean statement of what the AI got wrong. It doesn't say "I was wrong because..." but the content of what changed tells you exactly what the problem was.

This came up enough that I made it an explicit instruction to the extraction subagents: look for assistant messages that follow user messages containing "I fixed it", "I updated", "I adjusted", "I did it manually." The assistant's next message is usually a faithful description of the delta — and the delta is the correction.

A real example from a transcript: I manually refactored a function the agent had made too complex, told it I'd updated the file, and the agent responded with something like "I see you've simplified the `buildFinancialImpact` method — removed the intermediate array and collapsed the loop." That became: **Do not make unrequested refactors alongside bug fixes.** The agent had heard it explicitly half a dozen times, but mining the implicit signals is what made it show up as `[HIGH FREQ]`.

## Handling 503 Transcripts Without a Context Explosion

When I first asked the agent to read my transcripts for corrections, it was working with eleven files from a single project. That was fine. Then I pointed it at the full `~/.cursor/projects/` tree and the number was 503 files totalling 29 MB. The largest single transcript was 2.3 MB.

You cannot dump that into a single context. You have to batch.

The approach that worked: one subagent per batch of roughly 25 transcripts, running in parallel waves. Each subagent gets a list of file paths, reads them, and writes its findings to a temp file at a predictable location:

```bash
/tmp/transcript-feedback/batch-001.md
/tmp/transcript-feedback/batch-002.md
...
/tmp/transcript-feedback/batch-021.md
```

Each batch writes structured output — a flat list of extracted signals, one per line, with the source transcript UUID so you can trace back if something looks off. The coordinator agent then reads all 21 temp files, a total of maybe 50–80 KB of extracted signal instead of 29 MB of raw conversation.

For the oversized transcripts — the ones above 400 KB — each gets its own dedicated subagent with chunked reading rather than trying to load the whole thing at once. They were a small minority (maybe 6–8 files) but they were also the longest sessions and therefore the highest-signal ones.

The whole extraction run, dispatching the batches in two parallel waves of ten, took about twelve minutes.

## Deduplication is Where the Value Lives

Raw extraction gives you a lot of redundant entries. "Don't commit without asking" shows up seventeen times across seventeen sessions. "Use `filled()` instead of `!empty()`" shows up eight times. "Stop adding sign-off phrases" shows up fourteen times, which is embarrassing.

Deduplication is mechanical: group by semantic similarity, pick the clearest phrasing, count occurrences. Anything that appears in three or more transcripts gets marked `[HIGH FREQ]`. That tag does two things — it tells the agent this is a recurring issue and worth extra attention, and it tells me which corrections I should probably have made months earlier.

The grouping also surfaces patterns I hadn't consciously noticed. Seven separate transcripts had some variant of "I had to escalate to caps to get the AI to proceed" — `"NO."`, `"exec!"`, `"JUST DO IT"`. That became a single rule: **Do not over-investigate before acting on explicit, clear instructions.** Seeing the cluster made the rule clearer than any individual correction would have.

## The Ongoing Process

The full re-scan was a one-time operation. Keeping the file current doesn't need another one.

The practical process I settled on: when something worth capturing surfaces mid-conversation, I add it immediately — not at the end of the session, and definitely not in a batch cleanup later. I'll say "add that to the feedback rule" and the agent appends it inline. The rule file is a living document, not a snapshot.

This matters because the value of the rule compounds over time only if it's kept current. A rule file from six months ago that hasn't been touched is mostly a historical curiosity. One that was updated yesterday is a working contract.

The one thing that doesn't work is trying to automate the "end of session" append. There's no reliable signal for when a session ends, and the agent can't unilaterally decide what's worth capturing without context. The trigger has to be human. The execution can be agent.

## What the File Actually Looks Like

A few representative entries, to make this concrete:

```markdown
## Workflow

- **Do NOT commit and push unless explicitly asked to.** [HIGH FREQ]
- **Do not stop until ALL to-dos are completed.** [HIGH FREQ]
- **When Tom manually updates a file and tells you about it**, read the updated file
  before continuing — do not proceed from the old mental model. [HIGH FREQ]
- **When Tom rolls back the AI's implementation**, replace with the minimal/basic
  fix only — do not re-introduce complexity that caused the rollback.

## Code

- **Prefer Laravel Collections** over PHP array helper function chains
  (array_map, array_filter, etc.). [HIGH FREQ]
- **Do not make unrequested refactors alongside bug fixes.** [HIGH FREQ]
- **Remove unused imports after refactoring.**
- **Dead code should be removed proactively**, not just commented out.

## Communication

- **Do NOT add sign-off phrases** like "WITNESS ME!" or "Let me cook."
  Maintain a professional, direct tone. [HIGH FREQ]
- **Keep chat responses concise and dense** — put detail into the markdown
  file or structured output. [HIGH FREQ]
- **When a proposed fix has multiple options**, state a clear recommendation
  rather than listing options neutrally.
```

The `[HIGH FREQ]` tag does actual work. The agent treats it as increased weight — not just "this was mentioned once" but "this is a recurring failure mode, pay extra attention." In practice that means it catches these more reliably on the first attempt rather than needing a correction.

## The Honest Trade-Off

The rule file is not a replacement for judgment. It encodes patterns — things that were wrong repeatedly, preferences that don't need to be re-explained every session. What it can't encode is context: why a particular decision was made, what the broader architectural constraints are, which rules have exceptions in specific situations.

A rule that says "never commit without asking" is correct ninety-five percent of the time. The five percent where it's wrong is when I'm in a rapid iteration mode and I've said "just commit everything as you go." The rule doesn't know that. I still have to pay attention.

What it does do is eliminate the low-level friction. I'm not re-explaining the same preferences, not correcting the same stylistic choices, not catching the same workflow mistakes. The cognitive overhead that was going into those repeated corrections is now available for things that actually require thinking.

Mining the transcripts was a weekend afternoon. Writing the extraction prompt, running the batches, reviewing and deduplicating the output. The rule file has been compounding ever since. If you've been using an AI agent for more than a month and you don't have something like this, you're leaving a lot of signal on the floor.
