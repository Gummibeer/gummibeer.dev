The ticket comes in at 11 AM: "Checkout is broken. Orders are failing with 422."

You open your service logs, find the error, and start reading the validation stack. The field `pricing.unit_cost` is missing. You check your schema. It's required. You check when you last deployed. Three days ago, and the field was there then. You check the test suite. Passes. You check production payloads from this morning. The field is missing.

Two hours later you find it: the pricing service had a breaking schema change last night. They renamed `unit_cost` to `cost_per_unit`. Your service was right. Your validation was right. The 422 was correct — you received a payload that didn't match the contract you agreed on.

The bug belonged to the pricing service. But you owned the two hours of debugging.

That's the actual problem to solve.

---

## The 422 You Didn't Cause

A 422 Unprocessable Content means your service received a request it could parse but couldn't process — usually a validation failure. In a microservices system, your service is often just a pass-through of data that originated upstream. When that upstream data changes shape without notice, your validation fires, and the error surfaces at your boundary.

This makes the 422 your symptom, not your cause.

The client team blames you because you returned the error. You investigate because you assume you must have broken something. Neither assumption is wrong — they're just operating without cross-service observability. The gap isn't discipline, it's tooling.

Three things close that gap: structured log context, contract tests, and clear post-mortems.

## Structured Logging With Upstream Context

The first thing that will cut your debugging time in half is propagating a correlation ID across every service hop, and logging the upstream response alongside your own validation error.

Here's what a useful error log looks like when your order service fails to process a pricing service response:

```json
{
    "level": "error",
    "message": "Payload validation failed",
    "service": "order-service",
    "correlation_id": "req_01hwk3n8q2xzfg4j5v7",
    "upstream_service": "pricing-service",
    "upstream_request_id": "prc_7f3a19d2-c4e1-4b88-a901-3d2f1c09e856",
    "upstream_response_status": 200,
    "validation_errors": {
        "pricing.unit_cost": ["The pricing.unit_cost field is required."]
    },
    "upstream_payload_keys": ["pricing.cost_per_unit", "pricing.currency", "pricing.tax_rate"],
    "timestamp": "2026-04-23T09:14:37Z"
}
```

The key fields here are `upstream_request_id` and `upstream_payload_keys`. With the request ID you can go to the pricing service's own logs and see exactly what it returned and why. With the payload keys you can immediately see that `cost_per_unit` arrived but `unit_cost` did not — which tells you this is a field rename, not a null value or a missing record.

In Laravel, you can centralise this with a middleware that pulls a correlation ID from the incoming request and attaches it to your outbound HTTP client calls:

```php
<?php

declare(strict_types=1);

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Log;
use Symfony\Component\HttpFoundation\Response;

final class PropagateCorrelationId
{
    public function handle(Request $request, Closure $next): Response
    {
        $correlationId = $request->header('X-Correlation-ID') ?? 'req_'.str()->ulid();

        $request->headers->set('X-Correlation-ID', $correlationId);

        Log::withContext(['correlation_id' => $correlationId]);

        return $next($request);
    }
}
```

Then in your HTTP client wrapper, attach the correlation ID to every outbound call and log the raw response before validation:

```php
<?php

declare(strict_types=1);

namespace App\Services;

use Illuminate\Http\Client\Response;
use Illuminate\Support\Facades\Http;
use Illuminate\Support\Facades\Log;

final class PricingServiceClient
{
    public function fetchPricing(string $productId): array
    {
        $response = Http::withHeaders([
            'X-Correlation-ID' => request()->header('X-Correlation-ID'),
        ])->get(config('services.pricing.url')."/products/{$productId}/pricing");

        Log::info('Pricing service response received', [
            'upstream_service' => 'pricing-service',
            'upstream_request_id' => $response->header('X-Request-ID'),
            'upstream_response_status' => $response->status(),
            'upstream_payload_keys' => array_keys(data_get($response->json(), 'pricing', [])),
        ]);

        return $response->json();
    }
}
```

Now when validation fails five minutes later, you have everything you need in the same log stream.

## Contract Tests: Catch Schema Regressions Before They Ship

Structured logs tell you what broke. Contract tests stop it from breaking in the first place.

Consumer-driven contract testing with [Pact](https://pact.io) lets you define the shape you expect from an upstream service, publish that expectation to a broker, and have the upstream team verify their service still satisfies it before every deploy.

Here's a consumer-side Pact test for the pricing service interaction:

```php
<?php

declare(strict_types=1);

namespace Tests\Contract;

use PhpPact\Consumer\InteractionBuilder;
use PhpPact\Consumer\Model\ConsumerRequest;
use PhpPact\Consumer\Model\ProviderResponse;
use PhpPact\Consumer\MockServer;
use PhpPact\Consumer\MockServerConfig;
use PHPUnit\Framework\TestCase;

final class PricingServiceContractTest extends TestCase
{
    public function test_pricing_response_contains_unit_cost(): void
    {
        $config = new MockServerConfig();
        $config->setConsumer('order-service');
        $config->setProvider('pricing-service');

        $builder = new InteractionBuilder($config);

        $builder
            ->given('product SKU-001 exists')
            ->uponReceiving('a request for product pricing')
            ->with(
                (new ConsumerRequest())
                    ->setMethod('GET')
                    ->setPath('/products/SKU-001/pricing')
            )
            ->willRespondWith(
                (new ProviderResponse())
                    ->setStatus(200)
                    ->addHeader('Content-Type', 'application/json')
                    ->setBody([
                        'pricing' => [
                            'unit_cost' => 49.99,
                            'currency'  => 'USD',
                            'tax_rate'  => 0.19,
                        ],
                    ])
            );

        // Run your actual client against the mock and assert it works
        $client = new \App\Services\PricingServiceClient();
        $result = $client->fetchPricing('SKU-001');

        $this->assertArrayHasKey('unit_cost', $result['pricing']);
        $this->assertEquals(49.99, $result['pricing']['unit_cost']);

        $builder->verify();
    }
}
```

This contract gets published to the Pact Broker. When the pricing team tries to rename `unit_cost` to `cost_per_unit`, their provider verification step fails — because your published contract says you need `unit_cost`. They get a failing build before the change reaches production. You get a conversation instead of a 422.

The critical discipline here is running `can-i-deploy` in your pipeline before every production deployment. If any consumer contract is broken by your current code, the gate stops you.

## The Verbatim Replay Trap

When debugging cross-service failures, a common instinct is to capture the last known good request and replay it to verify your service still processes it correctly. This is useful, but it has a subtle trap.

If you captured the request before the upstream schema change, replaying it will succeed — because the old payload is valid against your old expectations. But the live system is now sending the new payload shape. A passing replay proves nothing about the current failure.

The verbatim replay is only meaningful if you replay what the upstream service is sending right now, not what it was sending when things worked.

Before you replay, ask: "Is this payload from before or after the upstream change?" If before, you're not testing the real problem. You need to capture a fresh payload from the broken live flow, or construct one that matches what the upstream service currently produces.

This is also where contract tests prove their worth again: they test against what the provider currently returns, not a frozen snapshot.

## Writing the Post-Mortem That Doesn't Lie

When cross-service failures hit production, post-mortems often drift into blame because the failure surface (your 422) and the root cause (their schema change) are owned by different teams.

A useful post-mortem for this class of failure answers five questions:

**1. What did users experience?**
Checkout failed for X% of orders between 08:50 and 11:20 UTC. Orders were not created. No charges were made.

**2. What was the proximate cause?**
The order service returned 422 because the field `pricing.unit_cost` was absent from the pricing service response.

**3. What was the root cause?**
The pricing service deployed a schema change at 08:47 UTC that renamed `unit_cost` to `cost_per_unit`. No consumer notification was issued. No contract tests existed to catch the regression.

**4. Why did our tooling not catch this before users did?**
No consumer-driven contract tests were in place between order-service and pricing-service. The pricing service CI pipeline did not verify consumer contracts before deploying.

**5. What changes prevent recurrence?**

- Add Pact contract tests for the pricing service integration (order-service team, by X date)
- Add `can-i-deploy` gate to pricing-service CI pipeline (pricing team, by X date)
- Add alerting on upstream response schema drift in production (platform team, by X date)

Notice what's missing: no section called "Who Made the Mistake." The pricing team made a breaking change without a contract gate. That's a process gap, not a moral failure. The post-mortem documents the gap and closes it. Assigning blame produces defensiveness; documenting process gaps produces pull requests.

## Alerting on Schema Drift Before It Reaches Users

Even with contract tests, not every upstream service will run them. You want a production safety net.

One approach: log a hash of the upstream response schema on every call, and alert when that hash changes.

```php
<?php

declare(strict_types=1);

namespace App\Services;

use Illuminate\Support\Facades\Log;

final class SchemaChangeDetector
{
    public function detect(string $service, array $payload, string $path = ''): void
    {
        $keys = $this->extractKeys($payload);
        sort($keys);
        $hash = md5(implode(',', $keys));

        $cacheKey = "schema_hash:{$service}:{$path}";
        $previousHash = cache()->get($cacheKey);

        if ($previousHash !== null && $previousHash !== $hash) {
            Log::warning('Upstream schema change detected', [
                'upstream_service' => $service,
                'path'             => $path,
                'previous_hash'    => $previousHash,
                'current_hash'     => $hash,
                'current_keys'     => $keys,
            ]);
        }

        cache()->put($cacheKey, $hash, now()->addDay());
    }

    private function extractKeys(array $array, string $prefix = ''): array
    {
        $keys = [];
        foreach ($array as $key => $value) {
            $full = $prefix !== '' ? "{$prefix}.{$key}" : $key;
            $keys[] = $full;
            if (is_array($value)) {
                $keys = array_merge($keys, $this->extractKeys($value, $full));
            }
        }
        return $keys;
    }
}
```

Wire this to an alerting channel and you'll know about schema changes in real time — often before the failure reaches users at scale.

## The Summary

Cross-service failures look like your bug because the error surfaces at your boundary. They're not. The work is building the infrastructure that makes the real owner visible within minutes, not hours.

Three things that deliver that:

1. **Propagate correlation IDs and log upstream context with every validation failure.** You need to be able to trace a 422 to a specific upstream response within 60 seconds.

2. **Run consumer-driven contract tests and gate deploys on them.** This moves schema regressions from production incidents to CI failures — where they belong.

3. **Write post-mortems that document process gaps, not people.** Blame produces defensiveness. Process documentation produces prevention.

The 422 that started this story was correct. The gap was that nobody could prove it fast enough.
