You receive a transaction. The sender name is "Bob Smith". Your watchlist has "Robert Smith". Should those match?

Exact match says no. A naive fuzzy match with a low threshold says yes — and also matches "Robb Smyth", "Rob Smithe", "Bart Schmidt", and a dozen other names you absolutely should not flag. Compliance tooling needs to answer this correctly at scale, under audit, where both false negatives (missing a real hit) and false positives (blocking a legitimate customer) have real costs.

The right approach is a pipeline. Not a single algorithm with a tuned threshold, but multiple strategies combined into a risk score that you classify into an enum with legal meaning. This post walks through building that pipeline in PHP.

## Why Both Naive Approaches Fail

Exact string matching fails for names more than any other domain. Names have:

- **Nicknames**: Bob/Robert, Bill/William, Liz/Elizabeth, Chuck/Charles
- **Cultural ordering**: "Zhang Wei" vs "Wei Zhang"
- **Transliteration variance**: Müller/Mueller/Muller, Dvořák/Dvorak/Dvorak
- **Honorifics and particles**: "Dr. Jean-Pierre de la Fontaine" vs "Jean Pierre Delafontaine"
- **OCR and transcription errors**: Torn edges, bad handwriting, legacy systems that strip diacritics

Naive fuzzy matching (pick a threshold, call it done) fails in the opposite direction. Jaro-Winkler between "Rob Smith" and "Ron Smith" is 0.97 — high confidence. But "Ron Smith" is a different person. At scale, with a list of 500k screened names, a 1% false positive rate generates 5,000 wrong flags per batch. Your compliance team can't clear 5,000 cases by hand.

The pipeline approach separates concerns: normalize first, then apply multiple matching strategies, then combine signals into a classification. Each layer has a specific job.

## Stage 1: Token Normalization

Before any comparison, get both strings into a canonical form. This eliminates noise that isn't semantically meaningful.

```php
final class NameNormalizer
{
    private const HONORIFICS = [
        'mr', 'mrs', 'ms', 'miss', 'dr', 'prof', 'rev', 'sir', 'dame',
        'jr', 'sr', 'ii', 'iii', 'iv',
    ];

    public function normalize(string $name): NormalizedName
    {
        // Lowercase and convert to ASCII
        $name = mb_strtolower($name, 'UTF-8');
        $name = $this->transliterate($name);

        // Strip punctuation except hyphens within tokens
        $name = preg_replace('/[^\p{L}\p{N}\s\-]/u', ' ', $name);

        // Tokenize
        $tokens = preg_split('/[\s\-]+/', $name, flags: PREG_SPLIT_NO_EMPTY);

        // Remove honorifics and single-character tokens (initials handled separately)
        $initials = [];
        $words = [];

        foreach ($tokens as $token) {
            if (in_array($token, self::HONORIFICS, strict: true)) {
                continue;
            }

            if (strlen($token) === 1) {
                $initials[] = $token;
                continue;
            }

            $words[] = $token;
        }

        // Sort tokens to normalize ordering
        sort($words);

        return new NormalizedName(
            tokens: $words,
            initials: $initials,
            raw: implode(' ', $words),
        );
    }

    private function transliterate(string $input): string
    {
        // Use intl if available, fall back to a manual map
        if (class_exists(\Transliterator::class)) {
            $transliterator = \Transliterator::create('Any-Latin; Latin-ASCII');
            return $transliterator->transliterate($input) ?: $input;
        }

        return strtr($input, [
            'ä' => 'ae', 'ö' => 'oe', 'ü' => 'ue', 'ß' => 'ss',
            'á' => 'a',  'é' => 'e',  'í' => 'i',  'ó' => 'o',  'ú' => 'u',
            'à' => 'a',  'è' => 'e',  'ì' => 'i',  'ò' => 'o',  'ù' => 'u',
            'â' => 'a',  'ê' => 'e',  'î' => 'i',  'ô' => 'o',  'û' => 'u',
            'ç' => 'c',  'ñ' => 'n',  'ø' => 'o',  'å' => 'a',
            'æ' => 'ae', 'œ' => 'oe', 'ð' => 'd',  'þ' => 'th',
        ]);
    }
}
```

Sorting tokens is the key move for cultural name ordering. "Zhang Wei" and "Wei Zhang" normalize to the same token set: `['wei', 'zhang']`. The ordering stops being a signal of difference.

The `NormalizedName` value object carries both the token list and the joined string, so downstream stages can operate on whichever representation suits them.

```php
final readonly class NormalizedName
{
    public function __construct(
        public array $tokens,
        public array $initials,
        public string $raw,
    ) {}
}
```

## Stage 2: Nickname Graph

Token normalization doesn't help with Bob/Robert. For that you need a nickname graph: a data structure that maps canonical names to all their known equivalents and vice versa.

The best freely available data source is the [names dataset from OpenNLP](https://opennlp.apache.org/), supplemented by [nickname databases on GitHub](https://github.com/onyxrev/common_nicknames) and the DIMECO database. For a production system, you load this into a lookup table at startup and query it at match time.

```php
final class NicknameGraph
{
    /** @var array<string, string[]> */
    private array $graph = [];

    public static function fromCsv(string $path): self
    {
        $instance = new self();

        $handle = fopen($path, 'r');
        while (($row = fgetcsv($handle)) !== false) {
            // Each row: canonical,nickname1,nickname2,...
            $canonical = strtolower(trim($row[0]));
            $nicknames = array_map(
                fn (string $n) => strtolower(trim($n)),
                array_slice($row, 1),
            );

            foreach ($nicknames as $nickname) {
                $instance->graph[$nickname][] = $canonical;
                $instance->graph[$canonical][] = $nickname;
            }
        }
        fclose($handle);

        return $instance;
    }

    /**
     * Returns all known equivalents for a name token,
     * including the token itself.
     *
     * @return string[]
     */
    public function equivalents(string $token): array
    {
        return array_unique([
            $token,
            ...($this->graph[$token] ?? []),
        ]);
    }

    public function areEquivalent(string $a, string $b): bool
    {
        if ($a === $b) {
            return true;
        }

        return in_array($b, $this->graph[$a] ?? [], strict: true)
            || in_array($a, $this->graph[$b] ?? [], strict: true);
    }
}
```

When you compare two normalized names token by token, replace each exact equality check with `$nicknameGraph->areEquivalent($tokenA, $tokenB)`. "Bob" and "Robert" both expand to the same canonical cluster and register as equivalent.

A gotcha: nickname graphs get circular fast. Robert → Bob → Bobby → Rob → Robert. The data structure handles this because `equivalents()` returns a flat unique list — you never recurse, you just expand one level from the lookup table.

## Stage 3: Scoring with Jaro-Winkler

Nickname matching handles known aliases. For everything else — typos, transliteration variants, OCR artifacts — you need string similarity. Jaro-Winkler is the right algorithm for names:

- It weights prefix matches more heavily, which matters for names (misspellings tend to be later in the string)
- It handles transpositions well (Smtih/Smith)
- Its output is bounded [0, 1], which composes cleanly into a pipeline

PHP doesn't ship Jaro-Winkler in the standard library, but the algorithm is compact enough to implement directly:

```php
final class JaroWinkler
{
    private const PREFIX_SCALE = 0.1;
    private const PREFIX_MAX_LENGTH = 4;

    public function similarity(string $a, string $b): float
    {
        if ($a === $b) {
            return 1.0;
        }

        $aLen = strlen($a);
        $bLen = strlen($b);

        if ($aLen === 0 || $bLen === 0) {
            return 0.0;
        }

        $matchWindow = max($aLen, $bLen);
        $matchWindow = (int) floor($matchWindow / 2) - 1;

        $aMatches = array_fill(0, $aLen, false);
        $bMatches = array_fill(0, $bLen, false);

        $matches = 0;
        $transpositions = 0;

        for ($i = 0; $i < $aLen; $i++) {
            $start = max(0, $i - $matchWindow);
            $end   = min($i + $matchWindow + 1, $bLen);

            for ($j = $start; $j < $end; $j++) {
                if ($bMatches[$j] || $a[$i] !== $b[$j]) {
                    continue;
                }

                $aMatches[$i] = true;
                $bMatches[$j] = true;
                $matches++;
                break;
            }
        }

        if ($matches === 0) {
            return 0.0;
        }

        $k = 0;
        for ($i = 0; $i < $aLen; $i++) {
            if (! $aMatches[$i]) {
                continue;
            }

            while (! $bMatches[$k]) {
                $k++;
            }

            if ($a[$i] !== $b[$k]) {
                $transpositions++;
            }

            $k++;
        }

        $jaro = (
            $matches / $aLen +
            $matches / $bLen +
            ($matches - $transpositions / 2) / $matches
        ) / 3;

        // Winkler prefix bonus
        $prefix = 0;
        for ($i = 0; $i < min(self::PREFIX_MAX_LENGTH, min($aLen, $bLen)); $i++) {
            if ($a[$i] !== $b[$i]) {
                break;
            }
            $prefix++;
        }

        return $jaro + $prefix * self::PREFIX_SCALE * (1 - $jaro);
    }
}
```

Jaro-Winkler alone is not the full story. Layer it with phonetic matching for a second signal:

```php
final class PhoneticMatcher
{
    public function match(string $a, string $b): bool
    {
        // metaphone is better than soundex for names — fewer collisions
        return metaphone($a) === metaphone($b);
    }

    public function bothSoundexMatch(string $a, string $b): bool
    {
        return soundex($a) === soundex($b);
    }
}
```

Phonetic codes are binary (match/no match) and have a high false-positive rate when used alone, but as a supporting signal they're useful. "Schmidt" and "Smith" share a Metaphone code — that's intentional, they sound similar in English. "Zhang" and "Chang" share one too, which is relevant in a transliteration context.

## Stage 4: Token-Pair Scoring

Names are multi-token. You can't just score the full strings — you need to align tokens optimally and score the best assignment.

```php
final class TokenPairScorer
{
    public function __construct(
        private JaroWinkler $jaroWinkler,
        private NicknameGraph $nicknameGraph,
        private PhoneticMatcher $phoneticMatcher,
    ) {}

    /**
     * Returns a score in [0, 1] for the best token alignment between two names.
     */
    public function score(NormalizedName $a, NormalizedName $b): float
    {
        if (empty($a->tokens) || empty($b->tokens)) {
            return 0.0;
        }

        $scores = [];

        foreach ($a->tokens as $tokenA) {
            foreach ($b->tokens as $tokenB) {
                $scores[$tokenA][$tokenB] = $this->scoreTokenPair($tokenA, $tokenB);
            }
        }

        // Greedy assignment: pair each token in A with its best match in B
        $used = [];
        $totalScore = 0.0;
        $pairs = 0;

        arsort($scores); // sort outer by token name; inner we'll sort by score
        foreach ($a->tokens as $tokenA) {
            $best = 0.0;
            $bestB = null;

            foreach ($b->tokens as $tokenB) {
                if (isset($used[$tokenB])) {
                    continue;
                }

                if ($scores[$tokenA][$tokenB] > $best) {
                    $best = $scores[$tokenA][$tokenB];
                    $bestB = $tokenB;
                }
            }

            if ($bestB !== null) {
                $used[$bestB] = true;
                $totalScore += $best;
                $pairs++;
            }
        }

        // Penalize token count mismatch
        $maxTokens = max(count($a->tokens), count($b->tokens));
        return $pairs > 0 ? $totalScore / $maxTokens : 0.0;
    }

    private function scoreTokenPair(string $a, string $b): float
    {
        if ($this->nicknameGraph->areEquivalent($a, $b)) {
            return 1.0;
        }

        $jw = $this->jaroWinkler->similarity($a, $b);

        // Phonetic match boosts a borderline JW score
        if ($jw >= 0.7 && $this->phoneticMatcher->match($a, $b)) {
            $jw = min(1.0, $jw + 0.05);
        }

        return $jw;
    }
}
```

The greedy assignment isn't the global optimum (you'd need the Hungarian algorithm for that) but it's O(n²) instead of O(n³) and close enough for name matching where token counts rarely exceed four or five.

The denominator uses `max(count($a->tokens), count($b->tokens))` rather than `count($a->tokens)`. This penalizes when one name has extra tokens the other doesn't — "Robert James Smith" against "Robert Smith" should score lower than two perfectly matching two-token names.

## Stage 5: Risk Classification

Raw scores don't belong in business logic. What belongs in business logic is a risk classification: an enum that says what action to take.

```php
enum NameMatchRisk: string
{
    case Match        = 'match';
    case PossibleMatch = 'possible_match';
    case NoMatch      = 'no_match';

    public function requiresManualReview(): bool
    {
        return $this === self::PossibleMatch;
    }

    public function shouldBlock(): bool
    {
        return $this === self::Match;
    }

    public function isCleared(): bool
    {
        return $this === self::NoMatch;
    }
}
```

The classifier maps scores to this enum. The thresholds are yours to tune — what follows is a starting point, not gospel:

```php
final class NameMatchClassifier
{
    private const MATCH_THRESHOLD         = 0.92;
    private const POSSIBLE_MATCH_THRESHOLD = 0.78;

    public function __construct(
        private TokenPairScorer $scorer,
        private NameNormalizer $normalizer,
    ) {}

    public function classify(string $candidate, string $screened): NameMatchRisk
    {
        $normalizedCandidate = $this->normalizer->normalize($candidate);
        $normalizedScreened  = $this->normalizer->normalize($screened);

        // Exact normalized match short-circuits
        if ($normalizedCandidate->raw === $normalizedScreened->raw) {
            return NameMatchRisk::Match;
        }

        $score = $this->scorer->score($normalizedCandidate, $normalizedScreened);

        return match (true) {
            $score >= self::MATCH_THRESHOLD          => NameMatchRisk::Match,
            $score >= self::POSSIBLE_MATCH_THRESHOLD => NameMatchRisk::PossibleMatch,
            default                                  => NameMatchRisk::NoMatch,
        };
    }

    /**
     * Screen a candidate against an entire list. Returns the highest-risk result found.
     *
     * @param  string[] $screenedList
     */
    public function screenAgainstList(string $candidate, array $screenedList): NameMatchRisk
    {
        $highest = NameMatchRisk::NoMatch;

        foreach ($screenedList as $screened) {
            $result = $this->classify($candidate, $screened);

            if ($result === NameMatchRisk::Match) {
                return $result; // can't do worse, stop early
            }

            if ($result === NameMatchRisk::PossibleMatch) {
                $highest = $result;
            }
        }

        return $highest;
    }
}
```

The early return on `Match` matters at scale. If your watchlist has 50,000 entries and the first 200 are already `NoMatch`, you don't gain anything by comparing the remaining 49,800 before returning.

For large lists you'll want to precompute a candidate set using phonetic blocking first — index your watchlist by Metaphone code, then only score within the same phonetic bucket. This takes screening from O(n) scoring calls to O(k) where k is the bucket size, typically 10–200 entries.

## Stage 6: Testing at Scale

The classifier is only as good as your tests. "Bob Smith" matching "Robert Smith" is trivial to verify manually. The problem is the long tail: 5,000 adversarial pairs that probe the edge cases.

Generate your test set programmatically:

```php
final class AdversarialNamePairGenerator
{
    private array $typoVariants = [
        // Common keyboard transpositions and double-letter errors
        fn (string $s) => substr_replace($s, strrev(substr($s, 1, 2)), 1, 2), // transpose chars 1-2
        fn (string $s) => $s . $s[-1],   // double last character
        fn (string $s) => substr($s, 0, -1), // drop last character
    ];

    /**
     * @param  string[] $names
     * @return array<array{candidate: string, screened: string, expected: NameMatchRisk}>
     */
    public function generate(array $names): array
    {
        $pairs = [];

        foreach ($names as $name) {
            // Should match: nickname substitution
            $pairs[] = $this->nicknameVariant($name, NameMatchRisk::Match);

            // Should match: token reordering
            $pairs[] = $this->reorderTokens($name, NameMatchRisk::Match);

            // Should match: minor typo
            $pairs[] = $this->typoPair($name, NameMatchRisk::PossibleMatch);

            // Should not match: different name entirely
            $pairs[] = $this->differentName($name, $names, NameMatchRisk::NoMatch);
        }

        return array_filter($pairs);
    }

    // ... generation methods
}
```

The critical test cases to cover explicitly:

```php
final class NameMatchClassifierTest extends TestCase
{
    /** @dataProvider nicknamePairs */
    public function test_nickname_equivalents_classify_as_match(
        string $candidate,
        string $screened,
    ): void {
        $result = $this->classifier->classify($candidate, $screened);
        $this->assertSame(NameMatchRisk::Match, $result);
    }

    public static function nicknamePairs(): array
    {
        return [
            'bob robert'       => ['Bob Smith',      'Robert Smith'],
            'bill william'     => ['Bill Johnson',   'William Johnson'],
            'liz elizabeth'    => ['Liz Taylor',     'Elizabeth Taylor'],
            'chuck charles'    => ['Chuck Davis',    'Charles Davis'],
            'kate katherine'   => ['Kate Brown',     'Katherine Brown'],
        ];
    }

    /** @dataProvider tokenOrderPairs */
    public function test_token_reordering_classifies_as_match(
        string $candidate,
        string $screened,
    ): void {
        $result = $this->classifier->classify($candidate, $screened);
        $this->assertSame(NameMatchRisk::Match, $result);
    }

    public static function tokenOrderPairs(): array
    {
        return [
            'given-family swap'  => ['Zhang Wei',       'Wei Zhang'],
            'middle name order'  => ['John Michael Smith', 'John Smith Michael'],
        ];
    }

    /** @dataProvider nonMatchPairs */
    public function test_different_names_do_not_match(
        string $candidate,
        string $screened,
    ): void {
        $result = $this->classifier->classify($candidate, $screened);
        $this->assertNotSame(NameMatchRisk::Match, $result);
    }

    public static function nonMatchPairs(): array
    {
        return [
            'similar sounding different people' => ['Ron Smith',  'Rob Smith'],
            'same first name different family'  => ['John Smith', 'John Jones'],
            'partial overlap'                   => ['Ana Garcia', 'Ana Maria Garcia'],
        ];
    }
}
```

The `nonMatchPairs` dataset is where pipelines tend to fail. "Ron Smith" vs "Rob Smith" will score 0.94 on Jaro-Winkler if you're not careful — the token-pair alignment needs to penalize differently enough. Run your full adversarial set and measure precision and recall separately. In compliance, the cost asymmetry matters: a false negative (missed watchlist hit) is typically far more costly than a false positive (manual review). Set your thresholds accordingly.

## Wiring It Together

The full pipeline in a service:

```php
final class CustomerIdentityScreener
{
    public function __construct(
        private NameMatchClassifier $classifier,
        private WatchlistRepository $watchlist,
    ) {}

    public function screen(string $customerName): ScreeningResult
    {
        $watchlistNames = $this->watchlist->allNames();
        $risk = $this->classifier->screenAgainstList($customerName, $watchlistNames);

        return new ScreeningResult(
            customerName: $customerName,
            risk: $risk,
            requiresReview: $risk->requiresManualReview(),
            blocked: $risk->shouldBlock(),
        );
    }
}
```

The enum carries the business semantics. The classifier produces it. The screening result exposes it for the application layer to act on. Nothing in the application layer needs to know a Jaro-Winkler score existed.

## Where to Go from Here

This pipeline handles the common cases. The next layers you'll hit in a real compliance system:

**Multi-name screening**: Some watchlist entries have multiple aliases. Screen against all of them and return the worst-case risk across all alias variants.

**Date-of-birth integration**: A name match with a corroborating DOB match should push a `PossibleMatch` to `Match`. Score signals from multiple data points before classifying.

**Audit trails**: Every classification needs to be explainable — not just the result but the score, which tokens matched, whether a nickname graph hit was used, what phonetic code fired. Store these alongside the result.

**Incremental updates**: Watchlists change. Design your screening service to re-run on affected transactions when new entries are added, not just at onboarding time.

The core insight holds across all of these: names are ambiguous data, and any system that treats them as exact strings will fail the moment it meets real-world input. A pipeline with explicit stages — normalize, alias-expand, score, classify — gives you something you can reason about, tune independently, and audit after the fact. That's the foundation everything else builds on.
