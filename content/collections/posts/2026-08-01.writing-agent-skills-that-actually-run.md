You wrote a skill. The agent reads it, nods along, and then ignores half of it — because the instructions conflict with each other, don't account for missing data, or are written for an idealized scenario that never actually happens. You get a hallucinated summary of Slack activity from a query that returned zero results, or the agent dumps three paragraphs into chat when the spec said one bullet per item.

This is the most common failure mode in skill writing: the skill describes _what the agent should do in the happy path_ and leaves everything else to chance.

Here's how to write skills that actually execute reliably.

## What a Skill Is (and Isn't)

A skill is a structured prompt file that encodes a workflow. It's not a description of what you want — it's a set of executable instructions the agent follows step by step. The distinction matters, because "summarize the Slack activity" reads differently to a human (who fills in the blanks from context) than to an agent (who takes it literally and makes something up if the query returns nothing).

A reliable skill has four parts:

1. **Trigger condition** — when this skill should be invoked
2. **Preconditions** — what must be true before the steps run
3. **Steps** — ordered, unambiguous instructions, with explicit handling for failure cases
4. **Output format** — the exact shape of what the agent should produce

Most skill files cover step 3 in detail and skip the rest. That's why they break.

## The Trigger Condition Is Not Optional

Without an explicit trigger, skills end up either applied everywhere or applied nowhere. The description field in the front matter has to be specific enough that the agent can decide — without ambiguity — whether this skill applies right now.

Bad:

```yaml
---
name: daily-briefing
description: Morning briefing for the user.
---
```

Good:

```yaml
---
name: daily-briefing
description: Use when the user says "daily briefing", "morning kickoff",
    "start my day", "what do I need to do today?", or "brief me".
---
```

The good version lists the exact phrases that trigger the skill. The agent doesn't have to infer intent. This isn't overthinking it — vague triggers are a constant source of skills running at the wrong time or not at all.

## Preconditions: State What Has to Be True

Before a single step runs, the agent needs to know what it's working with. In the daily briefing skill, that means computing today's date, determining whether today's file already exists, seeding from yesterday's file if it doesn't, and never overwriting completed items. Each of those is a precondition that has to be made explicit, or the agent will paper over it.

The pattern looks like this:

```markdown
## Step 0 — Bootstrap

Determine TODAY (ISO-8601). Daily file path: ~/notes/TODAY-{TODAY}.md

- If the file exists: read it fully. Use as base.
- If the file does not exist:
    - Check if yesterday's file exists. If yes, read it.
    - Create today's file from the template below.
    - Seed any incomplete [ ] items from yesterday. Do NOT copy [x] items.
```

Every conditional branch is written out. The agent doesn't decide what "seed from yesterday" means — you tell it exactly which items qualify.

## Graceful Degradation: What to Do When a Tool Returns Nothing

This is where most skills fail silently. The agent calls a Slack search, gets zero results, and then either hallucinates activity or crashes the whole workflow. Neither is acceptable.

Every tool call in a skill should have an explicit fallback:

Bad:

```markdown
Search Slack for messages mentioning @team after yesterday.
Summarize what was discussed.
```

Good:

```markdown
Search Slack: `@team after:YESTERDAY`

If results are empty: note "No team mentions since yesterday" and continue.
Do not infer, estimate, or summarize from zero results.
```

The good version doesn't just handle the failure — it tells the agent what _not_ to do. "Do not infer from zero results" is necessary because that's exactly what the agent will do if you leave it unsaid.

The daily summary skill takes this further for GitLab: it delegates to a sub-skill (`~/.cursor/skills/gitlab-cli/SKILL.md`) that handles the case where `glab` isn't installed or isn't authenticated, rather than letting the main skill break if that tool is missing. External tools should be wrapped in degradable sub-skills, not called raw.

## Avoid Ambiguous Instructions

"Summarize" is an instruction that means something different to every agent run. So is "briefly describe", "give an overview", and "list the key points". These are good enough for humans because we calibrate from context. Agents don't.

Bad:

```markdown
Summarize today's Linear activity.
```

Good:

```markdown
For each Linear issue updated today: one line, format:
`- [ISSUE-ID] — [title] — status changed to [status] ([timestamp])`
If no issues were updated: output "No Linear activity today."
```

The good version eliminates all degrees of freedom. The agent knows the format, the content, the line count, and what to output when there's nothing to say. That's not over-specifying — that's the minimum needed to get consistent output.

The same applies to priority levels. "High priority items" is ambiguous. The daily briefing skill maps it directly to data: `priority=1` is Urgent, `priority=2` is High. There's no interpretation involved. The agent reads the value from Linear and places it in the right section.

## Testing a Skill: Start With Adversarial Inputs

The happy path is easy to write and easy to test. Adversarial inputs are where skills reveal their weaknesses. Before shipping a skill, run it mentally (or actually) against:

- **Empty results from every data source** — does it produce something sensible, or does it hallucinate?
- **Missing preconditions** — what happens if yesterday's file doesn't exist? If the date can't be determined?
- **Partial results** — Slack returns 2 results instead of 20. Does the skill treat that as "done" or "possibly incomplete"?
- **Conflicting data** — Linear says an issue is Done, but the MR it's linked to is still open. What does the agent output?

The investigation skill handles this explicitly at the output stage: if the root cause can't be pinned with confidence, the skill instructs the agent to document what is known, what is unknown, and the best hypothesis with a confidence level. "Uncertain" is a valid, well-defined output. "Probably something with the database" is not.

## When to Stop and Ask vs. Proceed With Defaults

There are two failure modes here: the skill that asks for confirmation at every step (annoying) and the skill that never asks and makes things up (dangerous). The right model is: proceed with defaults unless a default would cause irreversible harm or produce meaningless output.

For the daily briefing, the skill never asks "are you ready?" or "should I search Slack now?" — it fires everything in parallel immediately. The user triggered the skill; that's consent enough. But for the daily summary's reconciliation step — marking items done and moving them to the Done section — the skill specifies exactly which evidence counts as "done" (merged MR, Linear status=Done, message confirming resolution). It doesn't ask the agent to guess.

A good heuristic: if the ambiguity can be resolved by data, resolve it with data. If the ambiguity requires a judgment call that could go wrong in a way the user would care about, stop and surface it.

## The One-Page Constraint

Long skills drift. Instructions written 40 lines above a step get forgotten or contradicted by the time the agent reaches the step. The investigation skill is about 100 lines including the output canvas spec. The daily briefing skill — which pulls from six different sources and writes a structured file — is under 150. Both are dense and concrete, not padded.

The constraint forces real decisions: what belongs in this skill vs. a sub-skill? What can be a default vs. an explicit branch? The daily briefing delegates GitLab entirely to `~/.cursor/skills/gitlab-cli/SKILL.md`. That's not laziness — it's scope management. Each skill should be answerable with a one-sentence description of its single responsibility. "Pull context from multiple sources and produce a triage list" is one responsibility. "Pull context, write a file, send a Slack message, and generate a report" is four.

## The Output Format Section Is the Most Important Part

Whatever the skill does internally, the output format is what the user actually sees. If it's underspecified, the agent fills in the blanks with whatever feels right — varying length, varying structure, varying detail level across runs.

The daily briefing's output spec is explicit to the point of prescriptive:

```markdown
Respond in chat with only:

Daily file updated: [path]

## Urgent / needs decision today

- [1-3 bullets max, most critical only]

## Geekbot prep

**What did you do since yesterday?** [2-3 bullets from yesterday's standup]
**What will you do today?** [top 3 from High Priority]
**Anything blocking?** [inferred blockers or "Nothing so far"]
```

And it ends with: "All detail lives in the markdown file. Do NOT dump walls of text into chat."

That last line is load-bearing. Without it, the agent will produce everything it knows in chat, because "more detail" is the default safe choice. Explicitly forbidding that behavior is what makes the output compact.

## What Reliable Skills Have in Common

Looking across the daily briefing, daily summary, and investigation skills, the pattern is consistent:

- **Exact trigger phrases** in the description — the agent knows when to use the skill
- **Numbered steps** — no ambiguity about order or dependency
- **Explicit empty-result handling** — every tool call has a fallback
- **Concrete output format** — format, length, and content are all specified
- **Named constraints** at the bottom ("Do not apply code changes", "Do NOT dump walls of text")

The constraints at the bottom are a useful pattern. Instead of trying to bake every rule into every step, name the global invariants once, clearly. The agent holds them across the whole workflow.

A skill that runs once and produces the right output is useful. A skill that produces the same right output on the fifth run, when Slack has no results and the GitLab CLI isn't authenticated and yesterday's file is missing, is actually reliable. That's the bar to aim for.
