You need to backfill `geocoded_at` for 200,000 address rows. Each one hits an external geocoding API, so you can't do it in SQL. A migration feels wrong — it blocks your deploy pipeline and isn't built for long-running HTTP calls. An Artisan command feels right, but nothing stops a panicked teammate from running it twice on production.

There's a better pattern. It has a name: one-time operations.

---

## The Three Flavors of "Run This Once"

Laravel gives you three built-in mechanisms for running code once:

**Migrations** are for schema changes. They track what's been applied in the `migrations` table and refuse to re-run completed ones. They run automatically on deploy. They're not designed for long-running data work — a migration that times out mid-way leaves your schema in an inconsistent state and blocks every deploy that follows.

**Seeders** are for populating data in known environments. They're idempotent by convention, not by enforcement. Nothing stops you from running `db:seed` twice.

**Artisan commands** give you full control but zero guarantees. They're the right tool for operational work, but they have no "run once" semantics out of the box.

The gap is real. Data backfills, computed column population, migrating from one third-party provider to another, re-geocoding addresses after a schema change — these are operational changes, not schema changes. They belong in their own category.

## The `completed_operations` Table

The migration tracking system is the right model. Build a lightweight version of it for data operations.

```php
// database/migrations/2026_04_23_000000_create_completed_operations_table.php

return new class extends Migration
{
    public function up(): void
    {
        Schema::create('completed_operations', function (Blueprint $table) {
            $table->id();
            $table->string('name')->unique();
            $table->timestamp('completed_at');
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('completed_operations');
    }
};
```

One row per operation. The `name` column is unique — a duplicate insert fails. That's your idempotency guard.

## A Base Command Class

Create an abstract base class that handles the bookkeeping so individual operations don't have to.

```php
// app/Console/Commands/OneTimeOperation.php

namespace App\Console\Commands;

use Illuminate\Console\Command;
use Illuminate\Support\Facades\DB;
use Illuminate\Support\Facades\Log;

abstract class OneTimeOperation extends Command
{
    abstract protected function operationName(): string;

    abstract protected function handle(): void;

    final public function handle(): int
    {
        $name = $this->operationName();

        if (DB::table('completed_operations')->where('name', $name)->exists()) {
            $this->info("Operation [{$name}] has already been completed. Skipping.");

            return self::SUCCESS;
        }

        $this->info("Starting operation [{$name}]...");

        $start = now();

        try {
            $this->runOperation();
        } catch (\Throwable $e) {
            Log::error("One-time operation [{$name}] failed.", [
                'exception' => $e->getMessage(),
                'trace' => $e->getTraceAsString(),
            ]);

            $this->error("Operation [{$name}] failed: {$e->getMessage()}");

            return self::FAILURE;
        }

        DB::table('completed_operations')->insert([
            'name' => $name,
            'completed_at' => now(),
        ]);

        $elapsed = now()->diffForHumans($start, true);
        $this->info("Operation [{$name}] completed in {$elapsed}.");

        Log::info("One-time operation completed.", [
            'operation' => $name,
            'elapsed_seconds' => now()->diffInSeconds($start),
        ]);

        return self::SUCCESS;
    }

    abstract protected function runOperation(): void;
}
```

The `handle()` method is `final`. Individual operations implement `runOperation()` and `operationName()`. They cannot accidentally skip the idempotency check or the completion log.

> Note the naming: `handle()` is declared `final` and delegates to `runOperation()`. This is intentional — Laravel calls `handle()` on commands, so we intercept it at the base class level.

## Writing an Actual Operation

Here's a concrete example: backfilling a `full_address` computed column from existing address fields.

```php
// app/Console/Commands/Operations/BackfillUserFullAddress.php

namespace App\Console\Commands\Operations;

use App\Console\Commands\OneTimeOperation;
use App\Models\User;
use Illuminate\Support\Facades\Log;

class BackfillUserFullAddress extends OneTimeOperation
{
    protected $signature = 'operations:backfill-user-full-address';
    protected $description = 'Backfill the full_address column for all users.';

    protected function operationName(): string
    {
        return 'backfill_user_full_address_2026_04_23';
    }

    protected function runOperation(): void
    {
        $total = 0;

        User::query()
            ->whereNull('full_address')
            ->whereNotNull('street')
            ->chunkById(500, function ($users) use (&$total) {
                foreach ($users as $user) {
                    $user->update([
                        'full_address' => implode(', ', array_filter([
                            $user->street,
                            $user->city,
                            $user->postal_code,
                            $user->country,
                        ])),
                    ]);

                    $total++;
                }

                $this->line("  Processed {$total} rows so far...");

                // Give read replicas a moment to catch up if your app uses them.
                usleep(50_000); // 50ms
            });

        Log::info('Backfill complete.', ['rows_updated' => $total]);
        $this->info("Updated {$total} rows.");
    }
}
```

A few deliberate choices here:

- **`chunkById` instead of `chunk`**: `chunk` uses `OFFSET`, which gets slower as it progresses through a large table. `chunkById` uses a keyset pagination approach (`WHERE id > ?`) — it stays fast regardless of table size.
- **`whereNull('full_address')`**: The operation is idempotent at the row level, not just at the command level. If it dies halfway through, re-running it (after removing the `completed_operations` row) won't double-process rows that already have a value.
- **The `usleep`**: Aggressive writes can lag read replicas and cause issues for application code reading from them concurrently. A small pause per chunk costs you almost nothing in total runtime and avoids support tickets.

## Running Operations

Run manually on production after deploy:

```bash
php artisan operations:backfill-user-full-address
```

Run all pending operations automatically — similar to `migrate`:

```bash
php artisan operations:run
```

That `operations:run` command queries `completed_operations`, discovers which operation commands haven't been logged yet, and runs them in order. You can hook it into your deploy pipeline alongside `migrate`.

---

## What to Log

Logging is the part most teams skip and then regret. At minimum, emit:

- Operation name and start time (before it runs, in case it dies)
- Row count processed
- Duration
- Any errors, with context

If you have an observability platform (Datadog, Sentry, etc.), emit a span or a custom metric for operation duration. You want to be able to look back three months from now and know that `backfill_user_full_address_2026_04_23` ran, took 4 minutes, and touched 198,443 rows.

Log to a dedicated channel if operations are noisy:

```php
// config/logging.php
'operations' => [
    'driver' => 'daily',
    'path' => storage_path('logs/operations.log'),
    'days' => 30,
],
```

```php
Log::channel('operations')->info('One-time operation completed.', [...]);
```

## Rollback Strategy

The honest answer: most operational changes can't be rolled back automatically, and pretending otherwise is worse than admitting it.

If your operation is purely additive (populating a nullable column), you can usually reverse it:

```php
public function down(): void
{
    User::query()->update(['full_address' => null]);
}
```

If your operation moves data between tables, deletes rows, or integrates with an external API, rolling back requires manual intervention. Document this explicitly in the operation class:

```php
/**
 * ROLLBACK: This operation calls the geocoding API and stores coordinates.
 * To reverse: manually null out lat/lng on affected rows. No API calls needed.
 */
protected function runOperation(): void { ... }
```

Migrations have a `down()` method but most teams disable it in production anyway. One-time operations are no different — what matters is knowing what state you're in and what it takes to undo it.

## Don't Want to Build It Yourself?

The [`php-operations/one-time-operations`](https://github.com/TimoKoerber/laravel-one-time-operations) package by Timo Körber implements this pattern with a proper CLI for listing, running, and resetting operations. It's worth reaching for if you want the conventions without the boilerplate.

The pattern above is closer to the metal — useful if you want control over the base class behavior, tighter integration with your logging setup, or you simply prefer owning what you deploy.

## When to Use What

| Situation                              | Use                        |
| -------------------------------------- | -------------------------- |
| Schema change                          | Migration                  |
| Populate test/dev data                 | Seeder                     |
| One-time data backfill                 | One-time operation         |
| Recurring data cleanup                 | Scheduled Artisan command  |
| Replayable recovery (webhooks, events) | Idempotent Artisan command |

The key distinction between a one-time operation and a scheduled command is the guarantee. A scheduled command is expected to run repeatedly and must be safe to re-run. A one-time operation runs exactly once per environment, and the system enforces that.

If you find yourself writing an Artisan command and adding a comment that says "only run this once" — that comment belongs in code, not in a docblock.
